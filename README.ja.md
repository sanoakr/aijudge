# aiJudge

English: [README.md](README.md)

理系科目のための AI 支援評価プラットフォーム ── プログラミング・数学・レポートを
ひとつの採点基盤の上で扱う。

3 つの機能を持ち、**それぞれ独立して運用できる**。

- **AI 採点** ── 決定的評価器が先（テスト実行・CAS による同値判定・単位検査）、
  残った観点だけを LLM がルーブリックで判定する。判定は必ず根拠を伴い、
  最終権限は必ず人間が持つ。
- **AI 作問** ── 狙った知識要素（KC）に向けて課題を生成し、解けること・解が
  一意であることを機械で検証してから教員のレビューに回す。
- **スキルとポートフォリオ** ── KC ごとの習熟度を根拠つきで推定し、科目と学期を
  またいで集約して、学習者自身が管理できる証明にする。

設計方針と構築計画: [`docs/design/`](docs/design/)。
アーキテクチャ上の決定: [`docs/adr/`](docs/adr/)。

> 状態: **Phase 0 は通しで動く** ── 提出・隔離実行・採点・確定・返却。
> 提出受付とジョブ管理（S3）、ローカル認証（S1）、学習者向け Web、
> PostgreSQL 永続化、採点ワーカー、次の一手のフィードバック、教員レビュー
> コンソールがすべて揃っている。動かし方は [`docs/RUNNING.md`](docs/RUNNING.md)。
>
> Phase 2（1 インスタンスで 2 科目・C と Python）と Phase 3（レポート ──
> 評価方法がまったく違う科目種）も構築済み。**Phase 3 はアーキテクチャの
> 検証が本題で、そこは合格した** ── レポート科目を足すのに `packages/core` と
> `packages/grading` の差分は **0 行**だった。精度の基準はハーネスの中では
> 判定できず、実運用で貯める blind 採点に対して判定する形に移した
> （[ADR 0012](docs/adr/0012-judge-report-grading-in-operation-not-in-the-harness.md)）。
> Phase 4（知識要素・Q-matrix・習熟度推定）は**骨格が通しで動く** ──
> Blueprint が知識要素を指名し、モデルが課題を下書きし、教員が見る前に
> 門 2 つと解答可能性の検査が走り、承認された版だけが出題される。
> **ただし合格基準はまだ 1 つも判定できない** ── 承認率は NOT_MEASURED を返し、
> BKT のパラメータは文献の既定値のままで、実データで当てていない。
>
> **コンテナの脱出試験は通っている** ── fork bomb の封じ込め、非 root 実行、
> read-only ルート、ホスト家目録の不可視、ネットワーク遮断、メモリと出力の上限。
> macOS でも colima 経由で走るので、Linux 限定の話ではない。`sandbox-exec` 単体では
> fork bomb を封じ込められず、それがコンテナを必須にしている理由である ──
> [ADR 0006](docs/adr/0006-execution-isolation.md)（実走して初めて出た 2 つの欠陥も
> そこに書いてある）。
>
> **採点精度の測定は Phase 1 であって Phase 0 ではない。** 必要な記録は最初から
> 取っている（blind 採点は後から復元できない）が、**採点はその測定に依存しない。**
> 精度のゲートは現在 NOT MEASURED を返す。
> [ADR 0007](docs/adr/0007-phase-separation-and-optional-measurement.md) を参照。

## 開発

[uv](https://docs.astral.sh/uv/) が要る。

```fish
uv sync --extra dev

uv run pytest          # テスト
uv run ruff check .    # lint
uv run mypy packages/core/src
uv run lint-imports    # モジュール境界の契約
```

### モジュール境界は「推奨」ではなく強制

`packages/core` は何にも依存せず、I/O を持たない。サブシステムどうしは互いを
import せず、`aijudge_core.events` のイベントだけで連携する。この規則は
`.importlinter` にあり、破ればビルドが落ちる。パッケージを足すときはそこへの
登録も要る ── 忘れても `packages/core/tests/test_boundaries.py` が捕まえる。

理由は [ADR 0001](docs/adr/0001-modular-monolith.md)。

### 科目を足すのにエンジンを触らせない

`packages/grading` は評価器を import しない。評価器は `aijudge.evaluators`
エントリポイントで登録し、`subjects/` の科目プロファイルが名前で指名する。

```yaml
# subjects/cs_intro_c.yaml
deterministic:  [code_test_runner]
ai_evaluators:  [rubric_ai_judge]   # 消しても採点は成立する（設計原則 P2）
review_policy:  {boundary_score: 0.6, boundary_margin: 0.05}
```

インストールされていない評価器を書けば、採点時ではなく**読み込み時に**落ちる。
エンジンが評価器を直接 import したら import-linter の契約がビルドを落とす。
`evals/test_prog2_ex06_p3.py` が実際の課題をこの経路で採点し、実データでも
主張が成り立つことを確かめている。

[ADR 0002](docs/adr/0002-evaluator-plugin-boundary.md) を参照。

### LLM の呼び出しはすべてゲートウェイを通る

モデルのプロバイダを直接呼ぶコードは無い。`packages/llm_gateway` が
「学習者のデータはローカルのプロバイダにしか渡さない」を強制し、構造化出力を
スキーマで検証し、合わなければ**実際のエラーを添えて**再試行し、どのプロンプト版と
モデルが結果を出したかを記録し、自己一貫性のばらつきから確信度を導く。

既定はローカルの ollama（`http://localhost:11434`、`gemma4:e4b`）。**既定が
学外へ送らない側に倒してある**（設計原則 P7）ので、GPU ホストを使うときは
`AIJUDGE_LLM_BASE_URL` と `AIJUDGE_LLM_MODEL` で明示的に指す。

```fish
AIJUDGE_LIVE_LLM=1 uv run pytest evals/test_llm_live.py -v -s
```

それ以外はすべて台本つきプロバイダでオフラインで走る。実機で何が分かったかは
[ADR 0004](docs/adr/0004-llm-gateway.md) ── 制約デコードについての想定は
いくつも実機に接触して壊れた。

### 採点とレビューは別のプロセス

```fish
uv run aijudge-web                             # 学習者が提出する          :8080
uv run aijudge-worker --phase deterministic    # 速い段階
uv run aijudge-worker --phase ai               # 遅い段階（あとから届く）
uv run aijudge-review                          # 教員が確定する            :8765
```

2 つの段階は**別のキュー**である。テスト実行は 0.5 秒、LLM は 17 秒かかるからで
（[ADR 0011](docs/adr/0011-split-the-grading-queue-by-phase.md)）、1 本のキューに
並べると、テストが終わっている学習者の結果が**他人の**モデル呼び出しの後ろで
止まる。exam08（実提出 496 件が 2 時間で一様に到着）で測ると、1 ワーカーで
p95 1689 秒。§9.1 の 30 秒に届かせるには 4 本要った。分けた後は
**1 ワーカーで p95 0.8 秒**、AI の判定は届いたときに届く。

ワーカーは提出を受けて採点し、コンソールは届いた結果を読む。
**レビューは採点の前提条件ではない。** かつてはそうなっていた ── コンソールが
教員の blind 採点の入力後にパイプラインを呼んでいたため、測定データを取ることが
採点そのものの前提になっていた。手段と目的が逆なので、取り消した
（[ADR 0007](docs/adr/0007-phase-separation-and-optional-measurement.md)）。

大半の提出では、教員は判定を読んで成績を確定する。**抽出された**一部については、
先に blind で採点し、そのあとにモデルの判定を見る。モデルを見た後の採点は
それに引きずられ、そこから測る一致度は実力より高く出る ── かといって全提出に
要求するとレビュー全体が重くなるので、抽出する。抽出率は科目ごとに宣言し
（`measurement.blind_sample_rate`）、対象は**提出 ID のハッシュ**で決める。
教員に選ばせると、難しい提出が過剰に選ばれる。

blind の画面には、採点が既に終わっていても判定の痕跡が無い。隠しているのではなく
**応答に含まれていない**（本文が綺麗であることをテストが検査している）。

認証はまだ無く、localhost にしか bind しない。公開する前に S1 の後ろに置くこと。

### 一部だけの合計は、合計が無いより悪い

S6 が停止しているとき AI の観点は飛ばされ、その run には「未採点」として記録される。
決定的評価の結果は学習者に返る ── テストは通ったか通らなかったかのどちらかで、
次に何を直すかはそれで分かる。

**総合点は返さない。** 残った観点を比例配分し直すと、算術的には正しいのに
「観点が欠けていることを知らない人」には「読みやすさ未評価のまま 100%」と読める
数字ができる。観点ごとの表には `確認中` と出るが、ページ上部の大きな数字の方が
先に読まれる。だから教員が欠けを埋めるまで総合点は保留し、**なぜ無いのかを
必ず添える** ── 点があるべき場所の空白は、0 点と見分けが付かない。

教員には見える。欠けを埋めるのが教員の仕事で、そのために決定的評価の結果が要る。

### 成績の確定は、教員が読んだこととは別

教員の待ち行列には、**学習者が異議を申し立てた提出だけ**が並ぶ
（[ADR 0009](docs/adr/0009-show-the-verdict-and-let-the-learner-contest-it.md)）。
受講 91 名 × 課題十数件で、人間が手を付けられる待ち行列はそれしかない ── だが
そうすると異議の出なかった提出が永久に未確定のまま残り、学期が閉じない。
閉じる手段は 2 つある。

```fish
uv run aijudge-finalize --once     # 締切 + n 時間の経過（cron 用）
uv run aijudge-finalize            # 常駐、15 分ごと
```

そして `/manage` の課題単位の**「残りを確定する」**ボタン ── 根拠説明を必須にし、
それを学習者に表示する。

**どちらも `HumanReview` を書かない。** 成績が閉じたことと、教員がその課題を
読んだことは別の事実で、記録は両者を分けて持つ
（[ADR 0010](docs/adr/0010-finalising-a-grade-is-not-a-human-review.md)）。

| 記録 | 意味 | κ の証拠になるか |
|---|---|---|
| `HumanReview` | 教員が**この**提出を読んだ | **なる** |
| `Finalization` | 成績が閉じた。どの経路で閉じたか | ならない |

混ぜると、学期の成績の大半に「教員が AI に同意した」という記録が残り、
誰も読んでいないのに一致度が測れてしまう ── まさに
[ADR 0005](docs/adr/0005-accuracy-measurement.md) が防ごうとしているものである。
分けてあるおかげで、測定側のコードは 1 行も変えずに済んだ。

自動確定は 2 段で走る。黙って閉じる成績は、
[ADR 0009](docs/adr/0009-show-the-verdict-and-let-the-learner-contest-it.md) が
避けようとした「一方的な通知」そのものだからである。

```
採点済み ──→ 締切で仮確定        「09/08 23:59 に確定します ── それまでに言ってください」
         ──→ 締切 + n で確定      異議が出ていなければ
```

**確定時刻を先に示すことが、n で異議受付を締め切る権利を作る。** その窓を逃すと、
画面はフォームではなく担当教員を指す。段階は `due_at` と猶予から導出し、
**保存しない** ── 締切は学期中に動くので、保存した段階は古いままになる。

自動の経路の方が厳しい。レビュー方針が旗を立てたもの（`review_required`）、
未採点の観点があるもの、学習者が異議を申し立てているものは確定させない ──
**誰も見ていない判定が、時計が進んだという理由で成績になってはならない**（P5）。
一括の経路はレビュー方針が旗を立てたものも含む。教員が文書で署名しているからである。

猶予は**分**で持ち、科目が既定を、問題セットがその上書きを持つ
（`auto_finalize_after_minutes`。`/manage` で INSTRUCTOR 以上が編集、既定は無効）。
分にしてあるのは「締切の 10 分後に確定」を表せるようにするため ── 演習中に
出してその場で返す使い方が時間単位では成立しない。`subjects/*.yaml` には置かない ── あちらは採点の設定で
ブラウザの外に置くと決めてある（[ADR 0002](docs/adr/0002-evaluator-plugin-boundary.md)）。
猶予は締切と同じ性質の運用値なので、締切と同じ場所に置く。

学習者には、どの経路で成績が閉じたかを示す。「教員が確認しました」と
「締切が過ぎました」は言い換えられる文ではなく、読まれずに閉じた成績は
異議申立のリンクを開いたままにする。

### 遅延は観点ではなく減点

**採点は締切を知らない。** どの評価器も締切を受け取らず、パイプラインは
`due_at` を見ない。遅れて出したことは、評価が終わったあとに評価の外から当てる。

```
評価（遅延を知らない）              減点（評価を知らない）
  GradingPipeline                   Course.late_penalty_steps × Task.due_at
        └──→ CriterionScore ─┬──────────────┘
                             ↓
              aijudge_core.final_score(run, task_version, review)
```

最初は逆だった ── 教員の採点表の備考欄に `遅延14h` が体裁の列に書かれていたのを
そのまま写し、遵守の観点の 1 段にしていた。段階に畳むと 3 つ壊れる。
観点の κ が「読解の一致」と「事務の一致」の混合を測るようになる。減点の免除は
段階を上げることになり、それは `HumanReview.adjusted_levels` に載って
**「教員が AI に反対した」**と読める（ADR 0010 が塞いだ穴の鏡像）。そして減点が
S7 まで乗って行き、**何ができるか**と**いつ出したか**が混ざる。

段はコースが持つ。`auto_finalize_after_minutes` の隣で、理由も同じである。
**段を置いていないコースでは減点せず、減点の欄自体を出さない** ── 置き忘れた規則が
「適用して 0 だった」ように見えてはならない。教員は免除できる（覆せない減点は
P5 に反する）。免除しても `agreed` は真のまま ── 不同意ではないからである。
**減点だけで合否が入れ替わる件はレビューに回す。** 遅延の事実に迷いは無いが、
免除するかどうかの判断は人にしか無い。

減点は**採点結果に記録**し、表示のたびに計算し直さない。規則は学期中に編集でき、
計算し直す作りだと、既に返した成績が黙って動く。
[ADR 0013](docs/adr/0013-lateness-is-a-deduction-not-a-criterion.md) を参照。

### 生成された課題は、通してもらう必要がある

```fish
aijudge-admin task draft  --course <id> --key gen/ex01 --author <id> \
    --kc cs.loops.termination --model <下書き役> --solver-model <解答役>
aijudge-admin task review list
aijudge-admin task review decide --version <id> --reviewer <id> \
    --reject --reason "入出力の形式が課題文にない"
aijudge-admin task review rate --course <id>
```

生成は易しい方の半分である。生成された課題が使えるかどうかを決めるのは
**それを捨てる仕組み**で、教員が注意を払う前に走る。

**門 1** は参照解答が自分のテストケースを通るかを見る。**門 2** はその解答を
変異させ、テストケースが気づくかを見る
（[ADR 0008](docs/adr/0008-companion-processes-for-network-tasks.md)）。
**効くのは門 2 である** ── 何を渡しても通るテストケースは、門 1 を満点で
通り抜ける。変異は字面で作る（4 種類、構文木を使わない）ので、C と Python が
同じコードを通り、科目を足しても変異器は増えない。

**走らせて初めて出た欠陥が 3 つあり、どれも門 2 を「甘くする」向きだった。**
`#include <stdio.h>` の `<` を反転するとコンパイルが必ず落ち、それが
「殺した」に数えられていた。コンパイルできない変異を分母に入れていたのも同じで、
`exit 0` を返すだけの検査が門 2 を通る道はここにあった。そして等価変異が
**まともな課題を落とした** ── `return 0;` の削除は C99 以降どんなテストでも
殺せず、6 件中 2 件が等価変異だったために正しい解答が 67%（閾値 80%）で
不合格になった。等価変異は一般に除去できないので、**閾値は 1.0 にしない。**

**解答可能性**は、参照解答を渡さずに**課題文だけ**を別のモデルに渡し、返ってきた
解答を門 1 と同じ経路に通す。参照解答と突き合わせはしない ── 正しい
プログラムは何通りもあり、問うているのは「課題文だけで解答に至れるか」だから
である。**解けなくても却下しない。** 曖昧だから解けないのか単に難しいのかを
機械は分けられず、自動で捨てると**難しい良問から先に消える。**

**決めるのは教員である。** 却下には理由が要る（プロンプト改善の材料であり、
承認率の分母でもある）。一度決めた版は覆せない ── やり直しは新しい版から。
承認率は生成物だけを数え（教員が自分で書いた課題は当然承認されるので、
混ぜるといくらでも高く出る）、標本 30 件未満は NOT_MEASURED を返す。

知識要素だけは、**モデルが決して選ばない**（`TaskDraft` に欄が無く、
Blueprint から読む）。ただし **「宣言した KC をその課題が実際に問うているか」は
誰も検証していない** ── 上のどの検査も見ているのは振る舞いだけである。
誤った札が付くと、学習者は問われていない KC の習熟度を得る。BKT は観測列を
畳むので、後から気づいても遡って直せない。間に立つのは 2 つで、
**どちらも自動判定ではない**：レビュー画面が知識要素を必ず表示して
「機械は検証していない」と明記すること、解答役が「自分の解答に実際に必要
だったもの」を申告すること。

門と並んでもう 2 つ検査が走る。**どちらも、答えるより断る方が多い。**

**重複。** 埋め込みは言い換えを、文字 3-gram は写しを捉える。どちらで測ったかを
必ず出す ── 字面だけで「見つからなかった」ことは、無いことの証拠ではない。
埋め込みを持たないプロバイダはゲートウェイがはっきり断る（空を返すと
「近い課題が無い」と区別が付かない）ので、重複検出はそれを捉えて字面に落とし、
そう記録する。**埋め込みも生成と同じ P7 のポリシーを通る** ── 埋め込みからは
元の文が部分的に復元できる。ベクトルは同じモデル・同じ科目の中でしか比べない。

**pgvector は意図的に使っていない。索引であって能力ではない。** 1 コースの
課題は数十〜数百件で、その規模では全件とのコサインの方が速く、テストが走る
SQLite でも動く。索引が要る規模になったら列型だけを替える ── 比較そのものは
authoring にあり、保存先を知らない。

**難度**は同じ近傍の正答率を類似度で重み付けして見込む。提出 15 件未満の課題は
数に入れず、実績の無い近傍は補わずに落とし、残りが 2 件未満なら推定しない
（1 件に賭けると、その課題の癖がそのまま予測になる）。どの経路も
**`NOT_MEASURED` と理由**を返す。そして測っているのは正答率で、出題時期・
任意か必須か・その年の受講者でも動く ── 40% を「難しい」と読み替えないよう、
毎回そう書く。

### 精度は測る。そして「測れていない」は合格ではない

```fish
uv run aijudge-eval --subject cs_intro_c --out accuracy.md
```

**これは採点しない。** 採点とレビューが残した観測レコード（提出 × 観点で 1 行）を
読み、Cohen の κ・二次重み付き κ・見逃し率・レビュー率を計算して
`evals/gates.yaml` と突き合わせる。κ の再計算に LLM もサンドボックスも課題定義も
要らない。`import-linter` が「測定側は採点側を import できない」ことを強制し、
**逆向きも**強制する。両方が要る ── 前者だけだったとき、レビューコンソールが
`analytics` から記録の型を import しており、`analytics` を削除したら採点が
起動しなくなった。記録の型はいま独立したパッケージにある。

判定は 2 値ではなく **3 値**で、終了コードもそれに従う。`0` 合格、`1` 不合格、
`2` **測定不能**。`min_sample_size` を下回る標本は、数字がどれだけ良くても `2` に
なる ── 3 件が完全に一致しても、それは何の証拠でもない。そして `2` は運用の
失敗ではない。**誰かが測るかどうかに関わらず、採点は動く。**

観測レコードは学生の提出と教員の採点を含むので、**repository の外**に置く
（`~/.aijudge/golden`、または `AIJUDGE_GOLDEN_DIR`）。AI の出力を見た後に付けた
採点は除外される ── それに引きずられており、正解データではないからである。
レポートは除外した観測を 1 件ずつ理由つきで並べる。
**ハーネスが自分に都合よく振る舞えないように作ってある**理由は
[ADR 0005](docs/adr/0005-accuracy-measurement.md) にある。
