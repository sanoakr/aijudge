# aiJudge の開発

この文書では、このコードベースの設計上の判断と、開発作業に使うコマンドを説明する。
運用については [`RUNNING.md`](RUNNING.md) を、決定そのものは [`adr/`](adr/) と
[`design/`](design/) を参照すること。

## コマンド

[uv](https://docs.astral.sh/uv/) が必要である。

```fish
uv sync --extra dev

uv run pytest          # テスト
uv run ruff check .    # lint
uv run mypy packages/core/src packages/submission/src packages/persistence/src packages/unit_of_work/src packages/course_admin/src
uv run lint-imports    # モジュール境界の契約
```

保存実装のテストは、**SQLite と PostgreSQL の両方**で同じものを実行する。手元では、
既定で SQLite のテストだけが実行される（多くの作業に DB は要らない）。PostgreSQL のテストも実行するには、
接続先を環境変数で渡す。**CI は両方を実行している**（#243）。

```fish
docker compose up -d
AIJUDGE_TEST_DATABASE_URL=postgresql+psycopg://aijudge:aijudge@localhost:5432/aijudge \
    uv run pytest packages/persistence
```

**PostgreSQL でしか検出できない不具合は、`[postgres]` のテストで確かめる。** 対象は、行ロック
（SQLite に無い）、列の長さ（SQLite は `VARCHAR(n)` の n を検査しない）、JSONB である。

CI はテストを**並列に**実行する（`uv run pytest -n auto --dist loadfile`、pytest-xdist）。
1 プロセスでは 15〜30 分かかっていた。手元でも同じコマンドで実行できる。PostgreSQL の
接続先を渡すと、リポジトリ直下の `conftest.py` が worker ごとに別の DB を使う
（`<DB 名>_gw0`、`<DB 名>_gw1`、…）。テストは表を削除しては作り直すので、1 つの DB を
共有すると、別の worker のテストを壊すためである。**この DB は毎回削除して作り直す**ので、接続先には
使い捨てのサーバーだけを指定すること。運用機へのトンネルの先は、決して指定しない。

### 利用ガイドのサイト

`docs/guide/` は利用者向けガイド（学生・TA・教員）で、`main` にマージされると
`.github/workflows/pages.yml` が GitHub Pages に公開する。設計文書や ADR とは
読者が違うので、別の MkDocs サイトにしてある。

```fish
uv sync --only-group docs
uv run --only-group docs mkdocs serve    # :8000 でプレビュー
```

`docs/guide/images/` のスクリーンショットは、**使い捨ての SQLite にサンプルの
アカウントを作って**撮影したものである。運用 DB からは撮影しない（学生の提出物が
入っているため）。`tools/guide_shots/guide_shots.py` が撮影を一通り行う。このスクリプトは DB を作り、
Web・コンソール・両ワーカーを起動し、ガイドの筋書き（提出・blind 採点・
再確認の依頼とその回答）を順に操作して PNG を書き出す。画面が変わったときと、
リリースのあと（フッターに版数が表示される）に撮り直す。

```fish
uv sync --extra dev --group guide-shots
uv run --group guide-shots playwright install chromium   # 初回だけ
set -x AIJUDGE_SANDBOX docker; set -x AIJUDGE_SANDBOX_WORKDIR ~/.aijudge/work
uv run --group guide-shots python tools/guide_shots/guide_shots.py all
```

採点に docker サンドボックスとモデル（`AIJUDGE_LLM_BASE_URL`、既定はローカルの
ollama）が必要なので、1 回の撮影に数分かかる。ログイン画面だけは運用サイトから撮影する
（`--login-url`）。使い捨ての環境には OIDC が無く、「ログインはまだ設定されて
いません」の画面になるためである。スクリプトは、テンプレートの h2 の文言を目印に画像を切り抜く。見出しを
変えるとスクリプトはエラーで止まるので、古い画像が気づかれずに残ることはない。

## モジュール境界は「推奨」ではなく強制

`packages/core` は何にも依存せず、I/O を行わない。サブシステムどうしは互いを
import せず、`aijudge_core.events` のイベントだけで連携する。この規則は
`.importlinter` に書いてあり、違反するとビルドが失敗する。パッケージを追加するときは、`.importlinter` への
登録も必要である。登録を忘れても、`packages/core/tests/test_boundaries.py` が検出する。

理由は [ADR 0001](adr/0001-modular-monolith.md)。

## 科目を足すのにエンジンを触らせない

`packages/grading` は評価器を import しない。評価器は `aijudge.evaluators`
エントリポイントで登録し、`subjects/` の科目プロファイルが評価器を名前で指定する。

```yaml
# subjects/cs_lang_c_intro.yaml
deterministic:  [code_test_runner]
ai_evaluators:  [rubric_ai_judge]   # 消しても採点は成立する（設計原則 P2）
review_policy:  {boundary_score: 0.6, boundary_margin: 0.05}
```

インストールされていない評価器を書くと、採点時ではなく**読み込み時に**エラーになる。
エンジンが評価器を直接 import すると、import-linter の契約によってビルドが失敗する。
`evals/test_prog2_ex06_p3.py` は実際の課題をこの経路で採点し、実データでも
この設計が成り立つことを確かめている。

[ADR 0002](adr/0002-evaluator-plugin-boundary.md) を参照。

## LLM の呼び出しはすべてゲートウェイを通る

モデルのプロバイダを直接呼ぶコードは無い。`packages/llm_gateway` は次のことを行う。
「学習者のデータはローカルのプロバイダにしか渡さない」という方針を強制する。構造化出力を
スキーマで検証し、合わなければ**実際のエラーを添えて**再試行する。どのプロンプト版と
モデルが結果を出したかを記録する。自己一貫性のばらつきから確信度を求める。

既定の接続先はローカルの ollama（`http://localhost:11434`、`gemma4:e4b`）である。**既定の設定では、
データを学外へ送らない**（設計原則 P7）。そのため、GPU ホストを使うときは
`AIJUDGE_LLM_BASE_URL` と `AIJUDGE_LLM_MODEL` で明示的に指定する。

```fish
AIJUDGE_LIVE_LLM=1 uv run pytest evals/test_llm_live.py -v -s
```

それ以外のテストは、すべて応答を決めておいたプロバイダを使い、オフラインで実行する。実機で分かったことは
[ADR 0004](adr/0004-llm-gateway.md) にある。制約デコードについての想定の多くは、
実機で試すと成り立たなかった。

## 採点とレビューは別のプロセス

```fish
uv run aijudge-web                             # 学習者が提出する          :8080
uv run aijudge-worker --phase deterministic    # 速い段階
uv run aijudge-worker --phase ai               # 遅い段階（あとから届く）
uv run aijudge-review                          # 教員が確定する            :8765
```

2 つの段階は**別のキュー**を使う。テスト実行は 0.5 秒で終わるが、LLM は 17 秒かかるためである
（[ADR 0011](adr/0011-split-the-grading-queue-by-phase.md)）。1 本のキューに
並べると、テストが終わっている学習者の結果が、**ほかの学習者の**モデル呼び出しの後ろで
待たされる。exam08（実提出 496 件が 2 時間で一様に到着）で測ると、1 ワーカーで
p95 は 1689 秒だった。§9.1 の目標の 30 秒以内にするには、ワーカーが 4 本必要だった。キューを分けた後は、
**1 ワーカーで p95 0.8 秒**になり、AI の判定は終わった時点で別に届く。

ワーカーは提出を受けて採点し、コンソールは届いた結果を読む。
**レビューは採点の前提条件ではない。** 以前は前提条件になっていた。コンソールが、
教員が blind 採点を入力したあとにパイプラインを呼んでいたため、測定データを取ることが
採点そのものの前提になっていた。手段と目的が逆なので、この作りをやめた
（[ADR 0007](adr/0007-phase-separation-and-optional-measurement.md)）。

大半の提出では、教員は判定を読んで成績を確定する。**抽出された**一部の提出については、
教員が先に blind で採点し、そのあとにモデルの判定を見る。モデルの判定を見たあとの採点は
その判定に影響されるので、そこから測る一致度は実際より高くなる。一方で、全提出に blind 採点を
求めるとレビューの負担が大きくなるので、一部を抽出する。抽出率は科目ごとに宣言し
（`measurement.blind_sample_rate`）、対象は**提出 ID のハッシュ**で決める。
教員に選ばせると、難しい提出ばかりが選ばれるためである。

blind の画面には、採点が既に終わっていても判定の痕跡が無い。画面で隠しているのではなく、
判定が**応答に含まれていない**（応答の本文に判定が無いことを、テストが検査している）。

認証はまだ無く、localhost にしか bind しない。公開する前に S1 の後ろに置くこと。

## 一部だけの合計は、合計が無いより悪い

S6 が停止しているときは AI の観点を飛ばし、その run に「未採点」として記録する。
決定的評価の結果は学習者に返す。テストは通ったか通らなかったかのどちらかなので、
学習者は次に何を直せばよいかが分かる。

**総合点は返さない。** 残った観点で比例配分し直すと、計算としては正しくても、
観点が欠けていることを知らない人には「読みやすさを評価しないまま 100%」と読める
数字になる。観点ごとの表には `確認中` と表示されるが、ページ上部の大きな数字の方が
先に読まれる。そのため、教員が欠けた観点を採点するまで総合点は保留し、**総合点が無い理由を
必ず表示する**。点があるべき場所が空白だと、0 点と見分けが付かないためである。

教員には決定的評価の結果が見える。欠けた観点を採点するのは教員の仕事で、そのために決定的評価の結果が必要になる。

## 成績の確定は、教員が読んだこととは別

教員の待ち行列には、**学習者が異議を申し立てた提出だけ**が並ぶ
（[ADR 0009](adr/0009-show-the-verdict-and-let-the-learner-contest-it.md)）。
受講 91 名 × 課題十数件の規模では、人が処理しきれる待ち行列はこれだけである。しかし
このままでは、異議の出なかった提出がいつまでも未確定のまま残り、学期の成績が確定しない。
成績を確定する手段は 2 つある。

```fish
uv run aijudge-finalize --once     # 採点 + n 分の経過（cron 用）
uv run aijudge-finalize            # 常駐、15 分ごと
```

もう 1 つは、`/manage` の課題単位の**「残りを確定する」**ボタンである。このボタンは根拠の説明を必須にし、
その説明を学習者に表示する。

**どちらの手段も `HumanReview` を書かない。** 成績が確定したことと、教員がその課題を
読んだことは別の事実なので、記録は両者を分けて持つ
（[ADR 0010](adr/0010-finalising-a-grade-is-not-a-human-review.md)）。

| 記録 | 意味 | κ の証拠になるか |
|---|---|---|
| `HumanReview` | 教員が**この**提出を読んだ | **なる** |
| `Finalization` | 成績が閉じた。どの経路で閉じたか | ならない |

両者を混ぜると、学期の成績の大半に「教員が AI に同意した」という記録が残り、
誰も読んでいないのに一致度が測れてしまう。これは、
[ADR 0005](adr/0005-accuracy-measurement.md) が防ごうとしている問題そのものである。
記録を分けてあるので、測定側のコードは 1 行も変えずに済んだ。

自動確定は 2 段階で行う。予告なしに確定する成績は、
[ADR 0009](adr/0009-show-the-verdict-and-let-the-learner-contest-it.md) が
避けようとした「一方的な通知」そのものだからである。

```
採点済み ──→ その場で仮確定      「09/08 23:59 に確定します ── それまでに言ってください」
         ──→ 採点 + n で確定      異議が出ていなければ
```

**確定までの時間は、課題の締切からではなく、その提出の採点が終わった時刻から数える。**
締切を起点にすると、締切前に提出した学習者は、自分の点が確定するまで何日も待つことになり、
その間は再提出を判断する材料が暫定のままになる。採点は提出の数秒後に終わるので、
そこから数えれば、**締切前に確定し、確定後も締切までは出し直せる**。出し直しは確定に
妨げられず（`Task.accepts_submissions_at` は確定を見ない）、採用されるのは
最高得点の提出である。

**確定時刻を前もって示すから、n 分後に異議の受付を締め切ってよいことになる。** その期間を過ぎると、
画面は依頼のフォームではなく、担当教員への連絡を案内する。この段階は導出し、**保存しない**。

自動確定の方が条件が厳しい。レビュー方針がレビュー必須とした提出（`review_required`）、
未採点の観点がある提出、学習者が異議を申し立てている提出は確定させない。
**誰も見ていない判定を、時間が過ぎたという理由だけで成績にしてはならない**（P5）。
一括確定は、レビュー方針がレビュー必須とした提出も含む。教員が根拠を書いて確定するからである。

猶予は**分**単位で持つ。既定はコースが持ち、問題セットがそれを上書きできる
（`auto_finalize_after_minutes`。`/manage` で INSTRUCTOR 以上が編集でき、既定は無効）。
分単位にしたのは、「締切の 10 分後に確定」を表せるようにするためである。演習中に
提出させてその場で返す使い方は、時間単位では成り立たない。猶予は `subjects/*.yaml` には置かない。科目プロファイルは採点の設定で、
ブラウザの外に置くと決めてあるからである（[ADR 0002](adr/0002-evaluator-plugin-boundary.md)）。
猶予は締切と同じ性質の運用値なので、締切と同じ場所に置く。

学習者には、どの経路で成績が確定したかを示す。「教員が確認しました」と
「締切が過ぎました」は意味の違う文である。教員が読まずに確定した成績では、
異議申し立てのリンクを残しておく。

## 遅延は観点ではなく減点

**採点は締切を知らない。** どの評価器も締切を受け取らず、パイプラインは
`due_at` を参照しない。遅れて提出したことによる減点は、評価が終わったあとに、評価とは別に適用する。

```
評価（遅延を知らない）              減点（評価を知らない）
  GradingPipeline                   Course.late_penalty_steps × Task.due_at
        └──→ CriterionScore ─┬──────────────┘
                             ↓
              aijudge_core.final_score(run, task_version, review)
```

最初は逆の作りだった。教員の採点表で、体裁の列の備考欄に `遅延14h` と書かれていたのを
そのまま写し、遵守の観点の 1 段階にしていた。遅延を段階に組み込むと、3 つの問題が起きる。
1 つ目に、観点の κ が「読解の一致」と「事務の一致」の混ざったものを測るようになる。2 つ目に、減点の免除が
段階を上げる操作になり、それが `HumanReview.adjusted_levels` に記録されて、
**「教員が AI に反対した」**と読める（ADR 0010 が防いだ問題の裏返し）。3 つ目に、減点が
S7 まで伝わり、**何ができるか**と**いつ提出したか**が混ざる。

減点の段階はコースが持つ。`auto_finalize_after_minutes` と同じ場所に置き、理由も同じである。
**段階を設定していないコースでは減点せず、減点の欄そのものを表示しない。** 設定し忘れた規則が、
「適用した結果 0 だった」ように見えてはならないからである。教員は減点を免除できる（覆せない減点は
P5 に反する）。免除しても `agreed` は真のままである。免除は AI への不同意ではないからである。
**減点だけで合否が入れ替わる提出は、レビューに回す。** 遅延したという事実は明らかだが、
免除するかどうかは人にしか判断できない。

減点は**採点結果に記録**し、表示のたびに計算し直さない。規則は学期中に編集できるので、
計算し直す作りにすると、既に返した成績が知らないうちに変わってしまう。
[ADR 0013](adr/0013-lateness-is-a-deduction-not-a-criterion.md) を参照。

## 生成された課題は、通してもらう必要がある

```fish
aijudge-admin task draft  --course <id> --key gen/ex01 --author <id> \
    --kc cs.loops.termination --model <下書き役> --solver-model <解答役>
aijudge-admin task review rate --course <id>
```

`task draft` が保存するのは、**課題ではなく下書き**である。承認と却下は、コンソールの
「未承認の課題（AI 作問）」だけで行う（#522）。CLI には承認と却下のコマンドが無い。

課題の生成は、作問のうち易しい方の半分である。生成された課題が使えるかどうかを決めるのは、
**使えない課題を捨てる仕組み**で、この仕組みは教員が読む前に実行される。

**検査 1（門 1）** は、参照解答が自分のテストケースを通るかを確かめる。**検査 2（門 2）** は、その解答を
変異させ、テストケースが変異を検出できるかを確かめる
（[ADR 0008](adr/0008-companion-processes-for-network-tasks.md)）。
**品質を左右するのは門 2 である。** どんなプログラムでも通るテストケースは、門 1 には満点で
合格してしまうからである。変異は文字列の置き換えで作る（4 種類、構文木を使わない）ので、C と Python で
同じコードを使え、科目を追加しても変異器は増えない。

**実際に実行して初めて見つかった欠陥が 3 つあり、どれも門 2 を「甘くする」ものだった。**
1 つ目に、`#include <stdio.h>` の `<` を反転するとコンパイルが必ず失敗し、それが
「変異を検出した」と数えられていた。2 つ目に、コンパイルできない変異を分母に入れていた。
`exit 0` を返すだけの検査が門 2 に合格できたのは、この 2 つのためである。3 つ目に、等価変異が
**まともな課題を不合格にした**。`return 0;` の削除は C99 以降、どんなテストでも
検出できない。6 件中 2 件が等価変異だったために、正しい解答の検出率が 67%（閾値 80%）になり、
不合格になった。等価変異は一般に除去できないので、**閾値は 1.0 にしない。**

**解答可能性**の検査では、参照解答を渡さずに**課題文だけ**を別のモデルに渡し、返ってきた
解答を門 1 と同じ経路で検査する。参照解答とは照合しない。正しい
プログラムは何通りもあり、確かめたいのは「課題文だけで解答に至れるか」だから
である。**解けなくても却下しない。** 課題文が曖昧だから解けないのか、単に難しいのかを
システムは区別できず、自動で捨てると**難しい良問から先に消える**からである。

**承認するかどうかは教員が決める。** 却下には理由が必要である（理由はプロンプト改善の材料になり、
承認率の分母にもなる）。一度決めた版の判断は覆せない。やり直すときは新しい版を作る。
承認率は生成物だけで数え（教員が自分で書いた課題は当然承認されるので、
含めると承認率がいくらでも高くなる）、標本が 30 件未満なら NOT_MEASURED を返す。

知識要素だけは、**モデルに決して選ばせない**（`TaskDraft` にはその欄が無く、
Blueprint から読む）。ただし、**「宣言した KC を、その課題が実際に問うているか」は
誰も検証していない**。上のどの検査も、プログラムの振る舞いしか見ていないためである。
誤った KC が付くと、学習者は問われていない KC の習熟度を得る。BKT は観測の列を
集約するので、後から気づいても遡って直せない。この誤りを防ぐ手段は 2 つあり、
**どちらも自動判定ではない**。1 つは、レビュー画面が知識要素を必ず表示し、
「システムは検証していない」と明記すること。もう 1 つは、解答役のモデルが「自分の解答に実際に必要
だったもの」を申告することである。

門と並んで、さらに 2 つの検査を実行する。**どちらの検査も、結果を出すより「測れない」と報告することの方が多い。**

**重複。** 埋め込みは言い換えを、文字 3-gram は文字どおりの写しを検出する。どちらで測ったかを
必ず表示する。文字の並びだけで「見つからなかった」ことは、重複が無いことの証拠にならないためである。
埋め込みを持たないプロバイダについては、ゲートウェイが明示的にエラーを返す（空を返すと、
「近い課題が無い」と区別できない）。重複検出はそのエラーを受けて文字 3-gram に切り替え、
そのことを記録する。**埋め込みも、生成と同じ P7 のポリシーに従う。** 埋め込みからは
元の文を部分的に復元できるためである。ベクトルは、同じモデル・同じ科目の中でしか比べない。

**pgvector は意図的に使っていない。pgvector は索引で、新しい能力を加えるものではない。** 1 コースの
課題は数十〜数百件で、その規模では全件とのコサイン類似度を計算する方が速く、テストを実行する
SQLite でも動く。索引が必要な規模になったら、列の型だけを替える。比較の処理そのものは
authoring にあり、保存先を知らない。

**難度**は、似た課題の正答率を類似度で重み付けして推定する。提出が 15 件未満の課題は
数に入れず、実績の無い課題は補わずに除き、残りが 2 件未満なら推定しない
（1 件だけに頼ると、その課題の癖がそのまま予測になる）。推定しない場合は、どの経路でも
**`NOT_MEASURED` と理由**を返す。また、測っているのは正答率で、正答率は出題時期・
任意か必須か・その年の受講者によっても変わる。正答率 40% を「難しい」と読み替えないよう、
毎回そのことを表示する。

## 精度は測る。そして「測れていない」は合格ではない

```fish
uv run aijudge-eval --subject cs_lang_c_intro --out accuracy.md
```

**このコマンドは採点しない。** 採点とレビューが残した観測レコード（提出 × 観点で 1 行）を
読み、Cohen の κ・二次重み付き κ・見逃し率・レビュー率を計算して、
`evals/gates.yaml` の基準と照合する。κ の再計算には、LLM もサンドボックスも課題定義も
要らない。`import-linter` は「測定側は採点側を import できない」ことを強制し、
**逆向きも**強制する。両方が必要である。前者だけだったときは、レビューコンソールが
`analytics` から記録の型を import していたため、`analytics` を削除すると採点が
起動しなくなった。記録の型は、いまは独立したパッケージにある。

判定は 2 値ではなく **3 値**で、終了コードもそれに従う。`0` は合格、`1` は不合格、
`2` は**測定不能**である。標本が `min_sample_size` を下回ると、数字がどれだけ良くても `2` に
なる。3 件が完全に一致しても、それは何の証拠にもならないからである。また、`2` は運用の
失敗ではない。**誰かが測るかどうかに関わらず、採点は動く。**

観測レコードは学生の提出と教員の採点を含むので、**リポジトリの外**に置く
（`~/.aijudge/golden`、または `AIJUDGE_GOLDEN_DIR`）。AI の出力を見たあとに付けた
採点は除外する。AI の出力に影響されており、正解データとして使えないからである。
レポートは、除外した観測を 1 件ずつ理由付きで並べる。
**ハーネスが自分に都合よく振る舞えないように作ってある**理由は
[ADR 0005](adr/0005-accuracy-measurement.md) にある。

## ログは 3 つある。混ぜると 1 つ失う

「ログ」と一括りにすると、保存すべき期間の違う 3 つの記録が、同じ言葉で区別できなくなる。

| | 何の記録か | 置き場 | 消えてよいか | 書けなかったら |
|---|---|---|---|---|
| 運用ログ | プロセスに何が起きたか | journald | よい（90 日） | 何も起きない |
| 監査ログ | **誰が**成績に届く何を変えたか | DB・append-only | だめ | 操作ごと失敗する |
| 採点記録 | どのルーブリック・プロンプト・モデルが点を出したか | `GradingRun` | だめ | 採点を保存しない |

3 つを 1 つにまとめると、2 つの問題のどちらかが起きる。消えては困る記録が、ローテートで消える場所に
置かれるか、ログ基盤の不調が採点を止めるかである。

運用ログを扱うのは `packages/telemetry` である。ログを設定するのは合成ルート（`apps/*`）
だけで、サブシステムが import すると `.importlinter` によってビルドが失敗する。
ライブラリが自分でハンドラを決めると、同じコードでも、どのアプリに取り込まれるかによって
ログの出方が変わるためである。**実際にそうなっていた。** `basicConfig` はワーカーと
finalize にしか無く、web とコンソールでは `logger.warning` が root の
lastResort ハンドラに渡り、INFO は捨てられていた。

**載せるのは識別子だけ。** 提出物の本文・氏名・プロンプト・モデル出力は載せない。
journald はバックアップも暗号化もされていないので、学習者データを journald に書いた
時点で、ゲートウェイが守っている保証（ADR 0004）を迂回してしまう。
`aijudge_telemetry.bind` は規約に頼らず、型と長さで値を拒否する。URL を丸ごと INFO で
出力するライブラリ（`httpx` など）は、設定の時点でログの水準を WARNING に下げる。そうしないと、
aiJudge のコードが 1 行もログを書かなくても、OIDC の認可コードが journal に残ってしまう。

ミドルウェアはリクエストに `request_id` を付け、応答ヘッダにも載せる。ワーカーは
ログに `job_id` / `submission_id` / `phase` を付ける。**web とワーカーのログを結び付ける鍵は
`submission_id`** で、これは両側に既にあった値である。#60 と #80 で欠けていたのは
まさにこの鍵だった。画面からは「採点が遅い」としか分からず、失敗の記録は、
どの提出のものか分からないワーカーのログの中にあった。
[ADR 0016](adr/0016-three-logs-operational-audit-and-grading-record.md) を参照。


## 監査ログは操作ごと失敗する。運用ログはしない

3 つのログの 2 つ目を扱うのが `packages/audit` である。監査ログは、成績に影響する何を**誰が**変えたかを
記録し、**消してはいけない**ログでもある。成績への異議申し立ては、学期が
終わってから届くことがあるためである。

監査ログは `uow.audit`、つまり操作と同じトランザクションの中に書く。これが
`packages/telemetry` との決定的な違いである。操作が巻き戻れば監査行も一緒に
巻き戻り（`--dry-run` の確定は何も残さない）、監査行を書けなければ操作の方が失敗する。
記録の型は保存先にも採点エンジンにも依存しない（契約 2 本）ので、
インメモリと SQL の 2 つの実装が同じテストに合格する。このリポジトリのほかの store と同じである。

記録が保つべき区別は 3 つある。

- **操作者は 3 種類ある。** `user`、`system`（人間の操作者がいない ── 締切
  経過による確定について、それが事実である）、そして `anonymous`（認証されて
  いない試み）。ログイン失敗は 3 つめで、パスワードを間違えたのが口座の
  持ち主とは限らず、**本人でない場合こそ記録が要る**。口座は *対象* に書き、
  操作者は名前を付けない。応答は「存在しない ID」と「パスワード違い」を
  分けないままだが（列挙を防ぐ）、**記録は分ける** ── 分けないと、多数の ID への
  総当たりと 1 つの口座への総当たりが後から同じに見える。
- **ログイン失敗は commit する。** 監査行は操作のトランザクションに含まれるので、
  失敗の処理がそのまま return すると、攻撃に気づくための記録まで
  巻き戻ってしまう。ログイン失敗には、巻き戻すべき「操作」は無い。
- **監査行は `HumanReview` ではない。** 教員の 1 操作が両方を書くが、κ の
  証拠になるのはレビューだけである（ADR 0010）。

`AuthService` が書くのは認証の結果だけである。認証の結果は、この層だけが知っている。
トークンの発行、受講、権限の変更は、呼び出し側が書く。これらを操作しているのは対象の
利用者ではないので、`AuthService` で書くと、**操作された人が操作した人として記録されてしまう。**

監査ログには、パスワード、再発行した平文のパスワード、API トークン、提出物の本文を記録しない。
`detail` は変更の前後の値を入れる欄で、上限を超える値はドメイン模型が拒否する。監査表を、
学習者データのもう 1 つのコピーにしないためである。

[ADR 0016](adr/0016-three-logs-operational-audit-and-grading-record.md) を参照。
