# 出題の可視性 ── 誰に・いつ見せるか

- ステータス: **検討中**（`feat/task-visibility` ブランチ）
- 日付: 2026-09-24
- 関連: #102, #108, #119, #146, #333, #340, #83 / ADR 0013, 0018, 0020 /
  `docs/design/online-coding-test.md`（`feat/online-coding-test`。本書を前提にする）

## 0. 何が問題か

課題の表示・日程・受付は、いま**課題単位で、受講者全員に同じ**である。
オンラインコーディングテストの検討で、次の 2 つが足りないことが分かった。
どちらも IDE とは独立した問題なので、別枠で先に決める。

### A. 一部の学習者にだけ出したい（追試・再試験）

問題セットを名簿で絞る手段が無い。追試を作ると受講者全員に見え、受けない
学生の画面にも「未提出」として並ぶ。

### B. 試験の内容が、公開前に TA に見えている

公開前の問題セットは、教員と TA の両方に見える。経路は 2 つある。

| 経路 | 根拠 | 見えるもの |
|---|---|---|
| 学生画面 `preview`（`_group_by_unit`・`_may_submit_before_open`） | #340「公開前こそ実物で確かめたい」 | 一覧・問題文・試しの提出 |
| コンソール `_require_reader`（`manage.py:247`） | #102「公開前の課題も読める：採点は公開前に用意されるものだから」 | 問題セットの画面（`/manage/courses/{id}/units/{unit}`）・課題の編集画面（読むだけ） |

どちらも**課題**を前提にした判断で、正しい。問題は、**試験と課題が区別されて
いない**ことである。課題なら TA が先に読んで質問対応に備えるのは望ましいが、
試験では TA（多くは学生）が内容を先に知ること自体が漏洩の経路になる。

加えて、**教員が公開前に試しに出した提出**（`is_trial`）も、提出一覧から TA に
見えうる。試験では、これは模範解答に近いものである。

## 1. 決定

### 1.1 A: 追試は別の課題にして、出題先グループで絞る

同じ課題のまま、一部の学習者だけ日程を上書きする形は採らない。

| | 別の課題 + 出題先（採る） | 同じ課題で学習者ごとに日程を上書き |
|---|---|---|
| 締切の求め方 | 課題ごとに 1 つ（いまと同じ） | 学習者ごとに変わる |
| 手が入る既存の規則 | 見せる・数える箇所の判定だけ | 受付判定・遅延減点（ADR 0013）・自動確定・動画の保存期間（ADR 0020）・カウントダウンの全部 |
| 成績 | 本試験と追試が別の課題になる。まとめるのは教員（**運用上問題なし、と確認済み**） | 1 つの欄 |

### 1.2 B: 「公開まで教員だけ」を課題の性質として持つ

`Task.confidential_until_open: bool`（既定 `False`）。真の課題は、`opens_at` より前は
**教員（とテナント管理者）にしか見えない**。TA には `opens_at` から見える。

TA に公開後も見せない、はしない。公開後は学習者に見えているものであり、
TA が質問対応と採点をするには読めなければならない（#102 の判断はそのまま生きる）。

### 1.3 「試験」は種別ではなく、設定の組み合わせにする

`kind: exam` のような種別を課題に持たせない。**種別に振る舞いを紐づけると、
種別を変えたときに何が変わるかが見えなくなる** ── 採点保留も学内限定も TA からの
秘匿も、それぞれ独立に要る場面がある（学内限定だが秘匿は要らない演習、など）。

モデルは独立した値のまま持ち、**コンソールに「試験として設定」のひと押し**を置く。
押すと問題セットの全課題に次をまとめて入れ、画面上でそれぞれ外せる。

| 値 | 既存か | 試験での値 |
|---|---|---|
| `confidential_until_open` | 新 | 真 |
| `grading_starts_at` | 既存（#67） | 受付の終わり（試験中は採点しない） |
| `campus_only` | 既存（#333） | 真（教室で行う試験の場合） |
| `answer_mode` | 新（IDE 側） | `editor`（IDE で行う場合。IDE 導入後） |

## 2. 型

- `CourseGroup(id, course_id, name)` と名簿 `course_group_members(group_id, user_id)`。
  コースごとに名前を付けて `/manage` で編集する（例:「前期追試対象者」）。
  名簿に入れられるのはそのコースの学習者だけ
- `Task.audience_group_ids: tuple[CourseGroupId, ...] = ()`。**空は受講者全員**（いまと同じ）。
  複数を持てば、いずれかの名簿に入っている学習者に出す（和集合）
- `Task.confidential_until_open: bool = False`

**最初から複数にしておく理由**: 将来、**グループごとに異なる問題セットを出す**
可能性がある（2026-09-24 確認。例: 時限の違う 2 クラスに別の問題を出す）。
これは「セット X はグループ 1 に、セット Y はグループ 2 に」と課題ごとに
出題先を付ければ、いまの型のまま表せる。単数で作ると、「1 と 2 の両方に出す
共通問題」を表すためにグループを合成するか、型を変える移行が要る。JSON の中の
値なので列の手間は無いが、既存の文書の書き換えは避けたい。

`Task` は `tasks` テーブルに JSON（`document`）で入っているので、2 つの値に
**列の追加は要らない**（`campus_only` の追加 `b83e5c17a204` と同じ）。新しい
テーブルはグループと名簿の 2 つだけ。

`campus_only` と同じく、**課題が持つが値を決めるのは問題セット単位**で、
コンソールの画面もそう作る。問題セットは `Task.unit` の束ね方にすぎず、
実体が無い（ADR 0018 の背景）。

## 3. 見える・見えないの規則

### 3.1 表

| 役割 | 通常の課題・公開前 | 通常の課題・公開後 | 秘匿の課題・公開前 | 秘匿の課題・公開後 |
|---|---|---|---|---|
| 教員・テナント管理者 | 見える | 見える | 見える | 見える |
| TA | 見える（#340・#102） | 見える | **見えない** | 見える |
| 学習者（出題先の中） | 見えない | 見える | 見えない | 見える |
| 学習者（出題先の外） | 見えない | **見えない** | 見えない | **見えない** |

- 「見えない」は、一覧に出さず、URL を直に開いても **404**（受講していない課題と
  区別しない）
- **出題先は学習者にだけ効く。** 教員・TA は名簿に関係なく見える
  （TA が追試の質問に答えられないと困る）。秘匿は出題先と独立に効く

### 3.2 判定は 1 か所で

**判定の関数を 1 つにし、全経路から呼ぶ。** 経路ごとに書くと、どれかが漏れる
（#119 の教訓。実際、`submit-video` は学内限定の判定を呼んでいない ── §6）。

```python
def may_see(task: Task, role: Role, *, in_audience: bool, now: datetime) -> bool:
    """この役割の人に、いまこの課題を見せてよいか。"""
```

置き場は `packages/core`（I/O なし・純粋関数）。学生画面とコンソールの両方が
同じ関数を呼ぶ。名簿を引くのは呼ぶ側（`in_audience` を渡す）。

### 3.3 各経路での適用

洗い出しの結果（2026-09-24）。

**学生画面**

| 箇所 | 何をしているか | 変更 |
|---|---|---|
| `_course_and_tasks`（`app.py:1858`） | 一覧の元。`withdrawn` を除く | **判定を足す**。コースページ・進捗・到達度はここから派生するので、ここで絞れば「出題先の外を未提出と数えない」も自動で満たす |
| `_task_and_course`（`app.py:1889`） | 課題ページ・提出・動画の関門の入口 | **判定を足す**。直 URL での閲覧と提出はここで止まる |
| `_group_by_unit(preview=...)` | 公開前のセットを教員・TA に出す | `preview` を「役割」ではなく `may_see` の結果で決める |
| `_may_submit_before_open` | 公開前の試し提出を教員・TA に開ける | 秘匿の課題では TA を外す（`may_see` と揃える） |
| `_submission_view`（`app.py:1944`） | 自分の提出の閲覧 | **変えない**。所有で判定する。名簿から外れても、自分の出した提出と成績は見られる |
| `statement_image`（`app.py:1271`） | 課題文の画像。受講者なら返す | 変えない（下記） |

**コンソール**

| 箇所 | 変更 |
|---|---|
| `_require_reader` を通る課題の画面（問題セット `manage.py:2577`・課題の編集 `:4585`） | 課題ごとに `may_see` を掛ける。TA には秘匿の公開前の課題を出さない |
| 提出の一覧・レビュー・blind | 秘匿の公開前の課題への**試し提出**（`is_trial`）を TA に出さない。公開前に学習者の提出は存在しないので、実質これだけ |

ただし、公開前の試験の課題文を画面に写して共有された場合は防げない（どの
仕組みでも同じ）。

### 3.4 監査

- 名簿の変更（誰を足した・外したか）と、2 つの値の変更は監査ログに残す
  （`AuditAction` に足す）。どちらも「誰が何を見られるか」を変える操作である

### 3.5 外から登録する API

名簿と出題先は、画面が無くても外から登録できるようにする（2026-09-24 の要望）。
当面は数が少ないので画面の手入力で足りるが、グループごとに問題セットを出し分ける
運用になると、名簿の作成と割り当てを手元のスクリプトから流したくなる。

**既存の API（`apps/reviewconsole/.../api.py`）に足す。** 認証は同じ
`Authorization: Bearer aij_...`（利用者の API トークン。Cookie は見ない ── CSRF の
経路を最初から持たない、という既存の判断のまま）。権限はそのコースの教員以上。

| メソッド・パス | 内容 |
|---|---|
| `GET /api/courses/{course_id}/groups` | グループと人数の一覧 |
| `PUT /api/courses/{course_id}/groups/{name}` | グループを作る・名簿を**丸ごと置き換える**。本文は `{"members": ["<login>", ...]}` |
| `DELETE /api/courses/{course_id}/groups/{name}` | グループを消す。**出題先として使われているグループは消せない**（409） |
| `PUT /api/courses/{course_id}/units/{unit}/audience` | 問題セットの全課題の出題先を置き換える。本文は `{"session": n, "groups": ["<name>", ...]}`。空は全員 |

- **置き換え（PUT）にして、足し引きの API は作らない。** 同じ要求を 2 度流しても
  結果が同じ（冪等）で、スクリプトの再実行が安全になる。応答で「足された人・
  外された人」を返し、何が起きたかを呼び出し側が確かめられるようにする
  （既存の `created` を返す判断と同じ）
- 名簿は **login（学籍番号）** で指定する。受講登録の名簿（`aijudge_admin.roster`）と
  同じ識別子である。そのコースの学習者でない login は、**全体を拒否**して、
  知らない login の一覧を返す（一部だけ登録されると、漏れに気づけない）
- グループはパスの上では**名前**で指す。スクリプトから ID を引き直さずに済む。
  名前はコース内で一意とする
- 画面の保存と API は**同じ関数**を通す（名簿の検証・監査ログ）。経路ごとに
  書くと、片方でしか効かない検査が生まれる（#119）
- 同じ操作を `aijudge-admin` の CLI からも呼べるようにする（運用機で直接流す場合）

**出し分けの検査（将来）**: グループごとに問題セットを出し分けるとき、
「どの版にも割り当たっていない学習者」と「2 つの版に割り当たっている学習者」は
設定の誤りである可能性が高い。問題セットの画面に警告として出す。判定はしない
（共通問題を両方に出す、のような正当な重なりがある）。

## 4. 既存を壊さないこと

| # | 不変条件 | 確かめ方 |
|---|---|---|
| V1 | 既定値（`audience_group_ids=()`・`confidential_until_open=False`）の課題では、全経路の振る舞いがいまと同じ | 既存のテストが無変更で通る。`may_see` の表（§3.1）の全マスをテストで固定 |
| V2 | 判定は `may_see` の 1 つだけ | 学生画面・コンソールの各経路で、出題先の外・秘匿の公開前に 404 になるテスト |
| V3 | 名簿から外れても、自分の提出と成績は見られる | 提出後に名簿から外し、提出ページが開けるテスト |
| V4 | 出題先の外の学習者は「未提出」として数えない | コースページの未提出数・進捗の分母のテスト |
| V5 | 課題の編集・YAML の再適用で 2 つの値が消えない | `save_task` のテスト（#83 と同じ形） |
| V6 | 教員の試し提出が、秘匿の公開前に TA に見えない | コンソールの提出一覧のテスト |

新しいテーブルが増えるので、in-memory と SQL の両方に同じテストを掛け、
`test_migrations.py` を通す。

## 5. 段階

| 段階 | 内容 |
|---|---|
| 1 | `may_see`（core）と表のテスト。`confidential_until_open` と学生画面・コンソールへの適用。B を先に塞ぐ |
| 2 | `CourseGroup`・名簿・`audience_group_ids`。`/manage` の名簿画面と問題セットへの設定、**API（§3.5）** |
| 3 | 「試験として設定」のひと押し |

段階 1 は小さく、運用中の問題（TA への事前公開）を直接塞ぐので、先に単独で
入れられる。決定は ADR 0025（出題の可視性）として起こす。

## 6. 別件で見つかった既存の穴（先に直す）

**`POST /tasks/{id}/submit-video`（`app.py:1136`）が学内限定の判定（`_require_campus`）を
呼んでいない。** 分割アップロード（`_video_gate`）と通常の提出は呼んでいる。
学内限定の動画課題に、このルートを使えば学外から出せる。

本書の変更とは独立した修正として、先に別の PR で直す（`_require_campus` を
足し、学外からの `submit-video` が 403 になるテスト）。本書の `may_see` と同じく、
**関門を 1 つにする**（§3.2）方向の修正でもある。

## 7. 決まったこと（2026-09-24）

| # | 論点 | 決定 |
|---|---|---|
| Q1 | 秘匿の課題を TA に見せ始めるとき | **`opens_at` から**。TA が試験監督をする場合も開始と同時に見える |
| Q2 | 秘匿の課題で、公開前の TA の試し提出 | **許さない**。公開前の試し提出は教員だけ |
| Q3 | 名簿の登録手段 | 当面は画面の手入力。**画面が無くても外から登録できる API** を用意する（§3.5）。将来、グループごとに異なる問題セットを出す可能性がある |
