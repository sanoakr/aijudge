# AI 学習評価プラットフォーム（仮称 aiJudge）設計方針と構築計画

## Context

プログラミング課題の自動採点システム Sharif Judge を出発点としつつ、**実装はゼロベースの新規開発**とし、数学・理科・レポートなど理系科目全般をカバーする Web 学習システムを設計する。

解きたい問題は 3 つある。

1. **採点の人手がボトルネック**。テストケース実行だけでは「論理・過程・記述」を評価できず、数学やレポートには適用できない。
2. **作問の負荷**。個別最適な練習問題を供給するには、KC（知識要素）を狙った問題を継続的に作る必要がある。
3. **学習成果が課題単位で分断されている**。科目・年度をまたいで「この学習者は何ができるか」を示す資産になっていない。

これを、AI 自動採点・AI 作問・スキル/ポートフォリオという 3 つの**独立して運用可能なサブシステム**として構築する。大規模運用（複数機関・複数科目）に耐える構造を最初から設計に入れるが、実装は初期運用に必須な Phase 0 から始め、段階的に拡張する。

### 前提（確定事項）

| 項目 | 決定 |
|------|------|
| 既存資産 | Sharif Judge は機能仕様の参照のみ。コード継承・データ移行はしない |
| 実行基盤 | 学内オンプレ GPU 中心（ローカル LLM 主／クラウド LLM は精度上限測定と補助）。個人情報は外部非送信 |
| 外部連携 | LTI 1.3・SSO（学認/SAML・OIDC）・Open Badges 3.0 / VC は**設計に織り込むが実装は後段**。当面は単独運用で動くこと |
| Phase 0 | プログラミング課題の提出・採点・教員確定までを初期運用の必須範囲とする（§9） |

参考資料：`ai4science/01〜03_*.md`（研究動向）、`ai4science/system_architecture.svg.png`（研究計画側のアーキ図）。本設計はこれらを制約ではなく参考として扱う。

## 1. 設計原則

以下 9 つを、以降のすべての判断の根拠とする。迷ったらこの順で優先する。

**P1. 科目非依存コア + 科目プラグイン**
コアが知る語彙は `Task / Rubric / Submission / GradingRun / KC / Skill / Credential` のみ。「コードか数式かレポートか」はコアに漏らさず、**Evaluator プラグイン**に閉じ込める。新科目の追加が「プラグイン 1 個追加」で済むかどうかが、このアーキテクチャの成否の判定基準。

**P2. サブシステムの独立運用**
各サブシステムは (a) 専用 DB スキーマ、(b) 公開 REST API、(c) 発行/購読イベント、を持つ。他が停止しても劣化動作する（例：Skill サービスが落ちても採点は完了し、イベントは後から追いつく）。単体で他大学に配布・導入できる粒度を保つ。

**P3. 決定的評価が先、AI は後**
採点は必ず「決定的評価器 → AI 評価器 → 集約」の順。テスト実行・CAS による数式同値判定・単位/有効数字チェック・形式検証は決定的側で確定させ、AI には**残りのルーブリック観点だけ**を担当させる。LLM の数値計算誤りをアーキテクチャで回避する。

**P4. AI 出力は必ず根拠付き構造化データ**
スコアだけを返させない。`criterion_id → evidence（解答中の該当箇所）→ judgement → score → rationale` の構造化 JSON を強制する。説明可能性は後付けできない（英国 AI 採点原則・EU AI Act の高リスク分類を想定）。

**P5. Human-in-the-loop を既定とする**
AI 採点は「確定」ではなく「提案」。confidence・評価器間の不一致・境界点付近を判定してレビューキューに振り分ける。教員の修正は**必ず学習データとして記録**し、ルーブリック改善とプロンプト評価に還流させる。

**P6. Q-matrix を全サブシステムの結節点にする**
`Task × KC` の対応付けを唯一の共通言語にする。作問は「KC を狙って生成」、採点は「KC 別の evidence を出力」、ポートフォリオは「KC 別習熟度の集約」。これにより 3 サブシステムは互いを直接知らずに連携できる。

**P7. LLM はゲートウェイ経由・ポリシールーティング**
アプリは LLM プロバイダを直接呼ばない。ゲートウェイが「個人情報を含むプロンプトはローカルモデル限定」「作問など非個人データはクラウド可」をポリシーで強制する。モデル差し替えがアプリ改修を伴わないこと。

**P8. 採点は再現可能でなければならない**
`(rubric_version, prompt_version, model_id, params, input_hash)` を GradingRun に記録。同一入力の再採点、モデル更新時の全件再評価、年度をまたいだ公平性の検証を可能にする。**採点結果は上書きせず追記**（イミュータブル）。

**P9. モジュラーモノリスから始める**
最初からマイクロサービスにしない。1 リポジトリ・1 デプロイ単位で、**モジュール境界だけを厳密に**保つ（モジュール間はインターフェース経由のみ、DB 直接参照禁止）。負荷とチーム分割の実態が見えた時点で境界線で切り出す。切り出しコストが低いことが P2 の担保。

### 2.1 レイヤ

```
┌─ Web UI ────────────────────────────────────────────────┐
│  学習者ポータル / 教員コンソール / ポートフォリオ公開ページ │
└──────────────────────┬──────────────────────────────────┘
                       │ BFF (REST + SSE)
┌──────────────────────┴──────────────────────────────────┐
│  コアサブシステム（S1–S9）                                │
│  ┌──────────┐ 内部イベントバス（Outbox → Redis Streams） │
└──┼──────────┼─────────────────────────────────────────┬─┘
   │          │                                          │
┌──┴────┐ ┌───┴──────────────┐ ┌──────────────┐ ┌───────┴──────┐
│Evaluator│ │Execution Sandbox│ │ LLM Gateway  │ │ Data Layer   │
│Plugins  │ │ (gVisor/Firecr.)│ │(local/cloud) │ │PG/S3/Redis   │
└─────────┘ └─────────────────┘ └──────────────┘ └──────────────┘
```

### 2.2 サブシステム一覧

| ID | 名称 | 責務 | 単独運用時の縮退 | Phase |
|----|------|------|-----------------|-------|
| **S1** | Identity & Tenancy | 認証、機関/コース/受講のテナント境界、権限。IdP は Keycloak。LTI 1.3・SAML は**アダプタとして差し込む口だけ**用意 | ローカル DB 認証で動く | 0（最小）/ 2（コース・教員）/ 8（機関） |
| **S2** | Authoring | 問題・ルーブリック・テストケース・KC タグの作成とバージョニング。AI 作問ワーカーを内包 | AI 作問なしで手動登録運用が可能 | 0（手動登録）/ 4 |
| **S3** | Submission & Orchestration | 提出受付、Artifact 保管、採点ジョブのキュー投入・冪等・リトライ・再採点 | — （コア） | 0 |
| **S4** | Execution Sandbox | 隔離環境でのコード実行・CAS 実行・シミュレータ実行。言語/ツールはコンテナイメージで定義 | 決定的評価が不要な科目では未使用 | 0（コード）/ 4–5（CAS） |
| **S5** | Grading Engine | 採点パイプライン実行、Evaluator レジストリ、スコア集約、confidence 算出、HITL 振り分け | AI 無効時は決定的評価器のみで完結 | 0 |
| **S6** | LLM Gateway | プロバイダ抽象、プロンプト/モデルのバージョン管理、PII ポリシールーティング、コスト・レート制御、キャッシュ | 停止時は AI 評価器のみスキップ | 0 |
| **S7** | Skill & Knowledge | KC 体系、Q-matrix、習熟度推定（BKT → DKT 差替可）、次問推薦 | 停止しても採点は完了（イベントは後追い） | 4 |
| **S8** | Portfolio & Credential | スキル状態の集約、公開ポートフォリオ、バッジ発行。OB3.0/VC は**発行アダプタ**として分離 | 内部表示のみで運用可 | 7 |
| **S9** | Analytics（測定） | 人間採点との一致率、採点ばらつき、バイアス、躓きパターン、xAPI/Caliper 出力。**記録された観測レコードを読むだけで、採点を実行しない** | **任意。削除しても採点は動く**（ADR 0007） | 記録=0 / 計算=1 |
| **S10** | Integrity（任意） | 類似度検出、AI 生成疑い、行動ログ。**誤検知の不利益が大きいため「フラグのみ・判定しない」** | 完全に任意 | 8 以降 |
| **S11** | Transcription | 手書き画像の OCR/VLM 書き起こし → **学習者による確認・修正** → 確定。数学の数式・レポートの手書き答案が対象 | 未導入でもテキスト提出のみで全機能が動く | 6 |

> **重要**：S5（採点）・S2（作問）・S7+S8（スキル/ポートフォリオ）が、ユーザーが要求した「3 つの独立サブシステム」に対応する。この 3 つは S1/S3 という薄い共通基盤の上に載り、相互には**イベントのみ**で結合する。

> **Phase 0 に入るのは S1（最小）・S3・S4・S5・S6 と教員レビュー**。S9 は「記録」だけが Phase 0 で、指標の計算は Phase 1（§9.3）。

### 2.3 サブシステム間の結合点（これだけ）

```
S3 → (SubmissionCreated)   → S5
S5 → (GradingCompleted)    → S7, S9      # KC別evidence。S9側の購読が落ちても採点は完了する
S7 → (SkillStateUpdated)   → S8, S2      # S2は「弱いKCを狙った作問」に使う
S2 → (TaskPublished)       → S7          # Q-matrix更新
S8 → (CredentialIssued)    → S9
```

イベントは Outbox パターンで PostgreSQL にコミットし、リレーが Redis Streams へ流す。購読側は冪等。

## 3. コアデータモデル

```
Tenant ─< Course ─< Enrollment >─ User

Task ─< TaskVersion ─┬─< RubricCriterion (weight, level_descriptors)
                     ├─< TestCase / ReferenceSolution
                     ├─< QMatrixEntry >─ KnowledgeComponent
                     └── provenance (authored_by | generated_by, review_state)

Submission ── state: draft | transcribing | awaiting_confirmation | submitted
    ├─< Artifact (code | latex | markdown | pdf | image)
    │      ├── role: original | transcription | attachment
    │      ├── derived_from → Artifact          # transcription は original を指す
    │      └── transcription_meta               # role=transcription のときのみ
    │            ├ engine, model_id, confidence_map (領域別)
    │            ├ learner_edited: bool, edit_diff
    │            └ confirmed_at, confirmed_by
    └─< GradingRun (immutable)
           ├── context: rubric_version, prompt_version, model_id, params, input_hash
           ├─< EvaluatorResult (evaluator_id, kind: deterministic|ai, raw_output)
           ├─< CriterionScore ─< Evidence (artifact_span, rationale)
           ├── aggregate: score, confidence, routing: auto|review_required
           └─< HumanReview (grader, adjusted_scores, comment)  # 追記のみ

SkillState (learner × KC) ── mastery, updated_at, model: bkt|dkt
    └─< SkillEvidence → GradingRun.CriterionScore

Credential ── skill_set, issued_at, evidence_refs, export: internal|ob3
```

設計上のポイント：

- **KnowledgeComponent は科目横断の階層体系**（例：`math.calculus.integration.substitution`）。複数科目で同じ KC を共有できることが、ポートフォリオの価値の源泉。
- **Evidence は必ず Artifact 内の位置を指す**。「なぜこの点数か」を UI 上でハイライト表示できる。
- **HumanReview は GradingRun を上書きしない**。AI と人間の差分がそのまま S9 の一致率データになる（P5）。

## 4. 採点パイプライン（最重要設計）

```
Submission
   │
   ├─ 1. Normalize        科目別 Normalizer（コード整形 / LaTeX 正規化 / PDF→text）
   │                      ★OCR はここに置かない。提出前に学習者が確定させる（§4.2）
   │
   ├─ 2. Deterministic    並列実行・失敗は結果として記録（例外にしない）
   │      ├ TestRunner        コード：テストケース実行（S4）
   │      ├ StaticAnalyzer    コード：lint / 複雑度 / 禁止 API
   │      ├ CasEquivalence    数学：SymPy による数式同値判定（S4）
   │      ├ NumericChecker    物理化学：単位・有効数字・許容誤差
   │      ├ FormalVerifier    証明：Lean4 等（将来）
   │      └ StructureChecker  レポート：必須節・引用形式・字数
   │
   ├─ 3. AI Evaluators    ★ルーブリック観点 1 つ = LLM 呼び出し 1 つ（並列）
   │      入力: 問題文 + ルーブリック観点 + 模範解答 + 学習者解答
   │            + 決定的評価の結果（★これを渡すのが精度の鍵）
   │            + RAG（講義資料・教科書からの根拠検索）
   │      出力: 構造化 JSON（evidence / judgement / level / rationale）
   │      複数モデル or self-consistency で n 回 → 分散を confidence に使う
   │
   ├─ 4. Aggregate        重み付き集約。決定的評価が「不正解」を確定した観点は AI で覆さない
   │
   ├─ 5. Route            confidence 低 / 評価器間不一致 / 合否境界 / 高配点 → review_required
   │
   ├─ 6. Feedback         日本語の形成的フィードバック生成（点数説明ではなく次の一手）
   │
   └─ 7. Publish          GradingCompleted イベント（KC 別 evidence つき）
```

**採点は締切を知らない**（ADR 0013）。上の 1〜7 のどこにも遅延は入らない。
遅れたことは観点の段階ではなく、**評価が終わったあとに評価の外から当てる
減点**として持つ（規則は `Course.late_penalty_steps`、記録は
`GradingRun.penalty`、学習者に出す最終点は `aijudge_core.final_score()`）。
混ぜると、観点の κ が「読解」と「事務」の混合を測り、教員が減点を免除すると
「AI の判定に反対した」という記録になり、S7 の習熟度に遅延が混ざる。

**科目ごとの構成は「どの Evaluator を有効にするか」の宣言だけ**で表現する：

```yaml
# subjects/math_calculus.yaml
input: {allow_handwriting: true, transcription: math_vlm}   # §4.2
normalizers: [latex_normalize]
deterministic: [cas_equivalence, numeric_checker]
ai_evaluators: [rubric_criterion_judge, step_by_step_judge]
aggregation: weighted_sum
review_policy: {confidence_below: 0.75, always_review_if_weight_over: 0.4}
```

これが P1 の具体的な形。**Phase 3 でこの YAML 追加だけでレポート課題に横展開できるかが、アーキテクチャ検証の本丸**（§9.2）。数学は Phase 5 で、CAS 実行基盤を AI 作問（Phase 4）と共有する。

### 4.2 手書き画像提出と OCR 確認フロー（S11／Phase 6）

数学の記述解答やレポートは、紙に手書きしたものを撮影して提出できるようにする。ただし **OCR の誤読をそのまま採点に流さない**。書き起こし結果を学習者が確認・修正して確定させ、確定テキストを提出物とする。

```
学習者が画像をアップロード（複数枚可）
   ↓  Submission.state = transcribing
S11: VLM による書き起こし（S6 経由・ローカル VLM。数式は LaTeX、文章は Markdown）
   ↓  領域ごとの confidence を付与
   ↓  Submission.state = awaiting_confirmation
★ 確認・修正 UI（原本画像と書き起こしを左右に並べる）
   ├ 低 confidence 箇所をハイライトして注意を促す
   ├ 数式は MathLive で直接編集（LaTeX ソースの手打ちを強要しない）
   ├ 図・グラフは書き起こさず画像領域のまま残す（role=attachment として切り出し）
   └ 学習者が「この内容で提出する」を明示的に押す
   ↓  Submission.state = submitted / confirmed_at 記録
採点パイプラインへ（§4）
```

設計上の判断：

- **採点対象は確定 transcription**。原本画像は必ず保管し、AI 評価器には図・グラフの解釈のために原本も参照させる（数式の読み取りは確定テキストを正とする）。
- **確定させた時点で内容の責任は学習者に移る**。これにより「OCR が間違えたせいで減点された」という異議申し立ての構造的リスクが消える。この一点のためにフローを分ける価値がある。
- **`learner_edited` と `edit_diff` を記録する**。修正箇所の集積がそのまま OCR 精度の実測データになり、モデル選定・改善に使える（教員修正データと同じ扱い）。
- **締切との関係を明示する**。締切は `confirmed_at` で判定する。書き起こし待ちで締切を跨がないよう、締切直前は残り時間を UI で警告し、猶予時間を科目設定で持たせる。
- **S11 が落ちてもシステムは動く**。手書き提出が使えなくなるだけで、テキスト直接入力の経路は常に残す（P2）。

**Phase 6（初期運用の必須外）**。実装は Phase 5 で数学の採点が成立してから着手する（§9.2）。手書きの主対象は数式であり、数式の採点が成立していない段階で書き起こし精度を測っても意味がない。ただし `Artifact.role` / `derived_from` / `Submission.state` は**コアデータモデルに最初から入れておく**（後から提出フローに状態を追加するのは破壊的変更になるため）。

## 5. AI 作問（S2）

```
Blueprint（KC + 難度 + 問題形式 + 制約）
   ↓ 生成
Task ドラフト（問題文・模範解答・ルーブリック・テストケース／検証コードを同時生成）
   ↓ 自動検証 ★ここが品質の要
   ├ 解の一意性：CAS / テスト実行で模範解答を実際に検証する
   ├ 解答可能性：別モデルに解かせて模範解答と一致するか
   ├ 難度推定：既存 Task との類似度 + 過去の正答率モデル
   └ 重複検出：既存問題との類似度（**pgvector は索引であって能力ではない** ── 下記）
   ↓ 教員レビュー（承認 / 修正 / 却下 ★却下理由を記録して改善に使う）
   ↓
公開（provenance に generated_by と review_state を必ず残す）
```

生成問題は**手動作成の Task と完全に同じスキーマ**に載せる。採点側は生成物かどうかを知らない（P1/P2）。

Blueprint は S7 の `SkillStateUpdated` を購読して「クラスの弱い KC」を自動で埋められるが、**その経路がなくても S2 は単独で動く**。

## 6. スキル・ポートフォリオ（S7/S8）

- **習熟度推定は BKT から始める**（pyBKT、パラメータ 4 つ、解釈可能で教員に説明できる）。`SkillEstimator` インターフェースの背後に置き、DKT/AKT への差し替えを可能にしておく。データが貯まる前に深層モデルを入れない。
- **ポートフォリオは evidence-based**。「積分の置換に習熟」ではなく「積分の置換：習熟度 0.82、根拠となる提出 5 件（うち教員確認済み 2 件）」を出す。
- **Credential 発行は 2 段構え**。内部バッジを先に作り、Open Badges 3.0 / VC は `CredentialExporter` アダプタとして後から追加する（鍵管理・DID・失効の複雑さを初期に持ち込まない）。
- 学習者が**自分のポートフォリオを部分公開できる**こと（公開範囲の粒度＝KC 単位）。就活・大学院進学での利用を想定。

## 7. 技術選定

| 領域 | 選定 | 理由 |
|------|------|------|
| API | Python 3.12 / FastAPI | 採点・ML 系ライブラリ（SymPy, pyBKT, transformers）と同一言語で書ける |
| DB | PostgreSQL 16 + pgvector | RDB とベクトル検索を 1 台で。テナントは schema 分離から開始 |
| ジョブ | Celery（Redis broker）または RQ | 採点ワーカーを GPU ノードに寄せるためキューを分ける |
| イベント | PostgreSQL Outbox → Redis Streams | Kafka は規模が見えるまで導入しない |
| オブジェクト | MinIO（S3 互換） | Artifact・生成物・実行ログ。オンプレ完結 |
| サンドボックス | gVisor（+ seccomp / netns 遮断 / cgroup 制限） | 実績と運用容易性。Judge0 は**参照するが依存しない** |
| LLM 実行 | vLLM（ローカル、OpenAI 互換 API） | ゲートウェイの下に置く。モデルは 30B〜70B クラス |
| LLM Gateway | 自前薄実装（OpenAI 互換で抽象） | ポリシールーティング・prompt versioning・評価ハーネスは既製品では足りない |
| UI | Next.js (App Router) + TypeScript | 学習者/教員/公開ポートフォリオを 1 コードベースで |
| 数式 UI | MathLive + KaTeX | LaTeX 入力と描画。OCR 確認画面の修正エディタも兼ねる |
| 手書き OCR | ローカル VLM（S6 経由）+ 数式特化モデルの併用 | 個人情報を含む答案を外部送信しない。専用 OCR エンジンは差し替え可能に |
| 認証 | Keycloak | OIDC/SAML/学認、LTI 1.3 も前段アダプタで受けられる |
| 監視 | OpenTelemetry + Prometheus + Grafana + Loki | 採点レイテンシと LLM コストを最初から可視化 |
| 基盤 | Docker Compose（Phase 0）→ K3s（Phase 8） | 早期に K8s を入れない |

## 9. 構築フェーズ

**Phase 0 は「これが無いと授業で使えないもの」だけ**にする。それ以外は
Phase 1 以降に分離する（ADR 0007）。各フェーズはアーキテクチャ上の仮説を
検証する単位も兼ねる。

### 9.1 Phase 0 — 初期運用に必須（ここまでで授業運用を開始する）

- **検証する仮説**：科目非依存コア（Task/Submission/GradingRun）の上で、
  プログラミング課題の提出・隔離実行・AI 採点・教員確定・返却が一巡する。
- **範囲**

  | 領域 | 内容 |
  |------|------|
  | S1 Identity | 学生が触る最小限の認証。SSO・LTI は入れない |
  | S3 Submission | 提出受付、Artifact 保管、採点ジョブの投入・冪等・リトライ・再採点 |
  | S4 Sandbox | 隔離実行。**実提出はコンテナで動かす**（seatbelt 単体は fork bomb を封じ込められない。macOS でも colima 等で同じ水準に揃う、ADR 0006） |
  | S5 Grading | 採点エンジン、科目プロファイル、`code_test_runner`（決定的評価） |
  | S6 LLM Gateway | ローカル LLM 経由の `rubric_ai_judge`（AI 評価）。停止時は決定的評価のみで劣化動作（P2） |
  | レビュー | 教員レビューコンソール。**教員が最終権限を持つ**（P5） |
  | フィードバック | 点数の説明ではなく「次の一手」。学習者に返す価値の本体 |
  | 劣化動作 | S6 停止時は決定的評価の結果を返すが、**全体の仮評価は保留する**。残った観点だけを比例配分した合計は、欠けを知らない学習者に到達度として読まれる（P2） |
  | 記録 | 観測レコードの書き出し（§9.3）。**指標の計算は含まない** |
  | 異議申立 | AI の判定を即時に示し、学習者が再確認を依頼できる。依頼と教員の確定の双方に**根拠説明を必須**にする（ADR 0009） |
  | 成績の確定 | 依頼が出なかった提出を閉じる導線。**締切で仮確定し、確定時刻を学習者に示した上で n 時間後に確定**（n はコースごとに教員が設定）。課題単位の一括確定も持つ。**確定は「教員が読んだ」記録とは別に持つ**（ADR 0010） |
  | 永続化 | PostgreSQL＋オブジェクトストレージ。ファイル置きから移す |
  | UI | 学生向け最小 Web UI（提出・結果表示） |

- **合格基準**（運用が成立するかだけを見る。採点精度の基準は課さない）
  - 1 科目 1 クラス（〜50 名）で 1 課題を通し運用する。ドライランではなく本番運用（成績反映は教員の確認後）
  - 提出から決定的評価の結果表示まで p95 < 30 秒。AI 評価は非同期で「あとから届く」。
    **実装済み**（ADR 0011）。キューを段階で分け、決定的専用ワーカー 1 本で
    p95 0.8 秒（exam08 の実測 496 件 / 2 時間の一様到着）。分ける前は 1 本で
    p95 1689 秒で、4 本立てて初めて基準を満たしていた
  - Sharif Judge の基本機能（課題・提出・ジャッジ・一覧）を欠かない
  - 隔離なしで採点が成立してしまう経路が無いこと（ADR 0006）
  - S6 を停止させた状態で E2E が通る（決定的評価のみで完結する）
  - 教員が AI の判定を覆せること、その修正が追記として残ること（P8）
  - 学習者が結果に異議を申し立てられること。**教員の待ち行列は依頼が出たものだけ**
    （全提出を並べると受講 91 名 × 課題数になり、何から見ればよいか分からない）
  - 学期末に成績が閉じること。依頼が出なかった提出も確定でき、かつ
    **誰も読んでいない提出に「教員が同意した」という記録が残らない**こと
    （残ると、そこから測る一致度が実力より高く出る。ADR 0005 / ADR 0010）

### 9.2 Phase 1 以降 — 初期運用の必須ではないもの

#### Phase 1: 採点性能の測定

- **内容**：S9 の指標計算（κ / QWK / 一貫性）とゲート判定。Phase 0 で貯めた観測レコードを読む。
- **合格基準**：一致度 **Cohen's κ ≥ 0.65**（観点単位）、見逃し ≤ 5%、レビュー行き ≤ 30%、
  反復採点の標準偏差 ≤ 満点の 5%、ローカル LLM がクラウド比 90% 以上の一致度、
  教員の 1 課題あたり採点時間が従来比 50% 以下。
- 採点運用はこれに依存しない（§9.3）。

#### Phase 2: 複数科目での運用

- **対象科目**（移行元が実在する 2 科目）

  | 科目 | プロファイル | 言語 | 自動採点できる課題 |
  |---|---|---|---|
  | プログラミング及び実習 2 | `cs_intro_c` | C | ex02–ex14・各 exam（約 130 件） |
  | ネットワーク及び演習 | `net_python` | Python | ex1–ex3・test2–test8（24 件） |

- **検証する仮説**：科目を増やす作業が**運用者の手で完結する**（コード変更を伴わない）。
  1 科目で成立した運用が、複数コース・複数教員でも崩れない。
- **内容**
  - 複数の科目プロファイルを同一インスタンスで同時運用する
  - コース・受講の管理と教員ロール（S1 の拡張。機関をまたぐ話は Phase 8）
  - 複数教員での採点分担（採点者の識別、担当割り当て、blind 抽出の分配）
  - 科目・課題の管理 UI（YAML の直接編集を運用の前提にしない）。**実装済み。**
    教員コンソールの `/manage` に、コース・課題・締切・受講の管理を載せた。
    **科目プロファイルは表示だけで編集させない** ── 評価器の指名と
    タイムアウトを持つ採点の設定で、ブラウザから壊せるようにすると 1 人の操作で
    全員の採点が止まる。コードと同じ扱いでレビューを通す（ADR 0002）。
    権限は 2 段で、コースの作成は ADMIN、課題と受講の管理はそのコースの
    INSTRUCTOR 以上（**TA には開けない**。締切と受講の変更は成績に直接効き、
    採点の分担とは別の権限）
  - 締切集中時のキュー挙動の実測（1 科目では出ない負荷）
- **合格基準**
  - 2 科目以上 × 複数教員で同一学期を通し運用する
  - 科目の追加がコード変更なしで完了する（ADR 0002 の運用面の検証）
  - コース間でデータが混ざらないことを自動テストで保証する
  - 締切直前の提出集中でキューが滞留しない（p95 の目標を科目ごとに置く）

- **実測**（2026-08-28、colima 上のコンテナ隔離、受講 91 名 × 1 課題 × テスト 5 件）

  | ワーカー | 所要 | 秒/件 | 二重採点 |
  |---:|---:|---:|---|
  | 1 | 53.0 秒 | 0.58 | なし |
  | 2 | 34.8 秒 | 0.38 | なし |
  | 4 | **25.2 秒** | 0.28 | なし |

  提出の受付は 209 件/秒（採点とは別プロセスなので締切直前も詰まらない）。

  **91 名の同時提出で §9.1 の「p95 < 30 秒」を満たすには 4 ワーカーが要る。**
  そして複数ワーカーには**行ロックが要る＝ PostgreSQL が要る**（SQLite には
  行ロックが無く、`Database.supports_row_locking` が偽を返して CLI が警告する）。
  同時実行で同じジョブが二度配られないことは PostgreSQL でのみ検証できるので、
  そのテストは PostgreSQL があるときだけ走る。

  スケールは線形でない（1 → 4 ワーカーで 2.1 倍）。ボトルネックは DB ではなく
  **実行 1 回ごとのコンテナ起動**で、1 提出につき 6 回（コンパイル 1 + ケース 5）
  起動している。1 提出 = 1 コンテナに束ねれば縮むが、Phase 2 の基準は
  満たしているので最適化は先に送る。
- **同じ科目種（プログラミング）のまま複数運用に耐えるかを先に確かめる。**
  新しい科目種の追加（レポート・数学）は Phase 3 以降で、そこと混ぜない。
  混ぜると、失敗したときに「運用の問題」か「アーキテクチャの問題」かが切り分けられない。
- **言語が違うのは科目種の違いではない。** 2 科目は C と Python で、扱う言語が
  違う。これは評価器の設定（`evaluator_options.code_test_runner.language`）で
  表現され、コアと採点エンジンは変わらない。実測で **0 行**だった。
- ネットワーク演習のクライアント／サーバ課題は**伴走プロセスで採点する**
  （ADR 0008、実装済み）。伴走プロセスは**教材から取り込む**（既に存在し、
  課題文が名指ししている相手なので、生成すると課題文と採点基準がずれる）。
  大学ネットワーク上の実サーバに到達させる案は採らない。

  同一コンテナ内の 2 プロセスにし、`--network=none` のまま loopback で
  通信させる。**S4 の変更は 0 行**で、隔離を課題の都合で緩めていない。
  **Sharif Judge で採点できなかったサーバ課題が採点できる。**
- **採点の経路に LLM を入れない。** 伴走プロセスは決定的評価器の参照実装で、
  そこに AI を置くと P3 に反し、全員が落ちる失敗を作れる。LLM の出番は
  「散文の要件 → テストケース」の翻訳で、Phase 4 に置き門を 2 つ課す（ADR 0008）。
- **自己採点課題（12 件）は保留。** 他問題の採点結果を入力に要するため、
  成績集約が入る Phase 5 で繋ぐ（ADR 0008）。

#### Phase 3: レポート課題の採点 ★アーキテクチャ検証の本丸

- **検証する仮説**：新しい科目種の追加が「Evaluator プラグイン + 科目 YAML」だけで済み、
  コアに変更が入らない。**最初に評価方法がまったく違う科目を通すのがここ。**
- **内容**：構造チェック（必須節・引用形式・字数）、AES/ASAG、RAG による事実性照合。
- **合格基準**
  - `packages/core` と `packages/grading` への変更行数が **50 行未満**
    （超えたら P1 が破綻している → 設計見直し）
  - 教員採点との一致度 **QWK ≥ 0.60**
  - 科目追加の実作業が 2 人週以内
- レポートを数学より先に置くのは、**コアの追加を要求しないから**。数学は数式入力・
  CAS 実行・途中式という新しい入力形式と実行手段を持ち込むので、P1 の検証と
  数学固有の実装が混ざる。まずコアが動かないことを確かめる。

- **以下の測定値には共通の限定がある（2026-08-29 追記）。**

  **段階の記述（descriptor）は採点表に無く、こちらが観点名から推測して書いたもの
  である。** 教員のルーブリック文書は残っていない。しかも 2026-08-29 の `c68706c`
  までは**課題文（Notion の実物）すら参照していなかった**ので、モデルには実際とは
  違う課題を採点させていた。したがって以下が測っているのは
  「教員のルーブリックに対する精度」ではなく
  **「こちらが書いた記述に対する精度」**である。**絶対値を基準の判定に使わないこと。**

  **方法論の知見（照合先を LLM にすると順位が反転する・観点ごとに一致度が桁違い・
  順位と尺度を分けて見る）は記述の良し悪しに依らないので、そのまま残る。**

- **判定はここで打ち切り、実運用に移す（2026-08-29、ADR 0012）。**

  **1 つめの基準（コア差分 50 行未満）は満たした。** レポート科目を足すのに
  変えたのは `subjects/report_ja.yaml` とプラグイン 3 つだけで、`packages/core`
  と `packages/grading` の差分は **0 行**。`import-linter` の 15 契約も無傷。
  **Phase 3 の本丸（新しい科目種が YAML とプラグインだけで足せる）は成立している。**

  **2 つめ（教員採点との QWK ≥ 0.60）は、ハーネスの中では判定できない。**
  標本が 19 件 / 28 件で `min_sample_size: 30` に届かず、どちらも形式的に
  `NOT_MEASURED` である。そのうえ**記述を変えるだけで合計 QWK が 0.234〜0.599
  の幅で動く** ── モデルの違いより記述の違いの方が大きい。記述を書き直しては
  測り直す作業に収束先が無い。

  したがって**判定の場所を実運用の `BlindMark`（教員が AI を見ずに付けた段階、
  ADR 0005）に移す。** 基準値は動かさない。`evals/gates.yaml` も書き換えない。
  **モデル選択も同じ場所で行う** ── ハーネスの数字では、どのモデルが良いかが
  照合先の年度で反転するため。運用の開始はこの判定を待たない（ADR 0007）。
  レポート採点には即時性の要求が無く、AI の判定は提案でしかない（P5）。

  **測定用ハーネスのコードは本番に入れない。** 知見は科目プロファイルと
  評価器に**書き写して**移し、コードは移さない。ハーネスは教員の採点表を読み、
  氏名と学籍番号を含むデータを前提に書いてあるので、本番から参照できる位置に
  置くと ADR 0007 と P7 の両方が壊れる。`import-linter` では守れない
  （配布物件ではなくモジュール名を持たない）ので、
  `tests/test_evals_stay_out_of_production.py` が本文を読んで検査する。

- **転移テストの結果**（2026-08-29、2025 年度の採点例から起こしたルーブリックを
  2023 年度の提出に当て、同年度の**教員本人**の採点と照合。n = 27、
  `evals/report_ja/transfer.py`）

  **尺度が違う（23 点 対 50 段階）ので生の QWK は比べない。** 順位が転移の本体で、
  QWK は 1 次式で人の尺度に写したあと（1 件抜き交差検証）の値である。

  | ルーブリック | ρ（順位） | r | 較正後 QWK |
  |---|--:|--:|--:|
  | `rubric_2025c` | +0.609 | +0.482 | +0.277 |
  | `rubric_2025d` | +0.587 | +0.510 | +0.312 |

  **年度を越えても順位は半分ほど移る（ρ ≈ 0.6）が、目盛りを合わせても 0.31 止まり。**
  採点者自身の言葉から段階を起こしても、別の年度・別の課題には届かない。

- **体裁を決定的評価に移した**（2026-08-29、`rubric_2025d`）。教員の採点表の
  備考が `遅延14h` と `ファイル名` だけで、**体裁は文章の質ではなく事務的な
  遵守の記録**だった。2023 年度 28 件で完全一致は、本文を読む
  `report_structure` が **42.9%**、提出そのものだけを見る新設の
  `submission_compliance` が **71.4%**。前者は教員が満点を付けたレポートを
  「節が無い」で減点していた。2025 年度の合計でも QWK 0.331 → **0.397**、
  平均絶対差 4.42 → **3.42 点**と改善する。

  `report_structure` は捨てない。あれが判定しているのは**採点に足るか（受理）**
  であって観点ではない。受理という概念をパイプラインがまだ持たないので、
  いまは採点の経路から外してある。

  **71.4% の内訳は「28 件中 20 件が体裁で満点」である。** 規則の中身ではなく
  **満点を既定にしたこと**が効いている。残る 8 件（半分が 6 件・最低が 2 件）は
  教員の付けた事務的な減点で、備考は `遅延14h` と `ファイル名` だった。

  **遅延は評価器に入れない**（ADR 0013、実装済み）。評価器も採点エンジンも
  締切を見ない。遅延は評価が終わったあとに、評価の外から当てる減点として持つ
  （規則は `Course.late_penalty_steps`、記録は `GradingRun.penalty`、

    採点者が見ている体裁（図表の作り・ページ番号・見栄え）を代理していない。
  - **弱いレポートを甘く見る。** CSV が 7〜11 点を付けた 4 件がすべて 15 点に
    なった。最大の誤差源で、しかも危険な向き（弱いレポートが及第に見える）。
    Phase 1 の「見逃し ≤ 5%」はここに効く。

#### Phase 4: AI 作問と KC 体系

- **検証する仮説**：Q-matrix を結節点にすれば作問・採点・スキル推定が疎結合のまま連携する。
  自動検証を通した生成問題が教員レビューを実用率で通過する。
- **内容**：S2（作問＋自動検証）、S7（KC 体系・Q-matrix・BKT）。
- **合格基準**：生成問題の教員承認率 ≥ 60%（無修正 or 軽微修正）。
  解の一意性検証で不正な問題を 95% 以上除去。BKT の習熟度が次課題の正誤を AUC ≥ 0.70 で予測。

- **骨格は一巡した**（2026-08-29）。作問 → 自動検証 → 教員レビュー → Q-matrix →
  習熟度が、`aijudge-admin task draft` / `task review` から通しで動く。
  **合格基準はどれもまだ判定できない**（後述）。

  ```
  Blueprint（人が KC を書く）
    → 下書き（問題文・参照解答・テストケースを 1 回で生成）
    → 門 1: 参照解答が全テストケースを通る
    → 門 2: 変異させた参照解答が落ちる
    → 解答可能性: 別モデルが課題文だけから解けるか
    → 教員レビュー（承認 / 却下＋理由）
    → 承認された版だけが出題される
  ```

  **仮説（Q-matrix を結節点にすれば疎結合のまま連携する）は成立している。**
  `aijudge_skill` は採点エンジンも保存先も import しない（`import-linter` の
  16 本目の契約）。採点は S7 を知らず、繋ぐのは app 層の購読者 1 モジュールだけ。

- **門 2 が本質である**（ADR 0008）。門 1 だけなら、何を渡しても通る
  テストケースが満点で通る。参照解答を機械的に壊し、壊れたものが実際に
  落ちることまで確かめて初めて、テストケースが何かを見ていると言える。

  **走らせて初めて出た欠陥が 3 つある。** どれも門 2 を**甘くする**向きだった。

  1. `#include <stdio.h>` の `<` を比較演算子として反転していた。必ず
     コンパイルが落ちるので「殺した」に見え、弱いテストでも門 2 を通る
  2. コンパイルできない変異を分母に入れていた。同じく甘くなる
  3. 等価変異（`return 0;` の削除は C99 以降どんなテストでも殺せない）で
     **まともな課題が落ちた**（6 件中 2 件が等価変異で 67%、閾値 80%）

  等価変異は一般に除去できないので、**閾値を 1.0 にしない。**

- **解答可能性は判断材料であって判定ではない。** 解けなかった原因が
  「課題文が曖昧」なのか「単に難しい」なのかを機械は分けられない。
  **自動で捨てると、難しい良問から先に消える**ので、教員に示して判断は人が持つ（P5）。
  参照解答はプロンプトに入れず、参照解答と突き合わせもしない
  （正しいプログラムは何通りもある）── 見るのは振る舞いで、門 1 と同じ経路を通す。

- **生成された課題の KC は人が決める。** `TaskDraft` に KC の欄が無く、
  `draft_to_spec` は `Blueprint` から読む。Q-matrix は S7 の習熟度が全面的に
  依存する対応表なので、生成の揺れを流し込まない。

  **ただし「宣言した KC をその課題が実際に問うているか」は誰も検証していない。**
  門も解答可能性も見ているのは振る舞いだけである。放置すると学習者に
  「問われていない KC の習熟度」が付き、BKT は観測列を畳むので遡って直せない。
  いま間に立つのは 2 つで、**どちらも自動判定ではない** ──
  レビュー画面が KC を必ず表示して「機械は検証していない」と明記すること、
  解答役が「実際に要った KC」を候補から選んで申告すること。

- **二段階キューが 1 提出につきイベントを 2 回出す**（ADR 0011 の帰結）。
  S7 を実配線して初めて出た。1 回目は AI 観点が未採点の暫定で、両方数えると
  同じ提出を二度、しかも一度目は不完全な評価で数える。イベントに
  `provisional` を足して暫定を飛ばす。

- **合格基準はまだ 1 つも判定できない。** Phase 3 と同じ構図で、
  **測れていないことは合格ではない**（ADR 0005）。

  | 基準 | 状態 | 要るもの |
  |---|---|---|
  | 教員承認率 ≥ 60% | `NOT_MEASURED` | 生成物 30 件の承認・却下。実装済みの `task review rate` が数える |
  | 不正な問題を 95% 以上除去 | 未測定 | 意図的に壊した課題の集合。門が落とす割合を測る対象がまだ無い |
  | BKT が AUC ≥ 0.70 | 未測定 | KC ごとに数十件の観測。**パラメータも文献の既定値のまま**で、実データで当てていない |

  承認率は**採点のゲートとは別に報告する**（`evals/gates.yaml` に混ぜない）──
  混ぜると、どちらが不合格なのか読めなくなる。

- **自動検証の 4 つが揃った**（2026-08-29）。設計方針 §5 が挙げた
  解の一意性・解答可能性・重複検出・難度推定が、作問の流れの中で走る。
  レビューは `/manage` の画面と CLI の両方から。

  **どれも判定ではなく材料である。** 門を通っていても課題文が妥当とは限らず、
  通っていなくても欠陥とは限らない。解けなくても、似ていても、捨てるのは教員
  （P5）── 自動で捨てると、難しい良問と同じ単元の正当な課題から先に消える。

- **重複検出は 2 つの尺度を持つ。** 埋め込み（コサイン）は言い換えを捉え、
  文字 3-gram は写しを捉える。**どちらで測ったかを必ず結果に残す** ──
  字面だけで「見つからなかった」ことは安全の証拠ではない。埋め込みを持たない
  プロバイダは Gateway がはっきり断り、重複検出はそれを捉えて字面に落とす
  （黙って「重複なし」にしない）。

  **pgvector は使っていない。索引であって能力ではない。** 1 コースの課題は
  数十〜数百件で、その規模では全件とのコサインの方が速く、SQLite でも動く
  （テストが走る環境がそこである）。索引が要るのは課題が万を超えてからで、
  そのときは保存側の列型だけを替える ── 比較そのものは
  `packages/authoring/similarity.py` にあり、保存先を知らない。

  **埋め込みも P7 のポリシーを通す。** 埋め込みからは元の文が部分的に復元
  できるので、生成と同じ扱いにする。モデルを跨いでベクトルを混ぜない
  （次元が同じでも意味空間が違い、無関係な課題が似ていることになる）。

- **難度推定は答えないことの方が多い。** 似た課題の正答率を類似度で重み付け
  するが、提出 15 件未満の課題は率として扱わず、実績のある近傍が 2 件に
  満たなければ推定しない（1 件に賭けると、その課題の癖がそのまま予測になる）。
  **どの経路も `NOT_MEASURED` と理由を返す** ── 数字を出さないことと、
  当てにならない数字を出すことは、教員にとって意味が違う。

  **測っているのは正答率であって難しさではない。** 出題時期・任意か必須か・
  その年の受講者でも動く。文面に毎回添える。

  正答率は **superseded されていない採点**から数える。両方数えると、
  二段階キューが 1 提出につき採点を 2 つ作るので提出数が倍になる
  （S7 で踏んだのと同じ罠、ADR 0011 の帰結）。

- **未実装**：生成の自動評価（門が「不正な問題を 95% 以上除去」できるかを
  測る対象集合がまだ無い）。

#### Phase 5: 数学課題の採点

- **検証する仮説**：CAS で決定的に判定できる部分と LLM に任せる部分の切り分けが、
  数学でも実用水準で成立する。
- **内容**：CAS による数式同値判定、数値の許容誤差・有効数字、LaTeX 入力（MathLive）、
  途中式の論理評価。
- **合格基準**
  - `packages/core` と `packages/grading` への変更行数が **50 行未満**（Phase 3 と同じ基準）
  - 教員採点との一致度 **κ ≥ 0.60**
  - **CAS が判定できた設問では誤りゼロ**（ここを LLM に譲らない）
- **Phase 4 の後に置く。** 解の一意性検証（Phase 4）は CAS で行うので、数学の
  同値判定と同じ実行基盤を共有する。作問側で CAS を通してから採点側に持ち込む方が、
  同じものを二度作らずに済む。KC 体系も数学で最初に効く（単元の依存関係が明確なため）。

#### Phase 6: 手書き画像提出

- **内容**：S11（VLM 書き起こし）、確認・修正 UI（MathLive 連携）、`Submission.state` の遷移。
- **合格基準**
  - 書き起こし後の学習者修正率（文字単位）≤ 10%、修正に要する時間の中央値 ≤ 3 分/枚
  - 確定 transcription での採点精度が、テキスト直接入力と比べて κ の低下 ≤ 0.05
  - 低 confidence ハイライトの再現率 ≥ 80%
  - 確認せずに提出できてしまう抜け道がないこと（状態遷移テスト）
- **Phase 5 の数学が合格していない限り着手しない。** 手書きの主対象は数式であり、
  数式の採点が成立していない段階で書き起こし精度を測っても意味がない。

#### Phase 7: ポートフォリオと外部発行

- **内容**：S8、公開ポートフォリオ、内部バッジ、`CredentialExporter` として Open Badges 3.0 発行。
- **合格基準**：複数科目・複数学期のデータから KC 別ポートフォリオが自動生成される。
  学習者が公開範囲を制御できる。発行したバッジが外部ウォレットで検証できる。

#### Phase 8: マルチテナント・外部連携・スケール

- **内容**：S1 のマルチテナント化（機関単位）、Keycloak 経由の SSO（学認/SAML）、
  LTI 1.3 アダプタ、K3s 移行。
- **合格基準**：2 機関 × 複数科目の同時運用。締切直前を想定した**同時提出 500 件のバースト**で
  採点キューが 10 分以内に捌ける。テナント間のデータ分離を自動テストで保証。

#### 順序の制約

```
Phase 0 ─┬─ Phase 1 (測定)
         ├─ Phase 2 (複数科目での運用)        ← 1 とは独立。どちらを先にしてもよい
         └─ Phase 3 (レポート) ★ ─ Phase 4 (AI 作問) ─ Phase 5 (数学) ─ Phase 6 (手書き)
                                        └─ Phase 7 (ポートフォリオ)
                                                    Phase 8 (マルチテナント)
```

- **Phase 1 と Phase 2 は互いに独立**。測定は Phase 2 を待たず、Phase 2 は測定の合格を待たない。
- **Phase 3 は Phase 1・2 と独立に着手できる**が、本番投入は Phase 2（複数科目の運用）が
  整ってからが自然。
- **Phase 4 は Phase 3 の一致度の合格を待たない**（2026-08-29、ADR 0012）。Phase 3 が
  Phase 4 に渡すのはアーキテクチャの検証結果（新しい科目種が YAML とプラグインだけで
  足せる）であって、レポートの採点精度ではない。精度の判定は実運用の `BlindMark` で
  並行して進む。
- **Phase 5 は Phase 4 の完了が前提**（CAS 実行基盤と KC 体系を共有する）。
- **Phase 6 は Phase 5 の合格が前提**。
- **Phase 7 は Phase 4 の完了が前提**（KC 別の集約が要る）。

### 9.3 採点性能の測定は「可能だが必須でない」

**測定は採点の質を知る手段であって、採点の一部ではない。** 分けて扱う（ADR 0007）。

| | フェーズ | 理由 |
|---|---|---|
| **記録** — blind 採点・確定採点・観測レコード | **Phase 0** | 後から再構成できない。AI の判定を見た教員の採点は、遡って blind にできない |
| **計算** — κ / QWK / ゲート判定 | **Phase 1** | 記録が揃っていれば、いつでも後から計算できる |

依存の向きを一方向に固定し、採点側は測定を知らない。

```
採点パイプライン ──→ GradingRun（不変）
                            ↓ 読むだけ
レビュー ──────────→ FinalDecision
                            ↓ 読むだけ（app 層の購読者）
                      Observation（1 提出 × 1 観点）
                            ↓ 読むだけ
                  analytics（κ / QWK / ゲート・純関数）
```

- **`packages/analytics` と `apps/evalrunner` を削除しても採点は動く。**
  これが「必須機能でない」の機械的な定義で、`.importlinter` の契約に書く。
  契約は**両方向**必要（片方向にした結果、採点側が測定の型を import していて
  削除すると起動しなかった。実際に削除して判明した）。
  記録の形式は独立パッケージ `packages/observation`（依存は pydantic のみ）に置き、
  「記録=Phase 0 / 計算=Phase 1」の分割をパッケージ境界に一致させる
- 観測レコードの書き出しが失敗しても採点は続行する（P2 の劣化動作と同じ扱い）
- 測定は再採点しない。記録済みの観測を読むだけ
- **採点は提出時に走る。** レビューは採点の起動条件ではない
- **blind 採点は全件必須ではなく抽出**。抽出率は科目プロファイルに宣言する。
  全件 blind はレビュー 1 件ごとに 2 段階の入力を強制し、測定コストを日常業務に
  転嫁する。教員の任意選択にしないのは、選択バイアスが入ると κ が意味を失うため

### 9.4 各フェーズ共通で必ずやること

1. **ADR（設計判断記録）を残す** — `docs/adr/`。特に「なぜ AI を使わなかったか」の判断。
2. **ゴールデンデータを増やす** — モデル/プロンプト変更時の回帰を CI で検出する。
   日常のレビュー作業から貯まる形にし、測定用に別途集める作業を作らない。
3. **教員修正データを蓄積する** — これが最終的に最大の資産になる（ルーブリック改善・ファインチューニング）。
4. **倫理・法務チェック** — 学習者への AI 採点の明示、異議申し立て導線、個人情報の外部非送信の実証。
   異議申し立て導線は Phase 0 で実装済み（ADR 0009）。AI 採点の明示は結果画面で
   判定の出所（「AI」／「テスト実行」）を区別して見せることで満たしている。

## 10. 主要リスクと対策

| リスク | 対策 |
|--------|------|
| 完全新規のためスコープが膨らむ | Phase 0 を「これが無いと授業で使えないもの」に限る。測定・作問・他科目・手書きは Phase 1 以降に分離する（ADR 0007）。各フェーズの合格基準を満たすまで次に進まない |
| ローカル LLM の精度が足りない | Phase 1 でクラウドとの一致度を測り、差が大きい観点だけをクラウド or 人間に回すハイブリッド運用に切り替えられる設計（S6 のルーティング）にしておく |
| 生成問題・AI 採点への教員の不信 | 全出力に evidence と rationale を付ける（P4）。教員が最終権限を持つ（P5）。κ を常時ダッシュボード表示 |
| 締切前バーストで GPU が詰まる | 決定的評価と AI 評価のキューを分離。AI 評価は非同期で「あとから届く」UX を最初から前提にする |
| KC 体系の設計が全体を止める | 科目ごとに独立した KC 名前空間から始め、横断の統合は Phase 7 まで先送りする |
| AI 生成解答の検出（S10） | 検出を採点に反映しない。フラグと行動ログのみを教員に提示する。誤検知の不利益が大きすぎる |
| OCR 誤読による不当な減点 | 学習者の確定ステップを必須にし（§4.2）、確定前は採点に進めない。原本画像を保管し、教員レビュー画面で常に並べて表示する |
| 確認・修正が学習者の負担になり手書き提出が使われない | 低 confidence 箇所のハイライトと MathLive での直接編集で修正コストを下げる。Phase 6 で修正時間を実測し、基準を満たさなければ機能を出さない |

## 11. 検証方法（動くもので確かめる）

各フェーズの完了判定は、以下を実際に走らせて行う。

1. **エンドツーエンド運用テスト**：実際の授業 1 コマで、実学生の提出を通す。ドライランではなく本番運用（成績反映は教員の確認後）。
2. **採点精度の測定（Phase 1）**：記録済みの観測レコードから κ / QWK / 一貫性を計算し、`evals/gates.yaml` の基準と突き合わせる。**判定は 3 値**で、データ不足は `NOT_MEASURED`（CI を落とさないが合格とも言わない、ADR 0005）。**採点運用はこの経路に依存しない**（ADR 0007）。
3. **アーキテクチャ制約の自動検証**：`import-linter` による依存方向チェックと、「新科目追加時の core 差分行数」を PR で計測。
4. **サブシステム独立性の検証**：S6（LLM Gateway）・S7（Skill）・**S9（測定）**をそれぞれ停止させた状態で E2E テストを回し、劣化動作することを確認する。S9 については「`packages/analytics` と `apps/evalrunner` を削除しても採点が動く」ことを契約として検証する。これを CI の定期ジョブに入れる。
5. **負荷試験**：k6 で同時提出バーストをかけ、キュー滞留・p95 レイテンシ・GPU 使用率を計測。
6. **セキュリティ**：サンドボックス脱出試験（ネットワーク到達・ファイルシステム・fork bomb・長時間実行）を評価用の悪意ある提出セットで実施。

## 12. Phase 0 の残作業

コアの契約（`packages/core`）、採点エンジン（S5）、決定的評価器、S6、S4、
教員レビューコンソールは実装済み。Phase 0 を閉じるために残っているのは以下。

**済**（2026-08-28）

- **採点の起動をレビューから切り離した** — 採点は `aijudge-grade` が走らせ、
  コンソールは届いた結果を読むだけ。レビューは採点の前提条件ではない。
- **観測レコードを導入した** — 測定は記録済みの観測を読むだけで採点を呼ばない。
  `import-linter` の契約で、測定側が採点側を import できないことを保証している。
- **blind 採点を抽出のみにした** — 抽出率は科目プロファイルが宣言し、対象は
  提出 ID のハッシュで決める（教員に選ばせると選択バイアスが入る）。

- **S3（Submission & Orchestration）** — 提出受付、Artifact 保管、ジョブ投入、
  冪等、リトライ、リース、再採点。採点ワーカーが S3 と S5 を束ねる。
- **S1（Identity）の最小実装** — ローカル認証、コース、受講、権限。SSO・LTI は Phase 8。
- **学生向け最小 Web UI** — 提出と結果表示。見せる範囲は `visibility.py` に集約。
- **永続化** — PostgreSQL（SQLAlchemy）＋ファイル／MinIO。プロトコルの背後に置いた。
- **フィードバック生成** — 決定的評価の結果だけから「次の一手」を作る。
  確定前の AI 判定を材料にしない（P5）。S6 停止時は要約に落ちる（P2）。
- **コンテナでの脱出試験を実走した**（2026-08-28、colima）。fork bomb の封じ込め、
  非 root 実行、read-only ルート、ホスト家目録の不可視、ネットワーク遮断、
  メモリ・出力の上限をすべて確認。実走して初めて 2 つの欠陥が出た
  （作業域が黙って空になる／シグナル終了が正常終了に見える）— 詳細は ADR 0006。
- **コンテナ隔離での通し実行を確認した**（提出 → 採点 → 結果表示）。所要時間:

  | 提出 | 点 | 振り分け | 所要 |
  |---|---|---|---|
  | 参照解答 | 90.1% | auto | 0.90 秒 |
  | 動作は正しいが読みにくい提出 | 90.1% | auto | 0.61 秒 |
  | コンパイルエラー | 0% | review_required | 0.12 秒 |
  | 無限ループ | 0% | review_required | 10.16 秒 |
  | fork bomb | 0% | review_required | 0.61 秒 |

  §9.1 の「決定的評価の結果表示まで p95 < 30 秒」は満たしている。
  ここでも設定の設計の誤りが 1 つ出た（`timeout_seconds` が LLM の予算と
  テストケースの実行上限を兼ねており、暴走コードに 120 秒 × ケース数の猶予を
  与えていた）— ADR 0002 の帰結に記録。

- **成績を閉じる導線を入れた**（2026-08-28）。**締切で仮確定 → n 時間の異議受付
  → 確定**の 2 段（`aijudge-finalize`、n はコースごとに教員が `/manage` で設定）と、
  課題単位の一括確定。仮確定の段階で「いつ確定するか」を学習者に示すので、
  期限で依頼を締め切れる（示さずに確定させると事後にしか分からない）。**確定（`Finalization`）を「教員が読んだ」記録（`HumanReview`）と
  別に持つ。** 混ぜると、受講 91 名 × 十数課題の大半に「教員が AI に同意した」
  という記録が残り、一致度が実力より高く出る（ADR 0005 が禁じた形）。分けた
  ことで測定側のコードは無変更のまま正しい。自動確定は要レビュー・未採点の
  観点・異議申立中のものを確定させない（設計原則 P5）— ADR 0010。
