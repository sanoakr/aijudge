# 動かす

aiJudge は、次のプロセスに分かれて動く。**採点はレビューより前に、
レビューとは独立に実行する**（ADR 0007）。

```
aijudge-web       学習者：提出と結果表示                    :8080
aijudge-worker    採点：キューを消費                        （常駐・段階ごとに立てる）
aijudge-relay     イベント：outbox を購読者へ流す            （常駐・1 本だけ）
aijudge-review    教員：確認して確定 + 科目・課題の管理      :8765
aijudge-finalize  成績：締切を過ぎた分を自動確定            （cron か常駐）
aijudge-admin     運用：学期の頭の一括操作（CLI）
```

コース・課題・締切・受講の管理は、教員コンソールの `/manage` で行う。
学期の初めの一括操作（90 名の登録、課題の一括取り込み）は `aijudge-admin` で行う。
**新規利用者の作成は CLI だけ**でできるようにしてある（パスワードの配布を伴うので、
画面に平文を表示しないため）。**利用者の無効化も CLI からできる**（#237）。画面
（`/manage/users`）はテナント管理者専用で、サーバにログインできる運用者が
テナント管理者とは限らないためである。

```fish
uv run aijudge-admin user disable --login <id>   # 削除ではない。記録は残る
```

## 開発機（macOS / 単独プロセス）

```fish
docker compose up -d                    # PostgreSQL（提出物はファイルシステム）
set -gx AIJUDGE_DATABASE_URL postgresql+psycopg://aijudge:aijudge@localhost:5432/aijudge

uv sync --extra dev
uv run alembic upgrade head             # スキーマを作る・更新する
uv run aijudge-worker
uv run aijudge-review
```

### スキーマの更新

**運用中の DB は、`alembic upgrade head` で更新する。** `--create-schema`
（`create_all`）は**無いテーブルを作るだけで、既存のテーブルに列を追加しない**
ので、運用を始めたあとは使えない。新しい列がいつまでも作られず、その表を読むすべての
クエリが失敗する（実際に起きた・#24）。

```fish
uv run alembic current                  # いまどの版か
uv run alembic upgrade head             # 未適用の版を順に当てる
uv run alembic history                  # 版の並び
```

模型（`packages/persistence/.../schema.py`）を変えたら、**必ず移行の版を追加する。**

```fish
uv run alembic revision --autogenerate -m "何を変えたか"
```

### 更新したら、プロセスを全部入れ替える

**ワーカーの再起動を忘れないこと。** Python は起動時に模型を読み込むので、Web とレビュー
だけを再起動して古いワーカーを残すと、**新しいコードが書いた採点結果を、古い
ワーカーが読めなくなる**。実際に 2 度起きた。

- `session=0` の問題セット（#60）を古いワーカーが読めず、その回の提出が
  すべて「採点されていません」のまま溜まった
- 点の付いていない採点結果（#80）を古い AI ワーカーが受け付けず、決定的段階だけが
  終わって、AI 段階が失敗し続けた

どちらの場合も、**エラーはワーカーのログにしか出ない**ので、画面からは「採点が遅い」
としか分からない。模型（`packages/core`）を変えた更新では、次のプロセスをすべて再起動する。

```fish
pkill -f 'aijudge-(web|review|worker|finalize)'
# それぞれ起動し直す（下の「開発機」の並び）
```

移行の版を書き忘れると、CI が失敗して知らせる（`packages/persistence/tests/test_migrations.py`
が、移行だけで作ったスキーマとモデルのスキーマを比べる）。

**既にテーブルがある DB を移行の管理下に置く**ときは、DB を作り直さずに
「適用済み」と記録する。

```fish
uv run alembic stamp head
```

`AIJUDGE_DATABASE_URL` を設定しない場合は、上と同じ PostgreSQL の URL を使う。
SQLite でも動くが、**行ロックが無い**ので、ワーカーは 1 プロセスだけにすること
（`Database.supports_row_locking` が偽になり、CLI が警告を出す）。

## ログを読む（ADR 0016）

ログは 3 種類あり、置き場所も保存期間も違う。**新しい記録を追加するときは、まずどのログに書くかを決める。**

| | 何の記録か | 置き場 | 寿命 |
|---|---|---|---|
| 運用ログ | プロセスに何が起きたか | journald（開発機は stderr） | 90 日 |
| 監査ログ | **誰が**成績に関わる何をしたか | DB `audit_events` | 消さない |
| 採点記録 | どの版・どのモデルで採点したか | `GradingRun`（ADR 0003） | 消さない |

開発機の既定は、人が読みやすい形式である。運用では `AIJUDGE_LOG_FORMAT=json` にする。

```fish
AIJUDGE_LOG_FORMAT=json AIJUDGE_LOG_LEVEL=DEBUG uv run aijudge-worker --once
```

**1 つの提出について、web とワーカーの両方のログを集める。** ログを結び付ける鍵は
`submission_id` で、上の #60 / #80 のときに欠けていたのはこの鍵である。

```fish
journalctl -t aijudge-web -t aijudge-worker-det -t aijudge-worker-ai1 -o cat \
  | jq -R 'fromjson? | select(.submission_id == "SUB-ID")'
```

1 つのリクエストの中で起きたことは、`request_id` で絞り込む。応答の `X-Request-ID`
ヘッダに同じ値が入るので、学生から報告された 1 件をそのまま追跡できる。

**ログに書くのは識別子だけである。** 提出物の本文・氏名・LLM のプロンプトと出力は
書かない（P7）。journald はバックアップも暗号化もされていないので、
学習者データを journald に複製した時点で、ゲートウェイが守っている保証（ADR 0004）を迂回してしまう。
`aijudge_telemetry.bind` が値の型と長さを検査して拒否するので、誤って本文を渡すと、
その場で例外になる。

### 監査ログを読む

`audit_events` は DB にある。**運用ログと違って、監査ログは削除しない。** 成績への異議
申し立ては、学期が終わってから届くことがあるためである。DB ダンプに含まれるので、restic のバックアップの対象にもなる。

```fish
# この提出に何が起きたか（新しい順）
psql aijudge -c "select at, action, actor_kind, actor_user_id, summary
                 from audit_events
                 where target_type='submission' and target_id='SUB-ID'
                 order by at desc"

# ログイン失敗を新しい順に（総当たりを見る）
psql aijudge -c "select at, target_id, source_ip, detail->>'reason'
                 from audit_events where action='login.failed' order by at desc limit 50"
```

**`actor_kind` を必ず確かめること。** 値は 3 種類ある。

- `user` … 認証済みの利用者の操作（`actor_user_id` がある）
- `system` … 人の操作者がいない操作。締切経過による自動確定と、`aijudge-admin`
  からの操作が該当する（CLI には認証された主体が無い。誰がコマンドを実行したかは、サーバに
  ログインできる権限の管理で扱う）
- `anonymous` … **認証されていない誰かの試み。** ログイン失敗が該当する。
  `target_id` でアカウントは分かるが、試みたのが本人とは限らない

監査ログには `request_id` が入っているので、運用ログの同じ ID と照合できる。

**監査ログに平文は記録しない。** パスワード、再発行した平文のパスワード、API トークン、提出物の本文は
記録しない。`detail` は変更の前後の値を入れる欄で、上限（4000 文字）を超えると、
保存時に拒否される。

## 実提出を通す前に

**seatbelt だけで、実際の学生のコードを実行してはならない。** seatbelt はプロセス数を
制限できず、実測で開発機のプロセス表が埋まった（ADR 0006）。
`sandbox-exec` が防げるのは書き込み・通信・ホームディレクトリの読み取りまでで、
プロセス数だけは制限できない。

運用を始める前に、コンテナ実行環境を導入する。**macOS でも、同じ水準の隔離にできる。**

```fish
brew install colima docker      # 軽量 VM 上の Linux コンテナ
colima start --cpu 4 --memory 8

AIJUDGE_SANDBOX=docker uv run pytest packages/sandbox/tests/test_container.py -v
```

このテストが **skip ではなく pass** することが、実際の提出を受け付ける前提条件である。
skip は「検証していない」という意味で、「安全」という意味ではない。
2026-08-28 に、colima で 15 件の合格を確認した（gVisor の 1 件だけ skip）。

**同じ試験を gVisor（runsc）でも実行する**（#502）。各試験は `[runc]` と `[runsc]`
の 2 通りで実行され、runsc の無い機械では `[runsc]` が skip になる。運用機のように
gVisor で採点する機械では、`gvisor` を明示的に指定し、skip を失敗として扱わせる。

```fish
AIJUDGE_SANDBOX=gvisor uv run pytest packages/sandbox/tests/test_container.py -k runsc -v
```

CI は runner に gVisor を導入し、この形で毎回実行している。

作業ディレクトリの既定は `~/.aijudge/work` である。**ホストの一時ディレクトリを使わない**のは、
macOS の `/var/folders/...` がコンテナ実行環境にマウントされず、bind mount が
エラーを出さずに空になるためである（ADR 0006）。変更するときは、`AIJUDGE_SANDBOX_WORKDIR` に
マウントされるパスを指定する。サンドボックスの構築時に検証するので、マウントされていなければ
採点は始まらず、`SandboxUnavailable` になる。

バックエンドは、使えるもののうち最も隔離の強いものを自動で選ぶ（gVisor > docker > seatbelt）。
どれが選ばれたかは採点結果の `isolation` に残るので、あとから
「どの水準の隔離で付けた点か」で絞り込める。

```fish
uv run python -c "
from aijudge_sandbox import build_sandbox
s = build_sandbox()
print(s.name, s.isolation.value, sorted(l.value for l in s.limitations))
"
```

## tailnet の他の端末から使う

既定では `127.0.0.1` にだけ bind するので、他の端末からはアクセスできない。
他の端末に公開する方法は 2 つある。

### tailscale serve（推奨）

前段で TLS を終端するので、**正規の証明書で HTTPS になる**。tailnet の中だけに
公開され、LAN には公開されない。

```fish
tailscale serve --bg --https=443 8080     # 学生 UI
tailscale serve --bg --https=8443 8765    # 教員 UI

# → https://<ホスト名>.<tailnet>.ts.net/       学生
# → https://<ホスト名>.<tailnet>.ts.net:8443/  教員

tailscale serve status     # 確認
tailscale serve reset      # 取り消し
```

アプリは `X-Forwarded-Proto: https` を見て、**セッション Cookie に `Secure`
を付ける**ので、追加の設定は要らない。

### Tailscale のアドレスに直接 bind する

```fish
set -l ts (tailscale ip -4)
uv run aijudge-web    --host $ts --port 8080
uv run aijudge-review --host $ts --port 8765
```

平文 HTTP だが、tailnet 内の通信は WireGuard で暗号化される。ただし
**Cookie に `Secure` が付かない**ので、`AIJUDGE_SECURE_COOKIES=1` は
設定しないこと（設定するとブラウザが Cookie を送らずログインできない）。

**`--host 0.0.0.0` は使わないこと。** tailnet だけでなく、同じ LAN 上の
すべての端末に公開されてしまう。

### 学生に配るとき

tailnet は教員・TA の端末をつなぐには十分だが、**学生向けには使えない**
（学生全員に Tailscale を導入させることになる）。実際の運用では、学内ネットワークに
リバースプロキシ（TLS 終端）を置き、`AIJUDGE_SECURE_COOKIES=1` を設定する。

## 1 回のログインで両方に入る（#103）

セッションは**両アプリで同じ表**（`AuthService`）を使う。Cookie の名前も
`aijudge_session` に揃えてあるので、**同じホストで動かしていれば、片方の
アプリにログインするだけで両方を使える。**

役割はコースごとに決まる（同じ人が「A では学習者・B では教員」になることがある）。
一覧の行からもう一方のアプリへのリンクは、**いま開いているホスト名のまま、もう一方の
ポートを**指す（#114）。1 台のサーバが `localhost`・IP・短い名前・FQDN のどれでも
応答するので、利用者が「どの名前でアクセスしたか」は起動時には決まらない。固定した名前へ
リンクすると、その名前でアクセスしていない人の Cookie が送られず、移動した先で
「ログインしてください」と表示されてしまう。

もう一方のポートが既定（8765 / 8080）でない場合は、そのポートだけを指定する。

```fish
set -gx AIJUDGE_CONSOLE_PORT 9765   # 学習者アプリが渡す先のポート
set -gx AIJUDGE_LEARNER_PORT 9080   # コンソールが渡す先のポート
```

**逆プロキシの後ろに置く場合や、実際に別のホストに置く場合は、URL で指定する。**
その場合、正しいホスト名を知っているのは運用者である。

```fish
set -gx AIJUDGE_CONSOLE_URL https://aijudge.example.jp/teach
set -gx AIJUDGE_LEARNER_URL https://aijudge.example.jp
```

**逆プロキシを前に立てるときは `AIJUDGE_ALLOWED_HOSTS` を設定する**（#116）。
`Host` と `X-Forwarded-*` はクライアントが自由に決められる値で、もう一方のアプリへの
リンクはこれらの値から組み立てている。検査せずに受け入れると、外部からの入力を
`X-Forwarded-*` にそのまま渡す設定や共有キャッシュがある場合に、リンク先を
書き換えられてしまう。

```fish
set -gx AIJUDGE_ALLOWED_HOSTS aijudge.example.jp,aijudge.example.jp:8765
```

**ホスト名が違えば、セッションは共有されない**（Cookie はホスト単位で、ポートは
区別しないので、同じホスト名ならポートが違っても共有される）。1 つの入口に
まとめる方法は、#103 の続き（逆プロキシ）で扱う。

## Google ログインを使えるようにする（#124・#125）

aiJudge 側の設定は `/manage/oidc-settings`（テナント管理者だけ）にある。
**その前に、機関の Google Cloud で OAuth クライアントを 1 つ発行しておく。**

### リダイレクト URI は 2 本いる

ここが最も間違えやすい点である。**学習者アプリと教員コンソールは別の入口を
持ち、それぞれが自分の `/auth/callback` へ戻る。**

```
https://<学習者の入口>/auth/callback
https://<コンソールの入口>/auth/callback
```

**コンソールを接頭辞の下に置いている場合、その接頭辞も URI に入る**
（`AIJUDGE_CONSOLE_ROOT_PREFIX=/console` なら
`https://example.jp/console/auth/callback`）。1 台のホストに 2 つのアプリを
まとめた構成では、学習者側だけを登録して、**コンソール側を登録し忘れやすい**。
学習者の画面では問題なくログインできるので、誤りに気づくのは、教員が最初に
ログインしようとしたときになる。

Google は登録した文字列と**完全一致**で判定する。

- `http` は受け付けない（`localhost` を除く）。逆プロキシで TLS を終端して
  いる場合は、アプリが `X-Forwarded-Proto` を受け取れるようにすること。受け取れないと、
  アプリは `http://…/auth/callback` を送り、原因の分かりにくい 400 エラーになる
- 末尾のスラッシュの有無や、ホスト名の違い（`www` の有無・別名）は、すべて別の URI として扱われる

### 症状から原因へ

Google の 400 エラーの画面で**「詳細」を開くと、Google が実際に受け取った値が表示される**。
この値を見ないと、原因を切り分けられない。

| 詳細に出るもの | 原因 |
|---|---|
| `redirect_uri_mismatch`（受け取った URI つき） | その URI が承認済みリストに無い。**コンソール側の登録漏れが最有力** |
| `org_internal` | 同意画面が「内部」になっている。組織外のアカウントは、設定上ログインできない |
| `access_denied` + テストユーザー | 公開ステータスが「テスト」のまま |

### いま何を送っているかを実機で確かめる

推測する前に、サーバが組み立てる URI を実際に確かめる。

```fish
curl -s -o /dev/null -w '%{redirect_url}\n' \
    -H 'Host: <公開しているホスト名>' -H 'X-Forwarded-Proto: https' \
    http://127.0.0.1:8765/auth/login
```

`redirect_uri` の値がそのまま表示される。**この値を、GCP の承認済み URI と 1 文字ずつ
照合する**のが最も速い。学習者側は、`:8080` に対して同じことをする。

### 受け付けるアカウント（#220）

**ログインできるのは、Google Workspace の組織アカウントだけである。** ID トークンの `hd`
（Google が発行する、組織への所属を示すクレーム）が許可ドメインに一致し、かつ
`email_verified` が真であることを要求する。

- `hd` が無いトークンは受け付けない。**`hd` が無いときにメールアドレスのドメインで判定すると、
  「その機関のドメインを名乗っているだけ」のアカウントと区別できない。** 個人の Google
  アカウントでも、確認さえ済ませれば任意のドメインのアドレスを登録できるためである
- **Workspace を使っていない機関のメールドメインは、この方法では受け付け
  られない。** 使える機関を狭める判断であり、そうした機関はローカル認証
  （`aijudge-admin staff`）を使う

### アカウントの選択（#208）

認可リクエストには、必ず `prompt=select_account` を付ける。付けないと Google は
ブラウザに残っているセッションを確認なしに再利用し、**私物のアカウントで
サインイン済みの端末では、機関のアカウントを選べない**。

許可ドメインがちょうど 1 つのテナントでは、`hd` も付ける（選択の候補が
その組織のアカウントに絞られる）。**このときの `hd` はヒントで、検査ではない。** URL を
書き換えれば外せるので、実際の検査は、ID トークンを受け取ったあとのドメイン検査で行う。

### ボタンの文言（#209）

ログイン画面のボタンは `/manage/oidc-settings` で機関ごとに変えられる
（「全学認証アカウントでログイン」など）。空欄なら、機関に依存しない既定の文言を表示する。

## 配色（昼・夜）

配色の切り替え（自動 / 昼 / 夜）は、画面の右下ではなく**フッタの左**にある。
フッタは両アプリの全ページに必ずある唯一の場所で、ヘッダはログイン後にしか
表示されない。ログイン画面でも画面がまぶしいことは同じだからである（#181）。

既定は**自動**（端末の設定に従う）で、以前からの動作をそのまま既定にしている。
選択はブラウザに保存されるので、**端末ごと・アプリごと**に決まる（学習者アプリと
教員コンソールは別オリジンなので、それぞれが別に記憶する）。サーバには保存しない。
サーバに持たせるほど重要な設定ではなく、保存すると DB とバックアップに列が 1 つ増えるためである。

JavaScript を無効にしていると切り替えは表示されず、端末の設定に従う。

## 環境変数

| 変数 | 用途 | 既定 |
|---|---|---|
| `AIJUDGE_DATABASE_URL` | 接続先 | ローカル PostgreSQL |
| `AIJUDGE_ARTIFACT_DIR` | 提出物の置き場所 | `~/.aijudge/artifacts` |
| `AIJUDGE_VIDEO_DIR` | 動画の置き場所（提出物とは**別のディレクトリ**）。**未設定なら動画提出は 501 で断る** ── 設定した人だけが持つ機能である。**web・review・admin が同じ場所を指すこと**（消すのは admin）。**systemd で動かすなら unit の `ReadWritePaths` の中に置くこと**（下記） | 未設定（機能ごと無い） |

## 締切集中に備える

**採点は 2 段階で、段階ごとにキューが分かれている**（ADR 0011）。決定的評価は 0.5 秒、
AI 評価は 17 秒かかる（実測）。同じワーカーに両方を任せると、テスト実行が終わっている提出の
結果が、前に並んだほかの学習者の LLM 待ちの後ろで待たされる。

**決定的評価専用のワーカーを、最低 1 本起動する。** これで、学習者に結果が返るまでの時間が p95 で 0.8 秒になる。

```fish
uv run aijudge-worker --phase deterministic --name det1 &   # 速い段階（最低 1 本）
uv run aijudge-worker --phase ai --name ai1 &               # AI はあとから届く
uv run aijudge-worker --phase ai --name ai2 &
uv run aijudge-worker --phase ai --name ai3 &
uv run aijudge-worker --phase ai --name ai4 &
```

`--phase` を付けないワーカーは、両方の段階のジョブを処理する。開発機ではそれで十分だが、**締切前に提出が集中すると、
決定的評価が AI 評価の後ろに並ぶ**ので、運用では分ける。

### イベントのリレー（#328）

```fish
uv run aijudge-relay        # 常駐
uv run aijudge-relay --once # 空になるまで流して終わる（cron でも可）
```

**リレーは 1 本だけ起動する。** 採点結果とイベントは同じトランザクションで書かれる
（outbox）ので失われないが、書いただけでは購読者に届かない。未送信のイベントを読んで購読者を
呼び出すプロセスが必要である。いまの購読者は習熟度（S7）で、**リレーが動いていないと、
知識要素の習熟度は 1 件も更新されない。**

複数起動しても壊れない（購読側は冪等で、同じ採点を二度受け取っても習熟度は
一度しか更新されない）が、重複配信を常態にする理由は無い。

**リレーが止まっていても、採点は完了する。** そのため、止まっていても気づけない。実際、購読者は
2026-08-29 に実装されたのに、購読者を登録するコードがテストにしか無く、運用では
`grading.completed` が 254 件、未送信のまま溜まっていた（`skill_states`
は 0 件だった）。いまは、設定のドリフト検査（`aijudge-config-check`）がこのユニットの停止を
検出する。

リレーを初めて起動すると、溜まっていたイベントが一度に送られる。ただし、**推移のグラフが「その日にすべて更新された」
形にはならない。** `SkillPoint.recorded_at` はイベントの `occurred_at` を
使うので、記録は実際の提出時刻に沿って並ぶ。

実測（exam08、提出 496 件を 2 時間の一様到着、400 回試行）:

| | 平均 | p95 |
|---|---:|---:|
| 分割前・1 本 | 910 秒 | 1689 秒 |
| 分割前・4 本 | 18.2 秒 | 25.2 秒 |
| **決定的専用 1 本** | **0.5 秒** | **0.8 秒** |
| AI 専用 4 本（到着まで） | 17.6 秒 | 24.3 秒 |

ワーカーを複数起動するときは、**DB に PostgreSQL を使うこと。**

実測（受講 91 名 × 1 課題 × テスト 5 件、colima 上のコンテナ隔離）:

| ワーカー | 所要 | 秒/件 |
|---:|---:|---:|
| 1 | 53.0 秒 | 0.58 |
| 2 | 34.8 秒 | 0.38 |
| 4 | 25.2 秒 | 0.28 |

91 名が同時に提出したときに「結果表示まで 30 秒以内」を満たすには、ワーカーが 4 本必要である。

**SQLite でワーカーを複数起動しないこと。** 行ロックが無いので同じ提出が
二度採点され、1 つの提出に採点結果が 2 つできてしまう。`aijudge-worker` は、
この構成で起動すると警告を出す。

### 並列度を決める値は複数の場所にある。まとめて変更する（#260・#261）

**運用機の並列度を決める値は、1 か所にまとまっていない。** どれか 1 つだけを上げると、混雑した
ときに DB の接続を取れずに失敗する。**値を上げるときは DB の上限を先に、下げるときは DB の上限を後に変更する。**

| 値 | 置き場所 | elite の現在 |
|---|---|---|
| 学習者アプリのプロセス数 | `AIJUDGE_WEB_WORKERS`（EnvironmentFile） | 2 |
| 教員コンソールのプロセス数 | 1 固定（`aijudge-review.service`） | 1 |
| 決定的ワーカー | `aijudge-worker-det.service` | 1 |
| AI ワーカー | `aijudge.target` の `Wants=`（@1〜@4） | 4 |
| 1 プロセスあたりの DB 接続 | `packages/persistence/.../engine.py` | `pool_size 10 + max_overflow 20` |
| DB の上限 | postgresql の `max_connections` | 300 |
| 待ち時間の目安に使う本数 | `AIJUDGE_AI_WORKERS`（EnvironmentFile） | 4 |

見積りは**プロセス数 × 30**（`pool_size + max_overflow`）。

```
web 2 + review 1 + det 1 + ai 4 + finalize 1 = 9 プロセス
9 × 30 = 270（最悪）   9 × 10 = 90（定常）
```

**`max_connections` は、この最悪値を上回るようにすること。** 定常値で決めると、
締切前の集中時にちょうど足りなくなる。接続が足りなくなるのは、最も混雑している瞬間である。

**`AIJUDGE_AI_WORKERS` は、AI ワーカーの本数と揃えること。** この値は、学習者に
表示する「あと何分」の計算にしか使わないが、**ワーカーの本数をもう 1 か所に書いた値**である。
4 本動いているのに 1 と設定すると、待ち時間の目安が 4 倍になる。採点は止まらないので、
ずれていても誰も気づかない。`aijudge-config-check` が両方を照合し、ずれていれば通知する。

**教員コンソールは 1 プロセスのままにする。** コンソールは操作の結果をプロセス内の変数に保持して
いるので（`Console.last_*`）、複数のプロセスにすると、POST と続く GET が別のプロセスで
処理され、**確定を押しても何も起きなかったように見える**ことがある（#260）。
この作りを直してから、プロセスを増やすこと。

### 書いた設定が機械に届いているか

**`deploy/systemd/` の変更は、デプロイのたびに配置される**（`install-units.sh`）。
以前は、`bootstrap.sh` を実行した最初の 1 回しか配置されていなかった。
2026-09-12 に確かめたときは 11 個中 9 個がずれており、AI ワーカー 4 本の宣言も、
ログの識別名も、systemd のサンドボックス化も、**ファイルには書いてあるのに反映されていなかった**。

疑わしいときは手で確かめる。

```fish
ssh <host> 'for f in /opt/aijudge/deploy/systemd/*; do n=(basename $f); cmp -s $f /etc/systemd/system/$n || echo "ずれ: $n"; done'
```

unit の再配置は、root で動く oneshot のサービスだけが行う（デプロイは aijudge ユーザで実行し、
`/etc/systemd/system/` への書き込み権限を持たない）。

```fish
ssh <host> 'sudo systemctl start aijudge-units.service; journalctl -u aijudge-units -n 20'
```

GPU を使う科目と使わない科目でワーカーを分けたい場合は、`--subject` で科目を指定する。

```fish
uv run aijudge-worker --subject cs_network_python --name py1
```

### 手でデプロイする（#345）

**デプロイは、タグを push したときに行われる。** 運用機の `aijudge-autodeploy.timer` が 5 分ごとに
origin の `v*` タグを確かめ、新しいタグがあれば `deploy.sh` を呼ぶ。手でデプロイする必要があるのは、
次の周回を待たずにデプロイし直したいときだけである。

**その場合は、先に環境ファイルを読み込むこと。** unit は
`EnvironmentFile=/srv/aijudge/config/aijudge.env` を読み込むが、ssh から
スクリプトを直接実行すると、環境ファイルは読み込まれない。

```fish
ssh <host> "sudo -u aijudge sh -c 'set -a; . /srv/aijudge/config/aijudge.env; set +a; exec /opt/aijudge/deploy/deploy.sh v1.2.3'"
```

環境ファイルを読み込まずに実行すると、`deploy.sh` は最初の段階で止まる（2026-09-20 に、`AIJUDGE_DATABASE_URL`
が無いまま実行され、alembic が既定値で接続して認証に失敗した。**このときは失敗したので気づけた**。
失敗しない場合に備えて、最初に実行を拒否するようにした）。

### 設定の控えはバックアップの中に置かない（#344）

`/srv/aijudge/config/` を編集する前に控えを取るなら、**`/srv/aijudge` の外**
（`/root/aijudge-env-history/` など）に置く。理由は 2 つある。

- **バックアップが止まる。** restic は `aijudge` ユーザで実行するので、控えを
  `root:root` で置くと読めず、**exit 3** で終了する。スナップショット自体は
  保存されるので気づきにくいが、`set -e` のために後段の
  `restic forget --prune` が実行されず、古い世代の整理が止まったままになる。
  2026-09-20 に 3 系統のバックアップが同時に failed になった原因はこれで、
  控え 7 つのうち 1 つだけ所有者が違っていた
- **認証情報のコピーが増える。** `/srv/aijudge/config/` はバックアップの対象なので、
  控えを置くと、その数だけすべてのスナップショットに含まれる

日次の `aijudge-config-check` は、`aijudge` から読めないファイルを見つけると
通知する（状態が変わったときだけ通知する）。

## 成績を閉じる

教員の待ち行列に並ぶのは、**学習者が異議を申し立てた提出だけ**である（ADR 0009）。
依頼が出なかった提出は、何もしなければ未確定のまま残るので、成績を確定する手段が必要である
（ADR 0010）。

### 自動確定（採点で仮確定 → n 分後に確定）

```
採点完了   仮確定。「MM/DD HH:MM に確定します」と学習者に示す。異議はここまで
  ↓ 採点 + n
確定       依頼フォームは閉じる（申し出は担当教員へ）
```

**確定までの時間は、課題の締切からではなく、提出ごとの採点完了から数える。** 締切を起点にすると、
締切前に提出した学習者は、自分の点が確定するまで何日も待つことになり、その間は
再提出を判断する材料が「暫定」のままになる。採点は提出の直後に終わるので、そこから
n 分で確定すれば、**締切前に確定し、確定後も締切までは出し直せる**。出し直しは確定に
妨げられず（`Task.accepts_submissions_at` は確定を見ない）、採用されるのは
最高得点の提出である。

要点は、**いつ確定するかを前もって学習者に知らせる**ことである。知らせずに確定させると、学習者は確定した
ことを後になってからしか知ることができない。前もって知らせてあれば、その期限で異議の受付を締め切ってよい。

猶予は、教員が `/manage` で**コースごと**に設定する（既定は「自動確定しない」。
設定しなければ仮確定にもならず、依頼はいつでも受け付ける）。
設定しただけでは確定しない。確定を実行するのは次のプロセスである。

```fish
uv run aijudge-finalize --once                # 1 回走って終わる（cron 向き）
uv run aijudge-finalize                        # 常駐（既定 15 分ごと）
uv run aijudge-finalize --once --dry-run       # 何が確定するかだけ見る
```

cron で実行するなら、1 時間ごとで十分である（猶予は時間単位で設定することが多いため）。

```
17 * * * * cd /srv/aijudge && AIJUDGE_DATABASE_URL=... /usr/local/bin/uv run aijudge-finalize --once
```

**自動確定しない提出**は、次の 3 種類である。これらは `/manage` の未確定件数に残るので、
一括確定するか、待ち行列から個別に処理する。

- 未対応の再確認の依頼がある提出（学習者が、人に確認してほしいと求めている）
- `review_required` に振り分けられた提出（コンパイルエラー、合否境界の近傍など）
- 未採点の観点がある提出（誰も見ていない観点を成績に含めない）

**確定の処理を、採点ワーカーには組み込んでいない。** 確定はレビュー側の判断なので、採点を
止めたいときに、確定まで一緒に止まると困るためである。

### 一括確定（課題ごと・教員の操作）

科目のページから問題セットのページを開くと、未確定の提出をまとめて確定できる。根拠の説明が必須で、
その説明は**学習者にそのまま表示される**。自動確定と違い、`review_required` の提出も含める
（教員が根拠を書いて責任を持つ操作だからである）。未対応の依頼がある提出だけは確定しない。

### 実施中に課題を直す

問題文の誤りに気づいたら、課題を開いて直す。**直すと新しい版ができ、出題済みの版は
書き換わらない**（P8）。過去の採点は、採点したときの版を指したまま残る。

**採点に使う材料は、その材料を使う観点の中で編集する**（#303）。課題の編集画面でルーブリック
の観点を開くと、その観点が指名した評価器の材料が表示される。`code_test_runner`
なら入出力セット（テストケース）、`checklist_ai_judge` なら項目表である。科目プロファイル
が宣言していなくても、**観点に評価器を割り当てた時点で欄が表示される**（観点は課題ごとに自分の
評価器を持つ・ADR 0018）。材料が 0 件なら、画面に「その観点は判定できない」と表示される
（総合点は表示しない・ADR 0015）。提出の遵守のように材料を持たない評価器には、欄を表示しない。

「テストケースを直す」「項目表を直す」で追加や修正をすると、**新しい版になる**（P8）。
どちらも「この問題を保存して更新する」とは別の操作で、**それぞれ別に版が上がる**。
**TA は確認だけができる**（材料を読めないと、「入力例 1 で失敗する」という質問に答えられないため。直すのは担当教員）。

どの観点にも指名されていない材料は、「**使われていない入出力セット**」として画面の
末尾に表示される。観点を宣言する前に作られた課題や、評価器を付け替えた課題で起きる。
材料があるのに画面から見えなくなるのを避けるための表示で、これらの材料は採点には使われていない。

### 直した課題をファイルに戻す（#363）

コンソールで編集した内容は、**その時点では DB にしか残らない**。課題の正本は講義
リポジトリ（private）の `<科目>/<年度>/assignments/` に置いてあるので、
直した日のうちにファイルへ書き戻し、PR を出す。

```fish
# 1. 運用機から書き出す（DB は変わらない。手元の講義リポジトリへ）
sudo -u aijudge sh -c 'set -a; . /srv/aijudge/config/aijudge.env; set +a; \
  exec /opt/aijudge/.venv/bin/aijudge-admin course export \
  --course <コース ID> --out /srv/aijudge/courses/<code>/2026/assignments --force'

# 2. 手元でずれが無いか確かめてから PR
uv run aijudge-admin course diff --file network/2026/assignments/course.yaml
```

**書き出せなかった課題があると、`export` は 1 を返し、その課題の名前を表示する。** ファイルが
不完全なまま正本になると、次に `course apply` を実行したときに、その課題が知らないうちに
変わってしまう。`diff` は、一致なら `0`、差があれば `1`、判定できないとき（定義が読めない・
まだ投入していない）は `2` を返す。**「判定できない」は合格ではない。**

**項目ごとに比べるときは、`course snapshot` を使う。** `diff` は課題ごとに「違う」としか
表示せず、課題の日程・問題セットの値・コースの値は比べない。`snapshot` は、
定義ファイル（`--file`）と DB（`--course`）を同じ規則で項目ごとの値に展開する。
DB 側には、項目ごとに「いまの値になった時刻」を付ける（版の項目は版の
`created_at`、課題の項目は監査記録 `task.updated` から求め、記録の無いものは `null`）。
定義ファイルに書いていない日程と問題セットの値は、`apply` が変更しないので出力しない。

**公開リポジトリのチェックアウトには書き出せない**（`export` が拒否する）。書き出す内容には
問題文・テストケース・参照解答が含まれ、未公開の回も含まれるためである。

### 承認待ちは課題ではない（#321・ADR 0019）

AI が作った課題も、AI が書き直した課題も、**下書き**として保存される
（`/manage/courses/{id}/drafts`）。**下書きが課題になるのは、採用したとき**である。それまでは、
学習者の画面にも課題の一覧にも表示されない。

- **採用するまでは、何でも直せる。** 直せるのは、課題キー・題名・問題文・出題する問題セットである。
  キーは、採用したあとは変更できない（提出も採点の記録も、このキーで課題に結び付くため）。
- **下書きを捨てると、すぐに削除される。** 理由は尋ねない（記録しないため）。まだ課題になって
  いないので、捨てても学習者には何も影響しない。
- 改訂の下書きでは、キーを変更できない（同じ課題の書き直しだからである）。採用すると新しい版に
  なり、その時点で出題される。

**この仕組みに移行する前の承認待ちは、引き継がれない。** `task_versions` に残る `IN_REVIEW` の版は
一覧に表示されなくなるので、課題の画面から削除して、入れ直すこと。

### 既存の課題を現在の基準に合わせて書き直す（#306）

既存の課題は、**入出力だけを採点する前提**で書かれていることが多い。仕様が曖昧だったり、
例と本文が食い違っていたり、読みやすさのような観点への配慮が無かったりする。コースの共通
ルーブリックで「読みやすさ 0.3」と決めても、**問題文がそれを求めていなければ**、
学習者には減点の理由が分からない。

課題の編集画面の「**AI に書き直させる**」で、いまの観点に合わせて問題文を
書き直し、問う知識要素を選び直す。

- **AI への指示を渡せる**（1 行に 1 件・任意）。何を直してほしいかは、問題文を読んだ教員が
  いちばんよく知っている。観点との食い違いは機械的に見つけられるが、「毎年ここで
  質問が来る」ことは教員しか知らない。**指示は必須事項の一覧ではない**ので、外せない条件は
  「必ず」、希望は「できれば」と書く（作問の指示欄と同じ扱い）。空欄でも実行できる。
- **書き直すのは、問題文と知識要素だけである。** 観点（ルーブリック）はコースが持って
  おり、段階まで決まっている。観点をモデルに書かせると、コースで決めた段階が
  課題ごとにばらばらになる。入出力セットと参照解答も変更しない（#305 の担当）。
- **結果は必ず承認待ちの版になる**（P5・ADR 0008）。承認するまで、学習者にはいまの版が
  表示される。
- **直すところが無ければ、新しい版を作らない。** 差分の無い版を増やすと、教員は中身の
  無い版を 1 件ずつ開いて確かめることになる。

未承認の一覧（`/manage/courses/{id}/drafts`）には、行ごとに**新規か改訂か**が
表示される。改訂の行には、**問題文の差分**と**提出の件数**が表示される。出題済みの課題の
問題文を書き換えると、既に提出した学習者と後から提出する学習者で、違う問題を解くことになるためである
（過去の採点は採点したときの版を指したまま残るので、壊れない・P8）。

### 解答例からテストケースを作る（#305）

課題の編集画面で、`code_test_runner` を指名した観点を開くと、**参照解答**を読める
（**教員だけ**が読め、TA には表示しない）。以前は参照解答が画面のどこにも表示されなかったので、
門 1（参照解答が全ケースを通る）で不合格になっても、何が通らないのかを確かめられなかった。

手順は 3 段階あり、**どの段階でも版は上がらない**（版が上がるのは、保存を押したときである）。

1. **AI に解答例を書かせる。** AI がいまの問題文から解答例を書き、欄に入れる。教員はそれを読んで直す。
2. **解答例からテストケースを提案させる。** 入力だけをモデルに考えさせ、**期待出力は、
   その解答例を実際に実行して求める。** モデルに期待出力を書かせないのは、期待出力の誤りが
   「全員が不合格になる」という形で現れ、原因が提出物の側にあるように見えるためである（決定的な結果は
   `conclusive` なので、AI にも見直されない・P3）。
3. **採用したテストケースだけ**が、入出力セットに入る。印を付けなかったものは消える（P5）。

**解答例を実行するには、サンドボックスが必要である。** `AIJUDGE_SANDBOX` が無い環境では、提案を
作れないと表示する（モデルが書いた出力で代用することはしない・ADR 0006）。macOS では、
colima を起動してから使うこと。

参照解答は、入出力セットと**組にして保存する**。門 1 は両方を照合する検査
なので、片方だけを先に保存できると、教員が意図していない組み合わせを検査する
ことになるためである。門で検査するのも、**いま欄に入っている内容**である。

**テストケースは、後から追加できる。** 「テストケースを後から付ける」で生成
すると、いまの問題文から参照解答とテストケースを作り、正しさの観点の判定をテスト実行に
戻した**新しい版**ができる。この版は生成物なので承認待ちになり、**承認するまで、学習者には
1 つ前の承認済みの版が表示される**。

**課題を訂正しただけでは、既に提出された答案は古い版の基準で採点されたままである。** 課題の
編集画面には、対象があるときだけ「いまの版で採点し直す（N 件）」が表示される。
採点し直すのはこのボタンを押したときだけで、**確定済みの提出は採点し直さない**。確定した成績を、
システムが勝手に変えないためである。過去の採点も消えず、新しい採点が終わると、古い採点に
「置き換わった」印が付く。

**課題を作り直して、同じ問題を 2 件にしないこと。** 同じ問題セットに同じ題名の課題が
複数あると、一覧に警告が表示される（別々の課題なので、提出も採点も分かれてしまう）。

### 課題を消す・取り下げる

知識要素と同じ区別を課題にも当てている。

    提出が 1 件も無い  削除できる（打ち間違いの後始末）
    提出がある         出題を取り下げる（学習者に出なくなる。記録は残る）

**採点結果は課題の版を指している**（P8）。提出のある課題を削除すると、その成績が
どの課題の点なのか辿れなくなり、蓄積した習熟度の根拠も失われる。そのため、
「使わなくする」と「無かったことにする」を分けてある。取り下げは**取り消せる**。

取り下げた課題は学習者の一覧に表示されず、URL を知っていても開けない。教員の一覧には、
「出題を取り下げ済み」の印が付いて残る。

### お試しコース（#194・#197）

**設定したときだけ使える機能である。** `AIJUDGE_DEMO_COURSE` にコース ID を設定した
ときだけ、ログインした人が自動でそのコースに受講登録される。提出も採点も通常のコースと
同じように動くが、**学習履歴にも評価にも残らない**（`is_trial`・#197）。

```fish
# 1. 定義から作る（冪等。subjects/demo/course.yaml）
uv run aijudge-admin demo seed
# 2. 表示されたコース ID を環境変数に置く（運用なら aijudge.env に書いて再起動）
set -gx AIJUDGE_DEMO_COURSE crs_...
```

**定義は `$AIJUDGE_PROFILES_DIR/demo/course.yaml` から読む。** 運用では、科目
プロファイルと同じディレクトリの下に置く必要がある。リポジトリの `subjects/*.yaml`
だけを運用側へコピーすると、`demo/` の階層が抜け落ち、`seed` も `reset` も「定義が無い」と表示して
止まる。

**提出が溜まりすぎたら、運用者が削除する。** `demo reset` は、提出・課題・受講登録を削除して、定義から
作り直す。削除する操作なので、既定では件数を表示して確認を求める。`--yes` を付ければ確認を省けるが、
**cron では実行しない**（#194 の判断）。提出の量は、コンソールのコース一覧で確認できる。
定義に課題を追加しただけなら、`demo seed` を実行すれば、既存の提出と受講登録を残したまま追加できる。

**運用機で手でコマンドを実行するときは、env ファイルを自分で読み込むこと。**
`/srv/aijudge/config/aijudge.env` を読み込むのは systemd の `EnvironmentFile=` だけなので、
`sudo -u aijudge aijudge-admin ...` のように直接実行すると、環境変数は何も設定されない。
`AIJUDGE_DEMO_COURSE が設定されていません` と表示されて止まるのはこのためで、設定の不備ではない
（同じ理由で `AIJUDGE_DATABASE_URL` も設定されないので、別の DB に接続するおそれがある）。

```fish
ssh <運用機> 'sudo -u aijudge sh -c "set -a; . /srv/aijudge/config/aijudge.env; set +a; exec /opt/aijudge/.venv/bin/aijudge-admin demo reset"'
```

引用符の内側は `sh` で実行するので、POSIX の構文で書く（fish には `set -a` が無い）。

### シラバスから基本情報と知識要素の候補を作る

入口は 2 つある。**コースの基本情報**（左の帯の「コースの基本情報」→
「基本情報を入力する」）と、**知識要素の候補**（知識要素 →「本文から候補を作る」）である。どちらも、
**本文を貼り付ける**か、**PDF / DOCX / テキストのファイルを選ぶ**。

コース名と概要・到達目標は `courses` に保存する。**科目プロファイルには置かない。**
科目プロファイルは採点方法の宣言（ADR 0002）で、コードと同じレビューを通す前提の設定だからである。
学期ごとに変わる事務データのためにブラウザから科目プロファイルを書き換えられるようにすると、1 人の操作で
全員の採点が止まりうる。コースコードと学期は、（テナント・コード・学期）の組で
コースを識別するのに使うので、この画面では変更できない。

URL は受け付けない。龍谷大学のシラバスは
JavaScript で描画されるページで、サーバから取得しても空の外枠しか返らないためである（実測で
1815 バイト、中身は `<title>acslb-client</title>` だけだった）。URL を取得しないので、
サーバが任意の URL にアクセスする経路も作らずに済む。

PDF からの抽出には、提出物の採点と同じ処理（`aijudge_norm_document_text.text_of`）を
使い、Markdown に整えて入力欄に入れる（見出しと「第 N 回」を整えるだけで、内容は
書き換えない）。**スキャン画像の PDF は読めない**（文字が埋め込まれている必要がある）。
読めない場合は、読めないと表示して処理を止める。黙って OCR にかけると、読み取りの誤りがそのまま
候補になり、候補の出所が分からなくなるためである。

表示されるのは、**登録済みの語彙から選ばれた候補**である。印を付けてまとめて採用すると、
**このコースが使う範囲**に追加される（語彙への登録ではない）。**新しいキーは提案されない。**
語彙は骨格（`aijudge-admin kc seed`）で決まり、画面から増やす方法は無い。
画面から増やせると、同じ概念が別のキーで二重に登録され、Q-matrix と習熟度が 2 つに分かれてしまう
（2026-09-13 決定）。モデルが一覧に無いキーを返したときは、理由を添えて候補から除く。
候補に無い知識要素は、「名前空間から足す」から分野ごとに探して追加する。

シラバスは、次の形式のリンクで直接開ける。

```
https://syllabus.ws.ryukoku.ac.jp/acrsw/CSylNoSSO/CNoSSO.do?i=<管理番号>&n=<年度>
```

- `i` … シラバス管理番号。**履修登録コードとは別物**で、シラバス一覧の
  検索結果に出ている
- `n` … 年度（`2026` のような文字列）

例（プログラミング及び実習Ⅱ）:

```
https://syllabus.ws.ryukoku.ac.jp/acrsw/CSylNoSSO/CNoSSO.do?i=Y001009010&n=2026
```

出典: <https://hig3r.hatenadiary.com/entry/2023/03/13/220000>

### ルーブリック（観点）をどこで決めるか

観点は 2 か所で決まり、**課題の宣言が優先される**。

    課題の宣言（`TaskVersion.criteria`）… 個別に変えたい課題だけ
    コースの共通（`Course.rubric`）……… その科目に共通の観点
    組み込みの既定 ………………………… 正しさ（0.7）＋読みやすさ（0.3）

共通ルーブリックは、コースの共通設定で決める。**新しい課題は共通ルーブリックを引き継ぐ**が、
既にある課題は変わらない。出題済みの課題の採点基準を書き換えないためである（P8）。
個別の課題の観点は、問題セットのページから直す。**直すと版が上がる**（過去の採点は
元の版のまま残る）。

段階は、`名前 | 説明 | 割合` の形式で 1 行ずつ書く。観点 1 つにつき 4 段階あり、それぞれに名前・
説明・割合があるので、入力欄に分けると 1 画面に 12 個以上の欄が並んでしまう。空にすると、
4 段階の既定（未達／一部／概ね／達成）が入る。**重みの合計は 1.0 にする**（観点ごとの
重みが、そのまま成績の配分になる）。

### コースごとの採点設定

`subjects/*.yaml` は**雛形**である。同じ雛形を複数のコースが使い、各コースは
雛形からの差分だけを持つ。

    実効設定 = 雛形（ファイル） ← コースの上書き（DB の `grading_overrides`）

上書きが空なら雛形の設定がそのまま使われ、既存のコースはこれまでと同じように動く。

**上書きは、そのコースにしか適用されない。** そのため、教員が画面から変更してよい
（共通設定 →「採点設定」）。ADR 0002 が避けたかったのは、「1 人の
操作で全員の採点が止まる」ことである。それが起きるのは、雛形そのものを書き換えられる場合である。
雛形は読み取り専用のまま残る。

変更できるのは、言語・時間の上限・blind 抽出率・評価器の組み合わせである。評価器は、
**インストール済みのものから選ぶ**（存在しない名前を書けると、その科目の採点が
ずっと失敗し続ける）。`kc_namespaces` はほかのコースと共有する語彙の範囲なので、
上書きできない。

保存時には、起動時と同じ検査を行う。**それでも検出できない誤りが 1 つある。**
`language` の取り違えは設定としては正しいので、結果は「全員 0 点」になり、原因が提出の側に
あるように見える。「この設定で試す」で、この誤りを見つけられる（そのコースの参照解答を 1 件実行する。
**結果は保存しない**ので、採点の履歴には残らない）。

新しい評価器が必要になるのは、判定の種類そのものが新しいときだけである（数学の
CAS による同値判定、物理の単位検査など）。`code_test_runner` は 1 つの評価器で言語を
選べ、`rubric_ai_judge` は言語に依存しないので、**コースを増やすたびに評価器を
作る必要はない。**

### 知識要素の骨格を入れる

**骨格は、学期の前に 1 度投入する。** 投入しないと、教員は知識要素を 1 件も追加できない。
分野と単位は骨格でしか作れず、木が空だと、「既存の単位の子としてだけ追加できる」という
規則のために、教員は何も追加できないからである。

**運用では科目プロファイルと同じ場所に置く。** リポジトリの `subjects/kc/` は
サンプルで、デプロイ（`git checkout <tag>`）のたびに入れ替わる。

```fish
sudo -u aijudge mkdir -p /srv/aijudge/subjects/kc
sudo -u aijudge cp /opt/aijudge/subjects/kc/*.yaml /srv/aijudge/subjects/kc/
```

`reference/` はコピーしない。原典を読むためのファイルで、投入しないためである。

同梱している骨格は 3 つある。**必要なものだけを投入すればよい**（投入していない名前空間を
プロファイルが宣言すると、そのコースでは知識要素を扱えない）。

| 名前空間 | 中身 | 規模 |
|---|---|---|
| `cs` | CS2023（ACM/IEEE-CS/AAAI） | 987 件 |
| `math` | CUPM 2015（MAA）＋ 高等学校学習指導要領（平成30年告示）数学 | 939 件 |
| `physics` | 参照基準 物理学・天文学分野（2016）＋ FCI ＋ 同 物理基礎・物理 | 535 件 |

```fish
uv run aijudge-admin kc seed --namespace cs
uv run aijudge-admin kc seed --namespace math
uv run aijudge-admin kc seed --namespace physics
```

何度実行しても、KC は重複して増えない。骨格ファイル（`$AIJUDGE_PROFILES_DIR/kc/<名前空間>.yaml`）に
項目を追加したら、もう一度実行すれば差分だけが投入される。投入は監査ログに残る
（`profile.updated` / 対象 `kc_namespace` / 出典付き）。

**知識要素は、テナントをまたいで共有される。** `knowledge_components` には
`tenant_id` が無く、語彙はデプロイ全体で 1 つである。そのため、投入は機関ごとの操作では
なく、サーバの運用者が 1 度行う操作になる。**共有するのは語彙だけで、習熟度は
共有しない**（`skill_states` の主キーは `(tenant_id, learner_id, kc_id)` である）。
2 つのテナントが同じ `math.calculus.integral.ftc` を参照するのは正常である。
同じ理由で、利用件数（課題数・コース数）も**テナントをまたいで**数える。
自分の機関の分だけ数えると、「ここでは誰も使っていない」ことが、ほかの機関が依存している
知識要素を引退させる理由になってしまう。詳しくは README の
「モジュールとテナント」を参照すること。

画面から追加できるのは**知識要素（第 3 階層）だけ**で、分野と単位は骨格が決める。
追加するときは、近い既存の KC が分野・単位をまたいで提示される（`subjects/kc/README.md`）。

### 習熟度を見る（#328）

知識要素を付けた課題が採点されると、学習者ごとの習熟度が更新されていく。
コンソールの「習熟度」（コースの左の帯）で、コース全体の分布と推移、
受講者 1 人分の内訳と根拠を確認できる。見られるのは**教員とテナント管理者だけ**で、
TA には表示しない。TA は採点を分担するが、習熟度は成績から算出する値だからである。

**習熟度は、学習者には表示していない。** 予測の妥当性（次の課題の正誤を AUC ≥ 0.70 で
予測する、という受け入れ基準）をまだ測れていないので、確定した評価として
読まれるおそれのある相手には表示しない（#327 で、段階的な公開を検討中）。

**推移は、記録のある期間しか描けない。** `skill_points` は、
移行 `a1c4f70b28de` を適用した時点から記録され、**それより前の推移は埋められない。**
それ以前の採点は習熟度の値には反映されているが、推移としては残って
いない。画面には「記録は ○月○日 から」と表示し、そのことを明示している。

**習熟度は、コースをまたいで蓄積される**（`skill_states` の主キーに
コースは含まれない）。コースの画面に表示されるのは、そのコースの受講者について、そのコースが
使う知識要素だけを取り出した値にすぎない。値そのものには、担当外の科目で得た
観測も含まれている。根拠として開けるのは担当コースの提出だけで、ほかのコースから来た観測は
件数だけを表示する（ほかのコースの課題名は、成績に近い情報だからである）。

### 学内からだけ受け付ける（#333）

試験のために、一部の問題セットを**学内からの接続に限定**できる。設定は 2 段階で行う。

**1. テナント管理者が範囲を決める**（`/manage/campus-networks`）。

**この画面は、学内の端末で開くこと。** 画面には「いまあなたが接続している
アドレス」と「この設定で、あなたは学内と判定されるか」が必ず表示される。範囲は
人が調べて書き写す値なので、書き写しの誤りは、**試験当日に全員が提出できない**という
形で初めて表に出る。開いた画面に表示されるアドレスを登録するのが、最も確実である。

**端末に割り当てられるアドレスを、そのまま書かないこと。** 無線 LAN の内側のアドレス
（`10.` で始まるものなど）と、サーバに届くアドレスは、間に NAT があると別の
ものになる。実測でも、`10.20.*` からの接続は 1 件も届いていなかった（2026-09-16）。

読めない行があると保存できない。読めない行を黙って無視すると、範囲が抜けたことに気づかない
まま試験を迎えてしまうためである。変更は監査ログに残る（`campus_networks.updated`）。

**2. 担当教員が問題セットごとに切り替える**（問題セットの「受け付ける場所」）。
日程と同じく問題セット単位で決まり、その問題セットのすべての課題に適用される。
コースの定義ファイルでは、`units` に `campus_only: true` と書いても設定できる（v1.39.3 から）。
定義から作り直すコース（`demo reset` など）では、この書き方にしないと、作り直すたびに制限が外れる。

判定の結果は 4 種類ある。**「学内か学外か」の 2 値にはしていない。**

| 状態 | 意味 | 提出 |
|---|---|---|
| 学内 | 範囲の中から来た | 通す |
| 学外 | 範囲の外から来た | 断る |
| 未設定 | 範囲が 1 件も無い | **通す**（設定忘れで全員を止めない） |
| 判定できない | 範囲はあるが接続元が読めない | **断る**（制限が黙って抜けるほうが悪い） |

**接続元は、`X-Forwarded-For` の右端の値**（逆プロキシが書いた値）で判定する
（`aijudge_telemetry.client_ip`）。左端の値はクライアントが自由に書けるので、
左端で判定すると、学内のアドレスを名乗るだけで提出できてしまう。**アプリに、逆プロキシを通さず直接アクセス
できないようにしておくこと。** 現在の構成では、`127.0.0.1:8080` だけで待ち受けている。

**この設定は、採点と確定には影響しない。** 既に提出されたものは、そのまま扱われる。

### 試験を公開まで TA に見せない（ADR 0025）

公開前の問題セットは、**通常は TA にも見える**（質問への対応と採点の準備のため・
#340・#102）。試験では、問題セットの画面の「公開前に見せる相手」を
**公開まで教員だけに見せる**に切り替える。

- 公開の時刻（`opens_at`）までは、TA の一覧（学生画面・コンソール）にも課題ページ
  にも表示されず、TA は試しに提出できない。**教員が試しに提出した答案も、TA には見えない**
  （模範解答に近いため）
- **公開の時刻以降は、TA にも見える。** 試験監督をする TA は、開始と同時に問題を読める
- **公開の時刻が無いと、この設定は機能しない。** 時刻の無い課題は、最初から公開済みとして扱うためである。
  画面に警告が表示されるので、先に日程を入れること
- 変更は監査ログに残る（`task.updated`・`field=confidential`）

### 一部の学習者にだけ出す ── 出題先の名簿（ADR 0025）

追試・再試験は**別の問題セットとして作り**、出題先を名簿で絞る。同じ課題のまま
一部の学習者の日程だけを変える方法は採らない（締切を学習者ごとに求めることになり、
遅延減点・自動確定・動画の保存期間のすべてを変更する必要があるため）。本試験と追試の成績は、
別の課題の成績として残る。

1. **名簿を作る**（`/manage/courses/<id>/groups`、または下の API・CLI）。
   名簿に入れられるのは、**そのコースの学習者だけ**である。登録されていないアカウントが 1 つでも
   混じっていると、**何も保存しない**（一部だけが登録されると、漏れた学生が追試を見られない
   ことに誰も気づかないため）。保存は常に**名簿全体の置き換え**で、追加・削除された人が画面に表示される
2. **問題セットの「出題先」で名簿を選ぶ**。複数の名簿を選ぶと、どれかに入っている学習者に
   出題される。何も選ばなければ、受講者全員に出題される（従来どおり）

- 出題先に含まれない学習者には、一覧にも表示されず、URL でも開けず、「未提出」としても数えない
- **TA と教員には、名簿に関係なく見える**
- 名簿から外しても、その学生が既に提出した答案と成績は、本人に見える
- 出題先として使っている名簿は削除できない（先に出題先から外すこと）
- 名簿の変更は `group.updated` / `group.deleted` として、出題先の変更は `task.updated` として監査ログに残る

**画面を使わずに登録する**こともできる（手元のスクリプトから、教員の API トークンを使う）。

```sh
T="Authorization: Bearer aij_..."
C=crs_...
# 名簿を丸ごと置き換える（無ければ作る）。同じ要求を何度流しても同じ結果
curl -X PUT -H "$T" -H 'Content-Type: application/json' \
  -d '{"members": ["y2400001", "y2400002"]}' "https://<host>/console/api/courses/$C/groups/前期追試"
# 問題セット（画面の URL と同じ鍵）の出題先を置き換える。空の配列で全員に戻す
curl -X PUT -H "$T" -H 'Content-Type: application/json' \
  -d '{"groups": ["前期追試"]}' "https://<host>/console/api/courses/$C/units/exam01r/audience"
curl -H "$T" "https://<host>/console/api/courses/$C/groups"          # 一覧
curl -X DELETE -H "$T" "https://<host>/console/api/courses/$C/groups/前期追試"
```

登録されていない login があると 422 を返し、その login を `detail.unknown_logins` に並べる。

**運用機で直接実行する**こともできる（操作者は `system` として監査ログに残る）。

```sh
aijudge-admin group set --course crs_... --name 前期追試 --members retake.txt  # 1 行 1 login
aijudge-admin unit audience --course crs_... --unit exam01r --group 前期追試
aijudge-admin unit audience --course crs_... --unit exam01r                  # 全員に戻す
aijudge-admin group list --course crs_...
```

### 動画置き場は unit の `ReadWritePaths` の中に

`deploy/systemd/*.service` は `ProtectSystem=strict` で、書けるのは
`ReadWritePaths=/srv/aijudge /var/lib/aijudge` だけである。`AIJUDGE_VIDEO_DIR`
を別のディスク（例: `/work/aijudge/video`）に置くときは、**web の unit に drop-in で
書き込みの許可を追加する**。unit 本体はデプロイのたびに配置し直される（#261）ので、機械ごとのパスは
本体ではなく drop-in に書く。

```sh
sudo mkdir -p /etc/systemd/system/aijudge-web.service.d
printf '[Service]\nReadWritePaths=/work/aijudge\n' \
  | sudo tee /etc/systemd/system/aijudge-web.service.d/video.conf
sudo systemctl daemon-reload && sudo systemctl restart aijudge-web
```

動画を書き込むのは **web だけ**である。review は動画を読むだけで、動画を削除する `video purge` は
admin CLI（systemd のサンドボックスの外）で実行する。

**この設定を忘れると、web が起動しない。** 受け皿（下記）は起動時に `_incomplete/`
を作るので、v1.12.0 からは、動画の提出時ではなく**起動時に**
`Read-only file system` で失敗する。しかも uvicorn の親プロセスは動き続けるので、
`systemctl is-active` は `active` を返し、子プロセスだけが失敗を繰り返して、nginx が 502 を
返す。2026-09-21 には、これでサービスが 4 時間止まった。いまは起動時に、`AIJUDGE_VIDEO_DIR` を
明記した 1 行のエラーを出して終了するので、`journalctl -u aijudge-web` の
末尾を確かめること。

### 切れても続きから送れる（#119）

動画の提出では、学内 Wi-Fi を通して数 GB を送る。**1 回の PUT で送ると、90% まで送ったところで切断されても、最初からやり直し**
になる。試験のように時間が限られている場面では、そのまま「間に合わなかった」ことになる。

そのため、動画は**分割して送る**。サーバが受け皿を 1 つ作り、クライアントは
8 MiB ずつ送る。接続が切れたら「いま何バイト届いているか」をサーバに問い合わせ、その続きから
再開する。やり直すのは、失敗した 1 つの分割だけである。

| | |
|---|---|
| 受け皿の場所 | `AIJUDGE_VIDEO_DIR/_incomplete/`。**動画ストアと同じ根の下** ── 確定が `os.replace` で済む（別の場所だと 3 GB のコピーが増える） |
| 期限 | 24 時間。**次に誰かが始めるとき**に古いものを消す（専用のタイマーを足すと、その停止に誰も気づかない） |
| 持ち主 | 受け皿に提出者を書いてある。id を知っていても、他人のものには書けない・見えない |
| 二度押し | 受け皿の id が冪等キー。確定を 2 回押しても提出は 1 つ |
| 中断からの再開 | 受け皿の id はブラウザに残る。ページを閉じても「続きから再開」が出る（**同じファイルを選び直す必要がある** ── `File` は再読込をまたげない） |

**受付期間の判定は、確定の瞬間に行う。** 送信を始めたときに受付中でも、送っている間に
受付が終わることがあるためである。提出が成立するのは、確定の瞬間である。

1 回で送る経路（`POST /tasks/{id}/submit-video`）も残してある。JavaScript が
無い環境と、既存の連携のためである。**検査は 1 か所にまとめてあり**（`_video_gate`）、
どちらの経路でも、受付期間・学内限定・拡張子・上限を同じ規則で判定する。

nginx には、1 つの分割を通せるだけの `client_max_body_size` と、
`proxy_request_buffering off` の設定が必要である（`deploy/nginx/aijudge.conf.template` に
入れてある）。1 回の PUT で送っていた頃と違い、**全体の大きさ（数 GB）を通す設定は要らない。**

### 動画の保存期間（ADR 0020）

**動画は、課題の締切から 6 ヶ月で削除する。** 起点は提出日でも成績確定日でもない。同じ問題
セットの課題は締切が揃っているので、**動画は回ごとにまとめて削除される**。最も早い回の動画
でも、削除はその学期の成績への異議申し立てが終わったあとになる（後期の 10 月締切の動画は 4 月に削除し、異議申し立ては 2〜3 月に届く）。

削除は運用者が実行する。自動では実行しない。

```fish
uv run aijudge-admin video purge                     # 下見（既定）。何件・何 GB か出す
uv run aijudge-admin video purge --course crs_...    # このコースだけ
uv run aijudge-admin video purge --apply             # 実際に消す
```

**動画の置き場所は、`AIJUDGE_VIDEO_DIR` から読む。** 提出物（`--artifacts`）とは
別のディレクトリなので、env ファイルを読み込まずに実行すると、空の既定値を
参照して「0 件」と表示する。運用機では、ほかのコマンドと同じ形で実行すること。

削除するのは**ファイルだけ**である。`Artifact` の行も採点結果も残るので、
その採点が何を見て付いたのかは、削除後も読める（P8）。削除した動画を開くと、
学習者にも教員にも「保存期間を過ぎたため消去されました」と表示する。404 では、
不具合と区別できないためである。

**締切の無い課題の動画は、提出から 1 年で削除する**（砂場・自習用の課題が該当する）。共通の起点
が無いので提出日から数え、回ごとにまとめては削除されない。長く保存する代わりに、
**受け付ける大きさを 256 MiB に制限している**（通常は 5 GiB・
`AIJUDGE_MAX_VIDEO_BYTES_WITHOUT_DEADLINE`）。上限と保存期間は組で決めているので、
片方だけを変更しないこと。長い録画を提出させたい課題には、締切を設定する。

**動画はバックアップしない**（2026-09-25 決定。restic がバックアップするのは `/srv/aijudge` と
作業の記録だけである）。試験や演習の主な提出はブラウザのエディタと作業の記録に移り、動画は
主な提出物ではなくなったためである。本番の環境が壊れると、動画は復元できない前提で運用する。

### ブラウザ IDE を有効にする（2026-09-24）

runner（`aijudge-runner@1..4`）と受付終了時の自動提出（`aijudge-ide-close.timer`）は
`aijudge.target` に含まれているので、デプロイすれば起動する。**運用機で 1 度だけ手で行う作業**
は、次の 2 つである（どちらもリポジトリの外のファイルを扱う）。

1. **作業の記録の置き場所。** `aijudge.env` に `AIJUDGE_ACTIVITY_DIR=/work/aijudge/activity`
   を追加し、所有者を `aijudge` にしてディレクトリを作る。web は `/work/aijudge` に書き込める
   （動画の drop-in による）。コンソールは読むだけである。設定が無いと作業の記録は 503 で拒否されるが、
   編集・実行・提出は止まらない
2. **エディタ本体を nginx から配る。** 雛形（`deploy/nginx/aijudge.conf.template`）の
   `location /static/vendor/` を運用機の vhost に追加し、`nginx -t` で確かめてから再読み込みする。
   この設定が無くても動くが、Monaco（約 4.5 MB）を web のプロセスが圧縮せずに配信することになり、
   授業の始めに全員が一斉に開くと、web が応答しなくなる

restic の環境ファイルにも `AIJUDGE_ACTIVITY_DIR` を追加すると、作業の記録もバックアップの対象に
なる（追加しなくても IDE は動く）。

有効にしたら、テスト用のコースで一通り確かめる（エディタで書く → 実行 → 提出 → 採点 →
コンソールの「作業の記録」）。IDE に問題が出たら、問題セットの「答え方」をファイル提出に
戻せば、その場で従来の提出方法に戻せる（エディタの課題でも、ファイルでの提出は使える）。

### IDE の作業の記録の保存期間（ADR 0023）

ブラウザ IDE の**作業の記録**（`AIJUDGE_ACTIVITY_DIR` の下のファイルと、DB の索引）と
**自動保存**（書きかけのコード）は、学習者のデータなので、保存期間を過ぎたら削除する。

- 作業の記録: **動画と同じ期間**。問題セットの締切から 6 ヶ月、無ければ IDE を開いた
  時刻から 1 年
- 自動保存: **受付終了から 1 ヶ月**（2026-09-24 決定）。受付終了時点の最新の内容は自動提出で
  提出済みになっているので、自動保存に残っているのは複製である。受付終了の無い課題では、最後の保存から 1 年

削除は運用者が実行する。自動では実行しない（`video purge` と同じ判断）。

```fish
uv run aijudge-admin activity purge                     # 下見（既定）。何回分・何件か出す
uv run aijudge-admin activity purge --course crs_...    # このコースだけ
uv run aijudge-admin activity purge --apply             # 実際に消す
```

**置き場所は `AIJUDGE_ACTIVITY_DIR` から読む**（`--activity-dir` でも指定できる）。置き場所を指定せずに
実行すると、作業の記録は削除しない。本体（ファイル）を削除できないのに索引だけを削除すると、誰も
辿れないファイルが残るためである。自動保存は DB にしか無いので、削除される。削除したことは、監査ログに
`activity.purged` として残る。

提出の出どころの記録（`ide_submission_links`）は削除しない。中身はコードではなく指紋なので、
提出と同じ期間だけ残す。

**バックアップとの整合（2026-09-24 決定）。** オフボックスの restic は、月次のスナップショットを 6 本残す
（本番の環境が壊れても、過去 6 ヶ月の状態には戻せる・`aijudge-restic-offbox.sh`）。作業の記録の本体も、
restic の環境ファイルに `AIJUDGE_ACTIVITY_DIR` を書けば、一緒にバックアップする。削除したデータは
バックアップに最大 6 ヶ月残るので、学習者への告知には、その期間を足した合計を書いてある（作業の記録は
締切から最大 12 ヶ月、自動保存は受付終了から最大 7 ヶ月）。**オフボックスの本数を
増やすときは、告知も直すこと。**

### 提出どうしの類似（Dolos・ADR 0029・#203）

同じ課題の提出どうしで似ている組を、**担当教員にだけ**示す。不正かどうかの判定はしない。Dolos の CLI は、
digest で固定したイメージのまま、提出物と同じ sandbox（gVisor・ネットワークなし）で
実行する。結果は DB には書かず、`AIJUDGE_SIMILARITY_DIR` の下にファイルとして残す。

**運用機で 1 度だけ手で行う作業**は次のとおりである（どれもリポジトリの外のファイルを扱う）。

1. **報告の置き場所。** `aijudge.env` に `AIJUDGE_SIMILARITY_DIR=/work/aijudge/similarity` を
   追加し、所有者を `aijudge` にしてディレクトリを作る。**restic の環境ファイルには追加しない。**
   報告は全員のコードのコピーなので、バックアップしない（提出と一緒に削除する）
2. **イメージの許可。** `AIJUDGE_SANDBOX_IMAGES` に
   `aijudge_course_admin.code_similarity.DOLOS_IMAGE`（digest 付き）を追加する。追加しないと、
   「許可されていないイメージ」として `NOT_MEASURED` になる
3. **Dolos の画面。** `aijudge.env` に `AIJUDGE_DOLOS_WEB_DIR=/srv/aijudge/dolos-web` を追加し、
   `aijudge` ユーザで `aijudge-admin similarity install-viewer` を実行する（検査と同じイメージから
   静的ファイルを取り出して置く。見本のデータは置かない）。**`DOLOS_IMAGE` を更新したら、もう一度実行すること。**
   実行しないと、CLI と画面の版がずれる。画面のファイルが無くても入口のページは開き、類似度の高い組だけが表示される
4. `aijudge-review` を再起動する（env を読み直すため）

コンソールでは、左の帯の「提出の類似」で確認する（担当教員だけが見られ、閲覧は監査ログに残る）。Dolos の画面は、外部への通信を
禁止する CSP を付けて配信する（配布物は Google Fonts を読み込もうとするが、止めても表示は崩れない）。

**類似の検査は自動で実行される。** `aijudge-similarity.timer`（15 分ごと）が `aijudge.target` に含まれているので、
unit を配置すれば有効になる。検査するのは、受付終了（無ければ締切）の 1 時間後以降で（試験では、締切のあとにまず採点を実行するため）、**その課題の
採点（決定的・AI とも）が終わり**、入力が変わった課題だけである。元の提出が削除された報告は削除する。置き場所（1）が無いうちは、何もせずに終了する。
unit が書き込めるのは `/work/aijudge/similarity` だけなので、**別の場所に置くときは、drop-in で
`ReadWritePaths=` を追加する**（動画の drop-in と同じ）。ログは `journalctl -u aijudge-similarity` で確認する。

手で実行するときは、次のコマンドを使う。

```sh
aijudge-admin similarity run --course crs_… --unit ex01   # 問題セットの課題すべて
aijudge-admin similarity run --task tsk_… --force         # 入力が同じでも回し直す
```

実測（運用機・gVisor・CPU 1 つ）: C 60 件 6 秒、Python 150 件 21 秒、C 300 件 102 秒。
プロセス数 64・メモリ 512 MiB が必要である（プロセス数 32 では失敗する）。1 回に検査できる上限は 300 件である。

### 習熟度を確かめる砂場（#328）

習熟度は、「**知識要素の付いた課題に、学習者として提出し、採点が完了する**」まで、
1 件も記録されない。学期の初めはどの条件も満たされていないので、画面を開いても空である。
かといって、本番のコースに試しの提出を入れると、精度と一致度の標本に混ざってしまう。

そのための試験用のコース（砂場）を同梱してある。

```fish
# 1. 砂場用の科目プロファイルを運用の置き場所へ（測定を分ける鍵）
sudo -u aijudge cp /opt/aijudge/subjects/cs_sandbox_kc.yaml /srv/aijudge/subjects/

# 2. コースと課題（知識要素つき）を入れる
sudo -u aijudge sh -c 'set -a; . /srv/aijudge/config/aijudge.env; set +a; \
  exec /opt/aijudge/.venv/bin/aijudge-admin course apply \
  --file /opt/aijudge/subjects/sandbox/course.yaml'

# 3. 砂場用の学習者を作る（本物の学籍番号とまぎれない login にする）
sudo -u aijudge sh -c 'set -a; . /srv/aijudge/config/aijudge.env; set +a; \
  exec /opt/aijudge/.venv/bin/aijudge-admin staff \
  --login sandbox-a --name "砂場 A" --course <コース ID> --role learner'
```

あとはその利用者でログインし、`.c` を数回提出すれば、リレーがイベントを送り、習熟度が記録される。

**なぜ測定に混ざらないか。** 観測レコードは科目プロファイルごとのディレクトリに
蓄積され、`aijudge-eval --subject <名前>` はそのうち 1 つしか読まない
（`evalrunner.observations.iter_observations`）。砂場は `cs_sandbox_kc` という
別の名前を持つので、`cs_lang_c_intro` や `cs_network_python` の標本には 1 件も
入らない。**採点の設定は本番のコピー**なので、表示される図は本番と同じ規則で描かれる。

**お試しコース（demo）は、砂場の代わりにならない。** お試しコースへの提出は `is_trial` で、
習熟度からも意図的に除外されている（`skill_subscriber`・#108/#197）。教員が
自分の課題を試した提出が学習者の記録を変えないための仕組みなので、迂回しない。

**教員が自分で提出しても、習熟度は記録されない。** `is_trial` は、「提出者が学習者でないか、お試し
コースへの提出か」で決まる（`Submission.is_trial`）。砂場でも、**学習者として登録した
利用者**で提出すること。

砂場は、残しておいても本番の数字には影響しない。なお、提出があるので、`course delete` ではコースごと削除できない
（画面の「このコースを削除する」も同じく拒否する）。

### 既存の DB に入れるとき

**スキーマの更新は Alembic が管理する**（v0.10.0 から）。運用の DB では、
`--create-schema` を使わないこと。`Base.metadata.create_all` は**新しい表は作るが、
既存の表に列を追加しない**ので、気づかないうちに、一部だけが新しい DB ができてしまう。

```fish
uv run alembic upgrade head
```

`deploy.sh` がタグの checkout の直後にこのコマンドを実行するので、**タグでデプロイする
限り、手で実行する必要はない**。手で実行するのは、デプロイの経路の外にある DB
（開発機・検証環境）を更新するときだけである。

#### Alembic より前の DB を引き上げる

以下は、**v0.10.0 より前の DB を Alembic の管理下に置くときだけ**必要な手順で、
いまの運用の手順ではない。`alembic upgrade head` が成功する DB でこの手順を実行すると、
Alembic が管理している状態と食い違ってしまう。

ADR 0010 で `courses` に列が 1 つ増えているので、既にデータのある DB では手で追加する。

```sql
ALTER TABLE courses ADD COLUMN auto_finalize_after_hours DOUBLE PRECISION;
ALTER TABLE grading_jobs ADD COLUMN phase VARCHAR(32) DEFAULT 'deterministic';
```

猶予の単位は**分**に変わった（「締切の 10 分後に確定」を表せるようにするため）。
新しい列を追加して値を換算し、古い列を削除する。

```sql
ALTER TABLE courses ADD COLUMN auto_finalize_after_minutes INTEGER;
UPDATE courses SET auto_finalize_after_minutes = ROUND(auto_finalize_after_hours * 60)
  WHERE auto_finalize_after_hours IS NOT NULL;
ALTER TABLE courses DROP COLUMN auto_finalize_after_hours;
```

提出できるファイル形式をコースが持つようになったので、その列も追加する
（NULL なら組み込みの既定値を使う）。

```sql
ALTER TABLE courses ADD COLUMN upload_suffixes JSONB;
ALTER TABLE courses ADD COLUMN description TEXT;
ALTER TABLE courses ADD COLUMN grading_overrides JSONB;
ALTER TABLE courses ADD COLUMN rubric JSONB;
```

課題側で増えた項目（提出開始・課題ごとの猶予・課題ごとの提出形式・
課題キーの記録）は `tasks` / `task_versions` の JSON の中にあるので、
**列を追加する必要はない**。古い行は、既定値（空・NULL）として読める。

`finalizations` 表は、`--create-schema` で作られる。**開発機でデータを
捨ててよいなら**、DB を作り直す方が確実である。

```fish
docker compose down -v; docker compose up -d
uv run aijudge-web --create-schema
```

### 仕掛け忘れに気づく

`/manage` の課題一覧には、**未確定の件数**と段階（仮確定中／期限経過）が表示される。
**期限を過ぎたのに未確定の提出が残っていると、「要対応」**と表示される。原因は次のどれかである。

- 未対応の異議申立、要レビュー、採点失敗（＝一括確定か個別確認で処理する）
- `aijudge-finalize` が動いていない

**異議を受け付ける期間は、提出ごとに独立している。** 採点完了から数えるので、遅れて提出した
答案にも、同じ長さの期間がある（締切を起点にしていた頃は、締切 + n の直前に採点された
提出には、数分しか残らなかった）。
