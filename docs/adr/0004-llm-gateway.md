# ADR 0004: LLM はゲートウェイ越しに呼び、構造化出力を信用しない

- ステータス: 採用
- 日付: 2026-08-27
- 関連: 設計原則 P4, P5, P7, P8

## 背景

AI 採点を入れるにあたり、学内 GPU ホスト（slab-llm、ollama 0.32.13）の
実機で挙動を測った。前提にしていたことがいくつも崩れた。

| 確かめたこと | 実測結果 |
|---|---|
| JSON スキーマを渡せば従うか | **ランナー依存**。`gemma4:e4b`（llama.cpp）は従う。`qwen3.8:27b-mlx`（MLX）は `format` を黙って無視し、Markdown を返す |
| pydantic のスキーマをそのまま渡せるか | **不可**。`$defs` / `$ref` があると HTTP 400 `failed to parse grammar` |
| 値の制約は渡せるか | **不可**。`maxLength: 2000` で 400。値によって通ったり通らなかったりする |
| 任意フィールドは埋まるか | **埋まらない**。`evidence` を任意にしたら、根拠を rationale の文中に書きながら配列は空で返してきた |
| 大きいモデルほど良いか | **限らない**。27B は長い日本語プロンプトで構造化出力が安定せず、9.6GB の `gemma4:e4b` の方が実用的だった |
| 思考モデルの扱い | `think` を切らないと `reasoning` にトークンを使い切り、`content` が空で返る |

これらはどれも「アプリが LLM を直接呼ぶ」設計では各所に散らばる。

## 決定

**アプリは LLM プロバイダを直接呼ばない。** `packages/llm_gateway`（S6）を必ず経由する。
ゲートウェイの責務は 4 つ。

### 1. ポリシールーティング（P7）

プロンプトには機微度（`DataClass`）を必ず添える。`PERSONAL`（学習者の解答を
含む）をローカルでないプロバイダへ送ろうとしたら**送信前に例外**にする。
判定してから送るのでは意味がないので、プロバイダ呼び出しの前に落とす。

### 2. 構造化出力の保証（P4）

スキーマ制約は当てにしない。

- プロバイダに渡すスキーマは `simplify_schema()` で削る。`$ref` を展開し、
  構造に関わらないキーワード（`maxLength` 等）を落とす。
  **文法が保証するのは「形」だけ。値の制約は pydantic が担保する。**
- 応答は `extract_json()` でコードフェンス・前置き・後書きから本体を拾う。
  ここを緩くしないと、内容は正しいのに形式だけで落ちる。
- pydantic で検証し、失敗したら**具体的なエラーを添えて**再試行する。
  「やり直して」だけでは直らない。
- 規定回数で直らなければ例外にする。**それらしい点数を捏造しない。**

必須にしたいフィールドは既定値を与えない。既定があるとスキーマ上「任意」になり、
モデルは埋めてこない。`evidence` を必須にしたことで、根拠なしの判定は
再試行に回るようになった。

### 3. バージョンの記録（P8）

`PromptTemplate` は `name` と `version` を持つ。文面を変えたら必ず版を上げる。
結果には `prompt_id` と `model_id` が付き、パイプラインが `GradingContext` に
集約する。これが無いと、後から「この採点は何で出たのか」を追えない。

### 4. 自己一貫性（P5）

温度 0 で 1 回引いても「モデルが自信を持っているか」は分からない。
同じ問いを n 回サンプリング（初回のみ温度 0、以降は上げる）し、
多数決を採り、**一致割合をそのまま確信度にする**。
割れた採点は確信度が下がり、レビューポリシーが人間へ回す。

### 既定モデル

`gemma4:e4b`。実測で構造化出力が安定し、1 観点あたり 6〜22 秒で応答する。
より大きい `qwen3.8:27b-mlx` を選ばないのは上表のとおり。
`AIJUDGE_LLM_MODEL` / `AIJUDGE_LLM_BASE_URL` で上書きできる。

## 帰結

- プロバイダ固有の癖はすべて `provider.py` に閉じる。vLLM へ移るときは
  OpenAI 互換のプロバイダを 1 つ足すだけで、アプリ側は変わらない。
- 再試行があるぶん最悪ケースの所要時間は 3 倍になる。
  科目プロファイルの `timeout_seconds` を LLM 込みの値にした。
- 自己一貫性のサンプル数だけコストが線形に増える。既定は 3。
  PoC-1 で κ と所要時間を測って決め直す。
- `evals/test_llm_live.py` は既定では走らない（CI はネットワークに出ない）。
  `AIJUDGE_LIVE_LLM=1` で実機検証する。ゲートウェイと評価器の
  通常のテストは `ScriptedProvider` で完結する。

## 却下した案

**OpenAI 互換エンドポイント（`/v1/chat/completions`）を使う。** 移植性は高いが、
ollama では `think` の制御とスキーマ指定が確実に効かない。プロバイダ抽象が
あるので、移植性はそちらで担保する。

**制約デコードに任せて検証を省く。** 同じホストの同じ API でも
ランナーによって従わない。検証は必須。

**根拠のない判定も点数として受け入れる。** 説明可能性（P4）が崩れる。
教員にも学習者にも「なぜその点か」を示せなくなる。
