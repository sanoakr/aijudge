# ADR 0018: 採点のプロファイルは課題が決める

- ステータス: 採用
- 日付: 2026-09-11
- 関連: 設計原則 P1, P6, P8 / ADR 0002, ADR 0005 / #194, #195

## 背景

`TaskVersion.subject_profile` は最初から存在していた。だが**常にコースの値の
写しが入り、誰にも読まれていなかった。**

```python
# manage.py の課題を作る全経路
subject_profile = (course.subject_profile,)
# apps/studentweb/.../app.py の提出を受ける全経路
subject_profile = (course_obj.subject_profile,)
```

結果として、**1 つのコースに種類の違う課題を置けなかった。** レポートと
プログラムが混在する科目は実在するのに、2 つのコースに割るしかない。

問題セットで分ける案は成り立たない。`unit` は `Task` が持つただの文字列で、
まとめて表示するための名前である ── モデルとしての実体が無いので、プロファイル
を持たせる場所が無い。

## 決定

**採点のプロファイルは課題が決める。コースはその既定を決める。**

| | 何を決めるか |
|---|---|
| **コース**のプロファイル | 語彙（`kc_namespaces`）と、新しい課題の既定 |
| **課題**のプロファイル | 採点（どの評価器がどの順で走るか） |

ADR 0002 が「科目は宣言であってコードではない」と定め、プロファイルを評価器の
指名と位置づけている。**評価器の指名は「何を採点するか」で決まる**のだから、
課題に付くのが筋である。

`TaskSpec.subject_profile` は `None` を既定とし、そのときコースの値を使う。
**既存の課題はすべて `None` なので、これまでと同じ値で採点される** ── 移行の
手順は要らない。同じ形を `aggregation` が先に採っている（課題ごとの例外、
既定はコース）。

### KC の名前空間はコース側に残す

知識要素はコースをまたいで共有される語彙であり（P6）、課題ごとに変わるもの
ではない。`allowed_namespaces(load_profile(course.subject_profile))` はそのまま。

### 観測レコードの投影も課題側から取る

再採点と観測の投影がコース側を見ていた（`refresh_observations`）。ここが
食い違うと、**観測レコードの `subject_profile` が採点時のものとずれ、測定の
標本が黙って混ざる**（ADR 0005）。採点したときと同じ値で投影する。

### 盲検の抽出率はコース側に残す

抽出率はレビュー方針の一部なので課題側に見えるが、**課題ごとに変わると
コース全体の κ の標本設計が課題ごとにばらつく**（ADR 0005）。標本の設計は
コース単位の話なので、ここは動かさない。

## やらないこと

- **コースのプロファイルを廃止する。** 語彙と既定はコース単位の概念である。
- **問題セットにプロファイルを持たせる。** `unit` には実体が無い。
- **既存の課題を移行する。** `None` が既定なので、何もしなくても同じ値になる。

## 帰結

- 1 つのコースに、画像・プログラム・レポートの課題を同居させられる（#194 の前提）。
- 課題を訂正して版を上げても、その課題のプロファイルは保たれる ── ここが
  落ちると、直した瞬間にコースの既定へ戻り、**訂正するまでは正しく動いていた
  ぶん原因が分かりにくい**。テストで固定した。
- ワーカーは `job.subject_profile` を見ているので、そこから先は変更が要らない。
