# ADR 0028: 1 つの DB・1 つのトランザクションで書き、イベントは遅れてよいことだけに使う

- ステータス: 採用（2026-09-28、段階的な立て直しの段階 5）
- 日付: 2026-09-28
- 関連: 設計原則 P2, P8, P9 / ADR 0001, 0002, 0007 / `docs/design/staged-refactor.md`・
  `docs/design/manage-split-map.md` / issue #437・#438
- 改める決定: ADR 0001 の「サブシステム間の連携はイベントと公開 API に限る」
  「スキーマはサブシステムごとに分ける」

## 背景

ADR 0001 は、モジュラーモノリスの境界を import-linter で強制し、サブシステム
どうしは**イベントだけ**で結び、DB は 1 つでも**スキーマはサブシステムごとに分ける**
とした。設計方針 §2.3 は 5 つのイベント（提出 → 採点 → 習熟度 → 証明・作問）で
全体をつなぐ図を描いた。

1 か月運用して、実装はそうならなかった（2026-09-26 の設計レビュー・#437）。

- **採点の起動はイベントではなくジョブの表**（`grading_jobs`）になった。提出と同じ
  トランザクションで積み、冪等・リトライ・再採点・試験の一括採点の待機を持つ
  必要があり、イベントの配信よりジョブの表のほうが素直だった
- **コース運営の操作は複数のサブシステムに同時に書く。** 課題を保存すると、課題と
  版（作問 S2）、Q-matrix（習熟度 S7 が読む）、受付の設定が 1 回の操作で変わる。
  コースを複製・削除すると、名簿（S1）・課題・提出（S3）に及ぶ。これをイベントで
  分けると、途中で落ちたときに「課題はあるが Q-matrix が無い」が生まれる
- その結果、全リポジトリを 1 つのトランザクションに載せる UnitOfWork（13 の
  リポジトリ・`aijudge_unit_of_work`）と、それを使う業務の層（`aijudge_course_admin`）が
  できた（段階 2・3）
- **DB のスキーマは 1 つ**のまま。他のサブシステムの表を直接読まないことは、スキーマ
  ではなく保存層のメソッドと契約（`apps-do-not-read-tables`）で守っている
- 5 つのイベントのうち実際に流れているのは `GradingCompleted` → 習熟度（S7）だけで、
  `TaskPublished`・`CredentialIssued` は一度も作られなかった（段階 5-2 で消した）

ADR 0001 の文面と実装が食い違ったままだと、次に読む人は「イベントでつなぐはずなのに
直接書いている」を違反と読むか、文面を信じて本当の違反を見逃す。

## 決定

**サブシステム間の書き込みは、同じ DB・同じトランザクションで行ってよい。**
イベントは**後で・別のプロセスで起きてよいこと**だけに使う。

層の形は次のとおりで、どれも import-linter の契約で強制する（破れば CI が落ちる）。

```
apps/*（合成ルート）                  web・console・worker・relay・admin CLI など
  │   アプリどうしは import しない                  apps-are-independent
  ▼
aijudge_course_admin（業務の層）       コース運営の操作。複数のサブシステムに 1 回で書く
aijudge_unit_of_work（束ねる型）       全リポジトリを 1 つのトランザクションに
aijudge_webapp（Web の共有部品）
  │   使ってよいのはアプリだけ          unit-of-work-is-for-the-apps・webapp-is-for-the-apps
  ▼
サブシステム（authoring・grading・llm_gateway・analytics・submission・identity・skill・ide）
  │   互いに import しない                           subsystems-are-independent
  │   保存先の実装もアプリも知らない                 subsystems-do-not-know-the-store 他
  ▼
aijudge_core（ドメインモデルとイベント。I/O なし）   core-is-independent・core-has-no-io

aijudge_persistence（保存層）          全リポジトリの SQL 実装。アプリだけが組み立てる
                                       アプリは表の定義を直接 import しない  apps-do-not-read-tables
```

- **サブシステムどうしは今も直接 import しない。** 変わったのは「複数のサブシステムに
  またがる書き込みを誰がするか」で、それはサブシステムではなく上の層（業務の層と
  アプリ）がする。サブシステムの独立（1 つを消しても他が動く・P2）はそのまま
- **イベントを使うのは、遅れてよく、別のプロセスで起きてよいこと。** いまは採点結果 →
  習熟度（`GradingCompleted`・`aijudge-relay`）だけ。outbox は採点結果と同じ
  トランザクションに書くので、「採点はあるのにイベントが無い」は起きない
- **表を読むのは保存層だけ。** スキーマは分けない ── 分けても 1 つの DB・1 つの
  トランザクションで書く以上、守りたいもの（他のサブシステムの表の形に依存しない）は
  保存層のメソッドと契約で守れている

## 根拠

- **1 回の操作が中途半端に残らないこと**のほうが、サブシステムを別プロセスに
  切り出せることより、いまの運用で重い。課題の保存が半分だけ成功すると、学習者に
  出ている課題の採点規則と Q-matrix が食い違い、成績と習熟度が静かにずれる（P8）
- 切り出しは今も機械的にできる。サブシステムどうしの import は無く、書き込みの束ねは
  上の層に集まっている。切り出すときは、その層の操作を「イベント＋補償」に置き換える
  作業になる ── 置き換える場所が 1 か所に集まっていること自体が、ADR 0001 の言う
  「切り出しコストの低さ」である
- 使われないイベントの定義は、読む人に「この経路が動いている」と誤解させる。
  流れているものだけを定義に残す

## 帰結

- サブシステム間の書き込みを足すときは、**サブシステムではなく業務の層かアプリに書く**。
  サブシステムの中に他のサブシステムを呼ぶ処理を書こうとした時点で、契約が落ちる
- 新しいイベントは**購読者と一緒に**足す。発行だけ先に書かない（`TaskPublished` の轍）
- 習熟度（S7）を止めても採点は完了する ── イベントが溜まるだけで、リレーが戻れば
  追いつく（購読側は冪等）
- ADR 0001 の該当箇所（イベントに限る・スキーマを分ける）はこの ADR が改める。
  ADR 0001 のそれ以外（1 デプロイ単位・境界を機械で強制・core は何にも依存しない）は
  そのまま

## 却下した案

**ADR 0001 どおりにイベントで分け直す。** 課題の保存やコースの複製を「イベント＋
補償トランザクション」に作り直すことになる。別プロセスに切り出す予定が無いのに
分散システムの失敗の形（半分だけ反映された状態）を持ち込む。学期中の運用で
得るものが無い。

**スキーマをサブシステムごとに分ける。** 1 つの DB・1 つのトランザクションで書く
以上、スキーマを分けても守れるものが増えない。守りたいのは「他のサブシステムの表の
形に依存しない」ことで、それは保存層と契約で既に守れている。
