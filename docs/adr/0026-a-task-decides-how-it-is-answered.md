# ADR 0026: 答え方は課題が持つ ── エディタからの提出も同じ入口を通る

- ステータス: 提案（`feat/online-coding-test`。段階 3 の負荷試験のあとで採否を決める）
- 日付: 2026-09-24
- 関連: 設計原則 P1, P2, P8 / ADR 0002, 0013, 0018, 0019, 0025 / #119, #146, #370 /
  `docs/design/online-coding-test.md` §2・§4・§9

## 背景

学習者の答え方は、これまで**ファイルを選んで出す**の 1 つだった。ブラウザ IDE で
「エディタで書いてその場で出す」を足すにあたって、次の 3 つを決める必要があった。

1. どの課題をエディタで解かせるかを、どこに持たせるか
2. エディタからの提出を、採点側にどう見せるか
3. 受付の終わりに書きかけのまま時間切れになった学習者を、どう扱うか

用途は試験と普段の課題の両方である。演習でも、学習者の手元の環境が壊れたときの
逃げ道になる（2026-09-24 決定）。

## 決定

### 1. `Task.answer_mode` ── 既定は `upload`

```python
class AnswerMode(StrEnum):
    UPLOAD = "upload"  # 既存。ファイルを選んで出す
    EDITOR = "editor"  # ブラウザのエディタで書いて出す
```

- 値は `tasks.document` に入るので**列は増えない**。既存の課題はすべて `upload` で、
  見え方も数え方もこれまでと同じ
- `campus_only` と同じく、**課題が持つが、決めるのは問題セット単位**である。
  コンソールの画面もそう作る。問題セット（`unit`）には実体が無いので（ADR 0018）、
  新しいエンティティは作らない
- 補完の切／入も同じ形で持つ（試験の既定は切、演習の既定は入）

**`editor` にできるのは、有効プロファイルの `deterministic` に `code_test_runner` が
あり、言語が `aijudge_toolchain.LANGUAGES` にある課題だけ。** 検査は保存時に
サーバ側で行う ── 画面で灰色にするだけでは境界にならない（#146）。

`save_task` の作り直しで値を落とさないよう、`answer_mode` を
`test_every_field_of_a_task_is_accounted_for` の一覧に加える（ADR 0025 の帰結。
`withdrawn` と `campus_only` で同じ取りこぼしが起きた）。

「試験」という種別は作らない。ADR 0025 の §3 と同じく、値は独立に持つ。

### 2. エディタからの提出は `SubmissionService.accept()` を通る

- エディタの内容から `IncomingFile(filename=<言語の source_name>, kind=CODE, ...)` を
  作り、**既存の `accept()` に渡す**。同じ内容の再提出は既存どおり同じ提出に畳まれる
- **採点側は提出の出どころを知らない。** `packages/core` の `Submission`・
  `packages/grading`・評価器は 0 行の変更とし、`aijudge_grading` と `evaluators/*` は
  `aijudge_ide` を import しない（`grading-does-not-know-ide` 契約）
- IDE との対応は別の表 `ide_submission_links(submission_id, ide_session_id,
  content_hash, origin)` に置く。`Submission` には何も足さない
- 関門（学内限定・受付期間・役割・`may_see`）は `/submit` と**同じ関数**を呼ぶ。
  写して持つと、写すときに判定が落ちる（#119、#370 で再発）

ADR 0002 が「科目の追加がエンジンを 0 行しか変えない」を設計の受け入れ試験に
したのと同じく、**答え方の追加が採点を 0 行しか変えない**ことを、このブランチの
受け入れ試験にする。

### 3. 受付の終わりに、サーバが自動保存の最新を提出する

- 対象は、一度も提出していないタブと、最後の提出のあとに書き換えたタブ
- **ブラウザ主導にしない。** 通信が切れた、PC がスリープした学習者の分が漏れる
- 時刻で動く処理として `aijudge-finalize` と同じ型で置き、`ide_submission_links.origin`
  に「受付終了時の自動提出」と印を付ける。本人が押した提出と区別して残す
- **成績は最高得点の提出が採用される**（同点なら後の提出）ので、本人が出すつもりの
  なかった版が自動で出ても、成績は下がらない
- 締切・受付の判定は既存のまま。受付を過ぎてから届いた自動保存は採用しない。
  遅延減点（ADR 0013）もそのまま効く

制限時間は**全員共通の時間枠**とし、既存の課題の日程（`opens_at`・`accepts_until`）を
そのまま使う。学習者ごとの「開始から N 分」は持たない ── 締切を学習者ごとに
求めることになり、ADR 0025 が追試を別の課題にしたのと同じ理由で、受付判定・遅延減点・
自動確定・保存期間のすべてに手が入る。

## やらないこと

- **対話的な標準入力。** stdin は実行前に一括で渡す。`code_test_runner` と同じ形で、
  sandbox に手を入れずに済む。当面の言語は C と Python
- **エディタ専用の採点。** 採点は `upload` の課題と同じ評価器が、同じ提出に対して行う

## 帰結

- `answer_mode=upload` の課題には何も起きない。新しい画面は `editor` の課題にしか
  出ず、既存の学生画面・提出・採点のテストは**無変更で**通ることを段階 2 の完了条件にする
- 自動保存の最後の更新から受付の終わりまで（最大 10 秒）は失われうる。受付終了の
  直前にクライアントが即時に自動保存を送ることで縮めるが、ゼロにはならない
- 1 つの問題セットの中で `upload` と `editor` が混ざってもよい。IDE の画面には
  `editor` の課題だけがタブとして並ぶ
