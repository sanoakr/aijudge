# ADR 0010: 成績の確定は「教員が読んだ」ことではない

- ステータス: 採用
- 日付: 2026-08-28
- 関連: 設計原則 P4, P5, P8 / ADR 0002, ADR 0005, ADR 0009

## 背景

ADR 0009 で、教員の待ち行列を**学習者からの異議申立だけ**にした。これは
正しい判断だった ── 受講 91 名 × 課題十数回の全提出を並べても、教員は何から
見ればよいか分からない。

しかしその結果、**依頼が出なかった提出が永久に未確定で残る**ようになった。
学期末に成績が閉じない。異議申立は少数で、大半の提出は誰も何も言わないまま
「担当教員の確認を経て確定します」と表示され続ける。

閉じる導線が要る。そこで問題になったのが、確定を何として記録するかである。

これまで**確定 = `HumanReview` の存在**だった。この記録は「教員が段階を直したか」
（`agreed`）を持っており、AI と人間の判定の差 ── つまり一致度の測定データ ──
の一部である（ADR 0005）。

ここに一括確定・自動確定を同じ記録として書くと、**誰も読んでいない提出に
「教員が AI の判定に同意した」という記録が残る。** 91 名 × 十数課題では大半が
そうなるので、その記録から測る一致度は実力より高い数字になる。ADR 0005 が
「測定は自分に有利な数字を作ってはならない」と決めた、まさにその形である。

## 決定

### 1. `Finalization` を `HumanReview` と別の記録にする

| 記録 | 意味 | 一致度の証拠か |
|---|---|---|
| `HumanReview` | 教員が**その 1 件を読んで**下した判断 | **なる** |
| `Finalization` | 成績が確定したという事実。出所を持つ | ならない |

`FinalizationSource` は 3 値。

- `instructor_review` — 個別レビューからの確定。`review_id` と `actor_id` を持つ
- `instructor_bulk` — 課題単位の一括確定。`actor_id` を持ち、`review_id` は持たない
- `deadline_elapsed` — 締切 + n 時間の自動確定。**`actor_id` も `review_id` も持たない**

自動確定に `actor_id` を持たせないのは型で示すためである。誰かの ID を借りて
書くと、あとから「その教員が確定した」と読めてしまう。

この分離により、測定側のコードは**一行も変えずに正しいまま**である
（`find_review_for_run` が引くものが変わらない）。一括確定・自動確定した提出は
測定側から見て「まだ教員が読んでいない」ままで、これは実態のとおりである。

### 2. 一括確定 — 教員が課題ごとに閉じる

`/manage` の課題一覧から、未確定分をまとめて確定する。**根拠説明を必須にする**
（`MIN_JUSTIFICATION_LENGTH`）。学習者にそのまま表示される。個別に読んでいない
成績を確定させる操作なので、何を根拠にそうしたのかが残らないと学習者は何も
分からない（設計原則 P4 を一括操作にも適用する）。

`review_required` の提出も含める。教員が根拠を書いて明示的に責任を取る操作
だからで、含めなければコンパイルエラーや合否境界の提出だけが永久に残る。

**未対応の異議申立は確定しない。** 学習者は「人に見てほしい」と言っている。
そこへ一括操作が確定を書き込むと、ADR 0009 で作った導線そのものが無意味になる。

### 3. 自動確定 — 締切で仮確定し、猶予のあいだ異議を受け付ける

締切そのもので確定させず、**2 段にする。**

```
採点完了 ──→ [暫定]      AI の判定。確定の予定はまだ告げない
   締切 ──→ [仮確定]     「MM/DD HH:MM に確定します」と学習者に示す。異議を受け付ける
締切+n ──→ [確定]        AI の判定のまま確定する
             └→ 未対応の異議申立があるものは確定せず、教員の待ち行列に残る
```

**仮確定の段階を置くのは、学習者に期限を示すためである。** 締切 + n で静かに
確定させると、確定したこと自体が事後にしか分からない。ADR 0009 が避けたかった
「一方的な通告」と同じ形になる。逆に、期限を示した以上そこで締め切ってよい ──
**確定後は再確認の依頼を受け付けない**（画面には「申し出は担当教員へ」と出す）。
締め切らなければ、教員の待ち行列は学期末まで新しい依頼を受け続ける。

`GradeWindow` は**保存しない。導出する**（`Task.due_at` と
`Course.auto_finalize_after_hours` から計算できる）。記録に持つと、締切を
直したときに古い値が残る ── 締切は学期中に動く。

**依頼の締め切りは時刻で決め、確定の有無では決めない。** 自動確定は定期実行
なので、期限と実際の確定の間に隙がある。そこで出された依頼は自動確定を恒久的に
止め、誰も気づかないまま学期末まで残る。

猶予を設定していないコースでは窓は開いたままである。確定の予定が無いのに
「いつ確定する」とは言えず、期限を示していない以上締め切ることもできない。

自動確定は人が関与しないので、条件は一括確定より厳しい。

- `routing == review_required` は対象外。レビュー方針が「人が見るべき」と判定
  したものを、人を通さずに成績にしない（設計原則 P5）
- 未採点の観点があるものも対象外。誰も見ていない観点が成績に入る
- 未対応の異議申立があるものも対象外

**既定は「自動確定しない」（`None`）。** 教員が明示的に値を入れて初めて始まる。
既定で自動確定させると、設定を知らない教員のコースで成績が勝手に閉じる。

### 4. 猶予はコースに持つ。科目プロファイルには置かない

`subjects/*.yaml` はブラウザから編集させないと決めてある（ADR 0002）。あれは
評価器の指名とタイムアウトを持つ採点の設定で、1 人の操作で全員の採点を止め
られるからコードと同じ扱いにしている。

猶予は締切（`Task.due_at`）と同じ性質の運用値である ── 教員が学期中に決め、
成績に直接効く。だから置き場所も権限も締切に揃える（DB、`/manage`、
INSTRUCTOR 以上。**TA には開けない**）。

`0` は拒否する。締切と同時に確定させると、締切直前の提出が採点前に確定しうる。

### 5. 走らせるのは `aijudge-finalize`。採点ワーカーには相乗りさせない

    uv run aijudge-finalize --once      # cron 向き
    uv run aijudge-finalize             # 常駐（既定 15 分ごと）

確定はレビュー側の判断で、採点側がそれを知る必要はない（`.importlinter` の
「採点とレビュー」の分離）。混ぜると、採点を止めたいときに確定も止まる。

**設定だけでは動かない。** 仕掛け忘れに気づけるよう、`/manage` の課題一覧に
未確定件数と自動確定の予定時刻を出す。件数が減らなければ何かが動いていない。

### 6. 学習者には確定の出所を示す

「確定済み」だけにすると、締切後に機械が確定した成績が「担当教員が確認しました」
として学習者に出る。これは嘘である。誰も読んでいないという事実が、異議を
申し立てるかどうかの判断を変える。

- `instructor_review` → 「担当教員が確認した成績です」
- `instructor_bulk` / `deadline_elapsed` → 「個別の確認は経ていません」と明記する

確定後は依頼の導線を閉じるが、**それは期限を示してあるからである**（§3）。
「申し出は担当教員に直接お願いします」と出し、画面の外に経路を残す。

### 7. 教員が読むのは確定より後でもよい

自動確定した成績に学習者が異議を申し立て、教員が読む ── この経路は実在する。
そのとき確定の記録は最初のもの（自動確定）を残し、`HumanReview` を追記する
（追記のみ、P8）。学習者に見せる顔は教員が読んだ方を採る。後から人が読んだ
のなら、それがその成績について言える一番強いことだからである。

## 帰結

- **`HumanReview` の意味が狭くなった。** 「成績の確定」から「教員が 1 件を
  読んだ判断」へ。この記録の存在で確定を判定していた箇所（学習者向け表示、
  `pending_for_course`）は `Finalization` に移した
- **一致度の標本は減る。** 大半の提出は誰も読まないまま確定するので、`HumanReview`
  が付くのは異議申立と blind 抽出の分だけになる。これは測定の弱体化ではなく、
  もともとその通りだったものが記録に正しく現れるようになったということである。
  Phase 1 の κ は blind 抽出（`measurement.blind_sample_rate`）で稼ぐ
- **確定済みの提出を再確定はできない。** 1 採点につき `Finalization` は 1 つ。
  やり直しは再採点から（新しい `GradingRun` が生まれる）
- **締切後に採点された提出（遅れ提出）は異議の窓が短い。** 窓は課題の締切から
  数えるので、締切 + n の直前に採点された提出には数分しか残らない。遅れ提出を
  受け付ける運用では猶予を長めに取る。提出ごとに窓を数える設計にしなかったのは、
  そうすると課題の確定時刻が提出ごとにばらけ、教員が「いつ閉じるか」を言えなく
  なるため
- `finalizations` テーブルが増えた。`courses` に列が 1 つ増えた
