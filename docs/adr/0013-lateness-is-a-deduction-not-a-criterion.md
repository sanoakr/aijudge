# ADR 0013: 評価は遅延と独立に行い、遅延は評価の結果に対する減点として持つ

- ステータス: 採用
- 日付: 2026-08-29
- 関連: 設計方針 §4, §9.2 Phase 3 / 設計原則 P3, P4, P5, P6, P8 / ADR 0002, ADR 0005, ADR 0010, ADR 0012

## 背景

`submission_compliance`（ADR 0012 で採点の経路に入れた決定的評価器）は、
提出の有無・ファイル名・提出形式に加えて**遅延も観点の段として数えて**いた。
教員の採点表がそうなっていたからである ── 2023 年度の備考欄には `遅延14h` と
`ファイル名` があり、どちらも体裁が満点から半分に落ちていた。

写した結果、観点が 2 つのことを同時に表すようになった。

- **提出の遵守**（出したか、名前と形式は規則どおりか）
- **事務上の遅れ**（締切に間に合ったか）

これを 1 つの段階に畳むと、3 つ壊れる。

1. **観点の一致度（κ）が混合を測る。** 「教員と AI がこの観点でどれだけ
   一致するか」が、読解の一致と事務記録の一致の混ざったものになる。
   どちらが効いているのか分解できない（ADR 0005）。
2. **教員が減点を免除できない。** 免除とは観点の段階を上げることになり、
   その修正は `HumanReview.adjusted_levels` に載る ── つまり
   **「教員が AI の判定に反対した」という記録になる。** 一致度が実力より
   低く出る。ADR 0010 が `Finalization` と `HumanReview` を分けて塞いだ穴の、
   符号が逆の同型である。
3. **習熟度に遅延が混ざる。** `GradingCompleted` は S7 が読む。何ができるかと、
   いつ出したかは別の事実である（P6）。

しかも遅延を評価器で見るには締切が要るが、評価器に届くのは `TaskVersion` と
`Submission` だけで `Task` は入っていない。`evaluator_options` から渡す案は、
課題ごとに違う値を科目全体の設定に書くことになって成立しない。**配管が無いのは
偶然ではなく、評価器が締切を知るべきでないことの現れだった。**

## 決定

**採点は遅延を知らない。** 評価器も採点エンジンも締切を見ない。遅延は
**評価が終わったあとに、評価の外から当てる減点**として持つ。

```
評価（遅延を知らない）              減点（評価を知らない）
  GradingPipeline                    Course.late_penalty_steps × Task.due_at
        │                                        │
        └──→ CriterionScore ─┬───────────────────┘
                             ↓
              final_score(run, task_version, review)
                評価点 → 教員の修正 → 減点（免除なら 0）→ [0,1] に丸める
```

### 1. 規則は `Course` が持つ（科目プロファイルではない）

`Course.late_penalty_steps` ── `{after_hours, ratio}` の段を並べたもの。
超過時間が届いた最も上の段が当たる。空なら遅延を見ない。

置き場所を `Course.auto_finalize_after_hours` に揃えるのは、**同じ性質の値**
だからである（あちらの docstring が既に理由を書いている）── 成績に直接効き、
教員が学期中に決める運用値。科目プロファイル（`subjects/*.yaml`）は評価器の
指名とタイムアウトを持つ採点の設定で、ブラウザから編集させないものと決めて
ある（ADR 0002）。遅延の規則はそちらではない。

**規則が無いコースでは減点しない。** 「規則を置き忘れた」と「規則を適用して
0 だった」は違う ── 前者では `LatePenalty` を作らないので、学習者の画面に
「遅延の減点」の欄自体が出ない。出すと、教員が決めていない罰則を機械が
課したように読める。

### 2. 減点は `GradingRun` に記録する。表示のたびに計算し直さない

`GradingRun.penalty: LatePenalty | None` を採点時に確定させる（P8）。規則は
教員が学期の途中で変えうるので、表示のたびに計算する作りにすると、規則を
変えた瞬間に**過去の成績が黙って動く。**

`LatePenalty` は割合だけでなく**超過時間・締切・提出時刻・当たった段の説明**を
持つ。学習者の画面に `評価 78% − 遅延 30 ポイント = 48%` と内訳を出し、
異議申立の対象を「内容」と「遅れたこと」に分けられるようにするためである（P4）。

### 3. 減点は総合点比から差し引く（掛けない）

`最終 = clamp(評価 − 減点, 0, 1)`。「減点」という言葉どおりで、学習者に最も
説明しやすい。下限は 0 で止める。

### 4. 教員は免除できる

`HumanReview.penalty_waived`。**覆せない減点を作らない**（P5）── 病欠や事前の
延長の合意はシステムの外で起きるので、規則の側では拾えない。

**免除は `agreed` を偽にしない。** 免除は AI の判定への不同意ではなく事務上の
措置である。含めると一致度が「教員が AI に反対した」と読める（上の 2 と同じ理由）。

### 5. 減点だけで合否が入れ替わる件は自動で閉じない

`penalty_crosses_boundary()` ── 評価としては及第だったものが遅延で不可になる
提出は `review_required` に上げる。遅延の事実に迷いは無いが、**免除するか
どうかの判断は人にしか無い**（P5）。振り分けの他の条件（確信度・評価器間の
不一致）は評価だけで決まり、減点は関与しない。

### 6. 総合点を作る場所は 1 つだけにする

`aijudge_core.final_score()`。以前は `apps/studentweb/visibility.py` の中に
あったが、そこに減点を書き足すと**教員が段階を直したときに減点が落ちる経路**が
できる。コアに上げ、学習者の画面と教員コンソールが同じ関数を通る。

## 帰結

**測定は影響を受けない。** 観測レコード（`Observation`）が持つのは観点別の
段階だけで、総合点も減点も入っていない。減点を外に出したことで、
**観点の κ は読解の一致だけを測るようになった。**

**`packages/grading` は無変更。** 採点エンジンは締切も減点も知らない。
減点を当てるのは採点ワーカー ── S3（提出・締切）と S5（採点）を束ねる
唯一の場所である（ADR 0001）。

**`packages/core` は変わる**（`LatePenalty` / `final_score` / `Course` の段）。
これは**科目の追加ではなく全科目に効くコース運用の機能**なので、Phase 3 の
「新科目追加で core 50 行未満」の計測には算入しない。算入すると指標の意味が
変わる。

**2023 年度の測定値は据え置く。** `submission_compliance` の完全一致 71.4% は
**もともと遅延を見ずに出した値**である（ハーネスは締切を渡していない）。
遅延を外したことで数字は動かない。ただし照合先の教員の体裁点には遅延が
畳み込まれているので、**残る不一致 8 件のうちいくらかは、いま減点として
外に出したぶんである。** 分解には提出時刻が要るが、評価用のデータには
入っていない。

## 却下した案

**評価器に締切を渡す口を作る（課題単位の `evaluator_options`）。** 配管の
問題として直せば動くが、直した先で観点が 2 つのことを表す状態は残る。
上の 3 つの破れはどれも配管ではなく**混ぜたこと自体**から出ている。

**減点を掛け算にする。** よくできた提出ほど減点の絶対量が大きくなる。
遅れたという 1 つの事実に対する罰が内容の出来に比例するのは説明しにくい。

**減点後の点で振り分けも合否も決める（減点前で判定する案の逆）。** 採らない。
ただし**合否が入れ替わる件だけ**は例外としてレビューに回す（上の 5）──
影響が最大で、件数は少ない。
