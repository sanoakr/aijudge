# ADR 0007: Phase 0 を初期運用の必須機能に限り、採点性能の測定は「可能だが必須でない」に置く

- ステータス: 採用
- 日付: 2026-08-28
- 関連: 設計原則 P2, P5, P8 / ADR 0002, ADR 0005

## 背景

構築計画を PoC-0〜PoC-5 として並べていた（設計方針 §09 の旧版）。これは
アーキテクチャ仮説の検証単位としては機能したが、**「どこまでできれば授業で
使い始められるのか」を示していない**。PoC-1 の合格基準に κ ≥ 0.65 が入って
いるため、読み方によっては「教員採点との一致度を測り終えるまで運用を
始められない」ことになる。

さらに実装が実際にその読み方になっていた。レビューコンソールは
`submit_blind()` で教員の blind 採点を保存した**あとに**初めて採点を走らせ、
`reveal` は blind 採点が無ければ入力画面へ戻す。つまり:

> **測定用データの入力が、AI 採点そのものの前提条件になっていた。**

測定は採点の質を知るための手段であって、採点の一部ではない。手段が目的の
前提条件になっているのは設計の誤りである。

## 決定

### 1. Phase 0 は「初期運用に必須のもの」だけ

Phase 0 の定義は「これが無いと授業で使えない」。含まれるのは提出・隔離実行・
採点（決定的＋AI）・教員レビューによる確定・フィードバック返却、および
それを支える認証と永続化。

**Phase 1 以降に分離するもの**（初期運用の必須ではないもの）:

- 数学（CAS・数式同値）とレポートの採点 — Evaluator プラグインと科目 YAML の追加で足りる（ADR 0002 の検証項目そのもの）
- 手書き画像提出と OCR/VLM 書き起こし（S11）
- AI 作問（S2）、KC 体系・スキル推定（S7）、ポートフォリオ（S8）
- **採点性能の指標計算とゲート判定（S9）**
- 反復採点による一貫性の実験
- Integrity（S10）、マルチテナント・LTI・スケール

### 2. 測定は「記録」と「計算」に分け、前者だけ Phase 0 に置く

この 2 つは性質が違う。

| | Phase | 理由 |
|---|---|---|
| **記録**（blind 採点・確定採点・観測レコード） | **Phase 0** | 後から再構成できない。AI の判定を見た教員の採点は、遡って blind にできない |
| **計算**（κ / QWK / ゲート判定） | **Phase 1** | 記録が揃っていれば、いつでも後から計算できる |

「測定できるように設計する」は前者、「測定を必須機能にしない」は後者を指す。

### 3. 採点は測定を知らない

依存の向きを一方向に固定する。

```
採点パイプライン ──→ GradingRun（不変）
                            ↓ 読むだけ
レビュー ──────────→ FinalDecision
                            ↓ 読むだけ（app 層の購読者）
                      Observation（1 提出 × 1 観点）
                            ↓ 読むだけ
                  analytics（κ / QWK / ゲート・純関数）
```

機械で確認できる形にする。**`packages/analytics` と `apps/evalrunner` を
削除しても採点は動く。** これが「必須機能でない」の定義である。
`.importlinter` にこの向きを契約として書く。

観測レコードの書き出しは app 層の購読者が行う。書き出しが失敗しても採点は
続行する（S6 停止時と同じ劣化動作の扱い、P2）。

### 4. 採点の起動をレビューから切り離す

採点は**提出時**に走る。設計方針 §10 の「AI 評価は非同期で『あとから届く』
UX を最初から前提にする」に合わせる。

blind 画面は、**既に存在する採点結果を隠すだけ**の画面になる。順序は
教員の目に対してのみ保証され、採点の実行順序には関与しない。

```
提出 → 採点（決定的 → AI・非同期）→ 待ち行列
                                      ├─ 通常レビュー: 結果を見て確定
                                      └─ blind レビュー: 先に付ける → 開示 → 確定
```

### 5. blind 採点は全件必須ではなく抽出

全件 blind は、レビュー 1 件ごとに 2 段階の入力を強制する。これは測定コストを
日常業務に転嫁したもので、「測定を必須にしない」と実質的に両立しない。

抽出率を科目プロファイルに宣言し、待ち行列が対象を指定する。教員の任意選択に
しないのは、選択バイアス（難しい提出だけ blind にする等）が入ると κ が
その分だけ意味を失うため。抽出率は、PoC-1 の基準（1 観点あたり 30 件）に
到達する提出数から逆算して決める。

## 帰結

- レビューコンソールの改修が必要になる（`submit_blind()` が採点を起動している箇所、
  および `reveal` の強制リダイレクト）。
- 測定は再採点を行わなくなる。`apps/evalrunner` の `run_evaluation()` は
  記録済み観測を読む関数になり、`pipeline.run()` を呼ばない。
  これに伴い ADR 0005 の「測定は採点し直す場合がある」という前提が消える。
- `--repeats`（同一提出の反復採点）は測定ではなく実験なので、別ツールに切り出す。
- 観点の段階（levels）は観測レコードに焼き込む。課題定義を読まずに QWK の
  重み行列が決まるようにする（現状は課題定義から引けなければ `(0,1,2,3)` に
  黙って落ちており、段階数が違えば誤った QWK が出る）。
- 見逃し率の定義を `FinalDecision.changed_after_seeing_ai`（AI を見た後に
  教員が変えたか）に一本化する。現状は「blind 採点と機械の段階の差」で
  計算しており、これは不一致率であって見逃しではない。
- `evals/gates.yaml` はプロジェクトの品質基準として CI に残す。採点運用の
  経路には入らない。データが無ければ exit 2（測定不能）で CI を落とさない
  現在の挙動をそのまま使う。

## 却下した案

**測定を最初から作らない。** blind 採点は遡って取得できない。運用を始めて
から「精度を測りたい」となった時点で、それまでの採点データは正解データに
ならない。器だけは初期から要る。

**PoC-1 の合格基準を運用開始条件のまま残す。** κ を測り終えるまで授業で
使えないことになり、実データが集まらない。実データが無ければ κ も測れない。

**全件 blind を続ける。** 標本は最速で貯まるが、教員が使わなくなる。
使われない仕組みからはデータが出ない。
