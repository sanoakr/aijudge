# ADR 0003: GradingRun は不変とし、人間の修正は追記する

- ステータス: 採用
- 日付: 2026-08-27
- 関連: 設計原則 P4, P5, P8

## 背景

AI 採点システムには、通常の業務システムにはない要求がある。

- **説明可能性**：なぜその点数になったかを学習者・教員に示せること。
  英国政府の AI 採点原則、EU AI Act の高リスク分類（教育評価）を想定する。
- **異議申し立てへの対応**：採点時点の基準・モデル・入力を後から再現できること。
- **精度の測定**：AI の採点と教員の修正の差分が、そのまま一致度（κ）の測定データになる。
- **モデル更新時の再評価**：モデルを差し替えたとき、過去の提出を再採点して
  影響範囲を測れること。

素朴に「採点結果テーブルを UPDATE する」設計にすると、これらがすべて失われる。
特に、教員が修正した瞬間に AI が何と言っていたかが消えるため、
PoC-1 の最重要指標である κ が測れなくなる。

## 決定

**`GradingRun` は作成後に変更しない。**

1. `GradingRun` は Pydantic レベルで `frozen=True`。
2. 教員の修正は `HumanReview` として**別レコードで追記**する。
   `HumanReview.adjusted_levels` は変更した観点だけを持ち、
   触っていない観点は「AI の判定に同意した」という意味になる（`agreed` プロパティ）。
3. 再採点は既存 run を書き換えず、新しい `GradingRun` を作る。
   古い run には `superseded_by` を立てる。
4. 再現に必要な情報は `GradingContext` に全部入れる。
   `rubric_version` / `prompt_versions` / `model_ids` / `model_params` /
   `input_hash` / `pipeline_version`。

### 永続化層での強制（実装時の必須事項）

型の `frozen` はアプリ内でしか効かない。DB レベルでも強制する。

- `grading_run` / `criterion_score` / `evaluator_result` テーブルに
  `UPDATE` と `DELETE` を禁止するトリガを置く。
- アプリのロールに `UPDATE` / `DELETE` 権限を与えない。
- 訂正が必要な場合は新しい run を作る。

これを PoC-0 の最初のマイグレーションに含める。あとから追加すると、
その間に書き込まれたデータの信頼性が担保できない。

## 根拠

- **不変にしないと κ が測れない。** PoC-1 の合格基準（κ ≥ 0.65、見逃し ≤ 5%）は
  「AI が何と言い、人間が何に直したか」のペアがなければ算出できない。
- **ストレージは安い。** 提出ごとに数 KB の JSON が積み上がるだけで、
  失われる情報の価値に比べれば無視できる。
- **監査に耐える。** 「採点をこっそり書き換えていない」ことを構造で示せる。

## 帰結

- 「現在の点数」を出すには `GradingRun` に最新の `HumanReview` を重ねる
  導出処理が必要になる。この導出は `packages/grading` に 1 か所だけ置く。
- 成績表示のクエリが素朴な SELECT ではなくなるため、
  読み取り用のマテリアライズドビュー（現在スコア）を用意する。
- 再採点を繰り返すとデータが増える。年度単位のアーカイブ方針が別途必要。
- `Evidence` は `artifact_content_hash` を持ち、Artifact が再正規化されたら
  古い根拠は「無効」と判定される（黙って別の場所を指さない）。

## 却下した案

**採点結果を UPDATE し、変更履歴を監査ログに残す。** 監査ログは構造化されておらず、
κ の算出に使えない。また「ログに書き忘れた更新経路」が必ず生まれる。

**AI の採点だけを保存し、人間の修正は成績表側に持つ。** 採点と成績が
別々の真実を持つことになり、どちらが正しいかを判定する処理が至る所に必要になる。
