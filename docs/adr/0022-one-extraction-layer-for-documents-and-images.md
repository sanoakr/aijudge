# ADR 0022: 文書からの抽出と画像からの抽出を、1 つの層にする

- ステータス: 採用
- 日付: 2026-09-19
- 関連: 設計原則 P1, P3, P8 / ADR 0001, ADR 0002, ADR 0011, ADR 0015, ADR 0018, ADR 0021

## 背景

ADR 0021 で画像を読む経路を作ったとき、同じ仕事が 2 か所に住むことになった。

| | PDF / DOCX → 本文 | 画像 → 本文 |
|---|---|---|
| 層 | Normalizer（変換層） | Evaluator（採点層） |
| 出力 | `bytes` | `CriterionScore`（点） |
| 下流での再利用 | 全評価器が読める | **誰も読めない** |
| 出所の記録 | 無し | `model_id` / `prompt_id` |

**対象が違うだけで仕事は同じ**なのに、片方は変換で片方は採点になっていた。
実害は明確で、画像から取り出した本文を `checklist_ai_judge` も
`rubric_ai_judge` も読めない ── PDF なら読めるのに。

## 決定

### 1. 抽出は 1 つの契約にする

`aijudge_core.extraction` の `Extractor` / `Extraction`。entry point の
グループは `aijudge.extractors`、ディレクトリは `extractors/`。

    document_text   PDF / DOCX → 本文（pypdf。決定的。出所は無い）
    image_text      画像       → 本文（VLM。出所を持つ）

**契約は core に置く。** 抽出を走らせるのは採点（S5）で、将来は受付（S3）に
移る（下記）── 2 つのサブシステムが同じ型を見る必要があり、サブシステムどうし
は直接 import しない（ADR 0001）。実装の登録簿は採点側が持つ。

`Extraction` は本文に加えて `model_id` / `prompt_version` を運ぶ。旧
`Normalizer` は `bytes` を返すだけで、**模型を使う抽出では「どのモデルの
どの版で起こした本文を採点したか」が残らなかった**（P8）。

### 2. 科目プロファイルの宣言は `input.transcription` に統合する

旧 `normalizers:` は同じ仕事を「変換」と呼んでいた側の名前である。
`input.transcription` は既に存在し、`allow_handwriting` の相方として
「書き起こす手段」を指していた。**2 つの名前のうち、残すのは後者**である。

**宣言は複数書ける**（2026-09-21 追記・#352）。当初は 1 科目 1 つだったが、
**1 つの科目に認定証（画像）とレポート（PDF）が並ぶのは実際の運用**であり、
`image_text` は PDF を扱わない（描画に要る PyMuPDF が AGPL で、Apache-2.0 の
このリポジトリに入れられない）。単数だと片方が書き起こされないまま評価器へ
渡り、「読めない」と判定されて人に回る ── **採点が止まらないので、設定の
誤りが結果に現れない**という最も見つけにくい壊れ方になる。

```yaml
input:
  transcription: [image_text, document_text]
```

振り分けは提出物の種類で行う（`Extractor.applies_to`）。**この選び方は
プロトコルが最初から前提にしていたもの**で、足りなかったのはプロファイル側
の単数制約だけだった。同じ種類を 2 つが名乗るときは**先に書いたほうが勝つ**。
1 つだけ書くときは文字列のままでよい（運用中のファイルは無改修）。

### 3. 抽出は決定的フェーズで 1 回だけ走り、結果は run に残る

以前はフェーズ分岐**より前**にあり、決定的評価と AI 評価で 2 回走っていた。
pypdf なら同じ結果が返るので害は無かったが、**模型を使う抽出では 2 回の
結果が一致せず、「決定的評価が見た本文」と「AI 評価器が見た本文」が違う
ものになる。**

`GradingRun.extractions` に残す ── 採点が何を読んだかそのものだからである。
AI フェーズは土台（`base`）からそれを読む。

**誰も読まないなら取り出さない。** 全観点を人が採点する課題では、機械は
1 点も付けない（人採点の観点に付いた判定は捨てられる・ADR 0015）ので、
書き起こしても行き先が無い。それでも走らせると画像 1 枚あたり 20〜40 秒を
捨てる ── ゲートが「LLM を呼ばないために」あるのと同じ理由である（ADR 0011）。

科目プロファイルは複数の課題で共有されるので、これは実際に起きる ── 同じ
コースに、画像を機械が読む課題（認定証・ex2）と、教員が目で見る課題
（認定証・ex1）が並ぶ。**ex1 は人採点のままなので、抽出は 1 回も走らない。**

### 4. 採点と照合を分ける

`image_text_check`（画像を読んで点まで付ける AI 評価器）は 2 つに割れた。

| | 何をするか | 種別 |
|---|---|---|
| `image_text` | 画像を書き起こす | 抽出器（VLM） |
| `text_pattern_check` | 本文と宣言された文字列を照合して段階を出す | **決定的**評価器 |

後者は LLM を呼ばない。**対象が画像由来でも PDF 由来でも同じ**で、速いレーンで
走り、`conclusive` を立てる（P3）。ADR 0021 が「モデルに書き起こしだけを
させる」と決めたことの、構造としての帰結である。

実測（ADR 0021 と同じ 47 件）に、実装した照合規則をそのまま当てて再現を
確認した ── `certificate` 46/46、`nickname` 46/46、3 サンプルの割れ 0。

### 5. 学習者の確認は、まだ実装しない

`TranscriptionMeta.confirmation_required`（**そのときの事実として焼き付ける**）
と `TaskVersion.confirm_transcription`（既定 False）を用意し、画面には出すが
**変更させない。** 値の意味と置き場所を先に決めておかないと、確認画面を作る日に
全課題の版を作り直すことになる。

**灰色にしただけでは境界にならない**ので（#146）、`TaskVersion` の検証で
True を拒む ── 課題を作る経路は 3 つあり（`course apply`・教員コンソール・
取り込み）、画面だけを直しても残り 2 つが素通りする。

**確認していないものを「確認済み」にしない。** `confirmed_at` / `confirmed_by`
は空のまま残り、記録は「誰も確認していない」と正直に語る。採点に使ってよいかは
新しい `is_settled`（確認済み **または** 確認を求めない）が判定する ──
`is_confirmed` をそのまま採点の可否に使うと、確認を求めない課題では永久に
採点できない。

## 検討して採らなかったもの

**抽出器を正規化器のまま、パイプラインの変換段に置く。** フェーズ分岐より
前なので 2 回走る（上記 3）。これが決定打だった。

**受付（intake）で抽出し、`TRANSCRIPTION` の成果物として保存する。**
本来の形で、Phase 6 の「手書きと OCR」がそこへ行く。いま採らないのは、
画像 1 枚の書き起こしが実測 20〜40 秒で、**提出ボタンを押した学習者を
その間待たせる**ためである。非同期にするには `TRANSCRIBING` 状態の実装
（core の状態遷移・ジョブ・画面）が要り、それは学習者の確認と一緒に作る方が
無駄が無い。

移行を塞がないようにしてある ── そのときは抽出器をそのまま受付へ移し、
`GradingRun.extractions` の代わりに提出物へ残る。読む側（`text_pattern_check`
も既存の AI 評価器も）は「本文」しか見ないので変わらない。

## 運用中の配備に載せ替えられるか

運用機（`judge.math.ryukoku.ac.jp`）では既に提出と採点が進んでおり、配備が
触らないものが 2 つある。`packages/grading/tests/test_upgrading_a_running_deployment.py`
がこれを固定する。

- **科目プロファイルは git のチェックアウトの外にある**（`AIJUDGE_PROFILES_DIR`）。
  配備は上書きしないので、`normalizers:` と書かれたまま置かれている。
  `extra="forbid"` のまま鍵を消すと**配備した瞬間に全科目の読み込みが失敗し、
  採点が止まる。** 旧キーを `input.transcription` として読む
- **配備の前に作られた `GradingRun` は `extractions` を持たない。** 空を
  そのまま信じると、配備をまたいだ AI フェーズだけが本文ではなく原本を読む。
  土台が空なら取り直す
- 既存の `TranscriptionMeta` は `confirmation_required` を持たず、既定は
  **True**（＝確認が要る）。旧来の意味がそのまま保たれる ── False を既定に
  していたら、過去の未確認の書き起こしが突然採点対象になっていた
- `TaskVersion` は JSON から復元されるのでマイグレーションは要らない

**配備しても挙動は変わらない。** 運用の 2 コースのプロファイルは
`normalizers: []`（空）なので、抽出器は解決されず 1 回も走らない。画像の
自動採点が動き出すのは、プロファイルに抽出器を書き、課題の観点が
`text_pattern_check` を指名したときだけである。
