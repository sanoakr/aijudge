# ADR 0016: ログは 3 つある ── 運用ログ・監査ログ・採点記録

- ステータス: 採用
- 日付: 2026-09-10
- 関連: 設計原則 P2, P7, P8 / ADR 0003, ADR 0004, ADR 0005, ADR 0007, ADR 0010

## 背景

「ログを整備する」は 1 つの作業に見えて、性質の違う 3 つを同じ言葉で呼んでいる。
一括りにすると、**消えては困る記録がローテートで消える場所に置かれる**か、
逆に**ログ基盤の不調が採点を止める**。どちらも起きうる形になっていた。

着手時点の実測はこうだった。

- `logger.*` の呼び出しは全リポジトリで 13 箇所。すべて `warning` / `exception` 系で、
  **正常系のイベントログは 1 行も無い**。
- `logging.basicConfig` は `aijudge-worker` と `aijudge-finalize` の 2 つにしか無い。
  `aijudge-web` / `aijudge-review` では、同じ `logger.warning` が root の lastResort
  ハンドラ（WARNING 固定・書式なし）に落ち、INFO は捨てられていた。
  **同じコードがプロセスによって違う出方をしていた。**
- `uvicorn.run(..., log_level="warning")` が `uvicorn.access` ごと黙らせていたので、
  **アクセスログが存在しなかった**。
- `audit` は全ソースで 0 ヒット。ログイン成否、API トークン発行、権限変更、
  成績の手修正、プロファイル編集 ── いずれも痕跡が残らない。
- systemd unit に `SyslogIdentifier` も保存期間の指定も無く、journald の既定任せ。

実害は既に記録されている。`docs/RUNNING.md` の「エラーはワーカーのログにしか
出ない」── #60 と #80 は、どちらも画面からは「採点が遅い」としか見えず、
2 度踏んだ。**原因はログが少ないことではなく、web の提出とワーカーの失敗を
突き合わせる鍵が無かったことである。**

## 決定

ログを 3 つに分け、混ぜない。

| | 何の記録か | 置き場 | 消えてよいか | 書けなかったら |
|---|---|---|---|---|
| **運用ログ** | プロセスに何が起きたか | journald | よい（既定 90 日） | 何もしない（best-effort） |
| **監査ログ** | **誰が**成績に関わる何をしたか | DB `audit_events` | だめ | **操作ごと失敗させる** |
| **採点記録** | どの版・どのモデルで採点したか | `GradingRun`（既存） | だめ | 採点を保存しない（ADR 0003） |

### 1. 運用ログ ── `packages/telemetry`

設定を持つのは**合成ルート（`apps/*`）だけ**。各パッケージは標準の
`logging.getLogger(__name__)` を使う。ライブラリ側がハンドラと書式を決め始めると、
同じコードが取り込まれ方によって違う出方をする ── **実際にそうなっていた。**
`.importlinter` の `only-apps-configure-logging` がこれを落とす。

出力は 1 行 1 イベントの JSON（`AIJUDGE_LOG_FORMAT=json`、開発の既定は text）。
`AIJUDGE_LOG_LEVEL` で段を決める。

**載せてよいのは識別子だけ。** 提出物の本文・氏名・メール・LLM のプロンプトと
出力は載せない（P7）。journald はバックアップも暗号化も掛かっていない場所で、
そこへ学習者データを複製した時点で、ローカルモデルにしか流さないというゲートウェイ側の
保証（ADR 0004）が迂回される。規約では守れないので、`aijudge_telemetry.bind` が
値の型と長さを見て弾く。

**相関 ID。** `RequestContextMiddleware` が 1 リクエストに `request_id` を発行し
（前段が付けていれば引き継ぐ）、その区間の全ログに載せる。ワーカー側は
`job_id` / `submission_id` / `phase` を積む。**web とワーカーを繋ぐ鍵は
`submission_id`** で、これは両側に既にある値である ── 新しい列は要らなかった。

アクセスログはこのミドルウェアが出し、**uvicorn 自身のアクセスログは止める**。
uvicorn の既定書式はパスとクエリを一体で持つので `?token=` の類が平文で残り、
かつ uvicorn は `request_id` を知らない。

**運用ログは採点の依存にしない**（P2）。`telemetry-knows-nothing` 契約で、
このパッケージが他のどのサブシステムも知らないことを固定する。ログを外しても
採点は動く。

### 2. 監査ログ ── `packages/audit` ＋ `audit_events`

ファイルではなく DB に置く。成績に関わる「誰が変えたか」を、ローテートで消える
場所に置いてはいけない。DB なら restic の対象（DB ダンプ）に自動的に入る。

パッケージを分けるのは `packages/observation` と同じ理由である ── 記録の型を
別のパッケージに置いたせいで、そのパッケージを消すと採点が止まった（ADR 0007）。

**`HumanReview` と混ぜない。** 監査行は κ の証拠ではない。レビュー 1 件に対して
監査行が 1 本増えるだけで、`human_reviews` の意味は変えない（ADR 0010 の再演を
避ける）。

運用ログと決定的に違うのは失敗時の扱いで、**監査の書き込みは操作と同じ
トランザクションで行い、書けなければ操作ごと失敗させる。** 成績変更が監査なしで
成立してはいけない。

### 3. 採点記録

`GradingRun` の再現フィールド `(rubric_version, prompt_version, model_id, params,
input_hash)`（ADR 0003）。ログではなく採点の実体である。ここに書くべきものを
運用ログに書かない ── 特に **LLM のプロンプト全文とモデル出力はログに出さない**。

### 保存期間

- journald: unit に `SyslogIdentifier=aijudge-*`、`journald.conf.d` で
  `SystemMaxUse` と `MaxRetentionSec=90d` を明示する。
- `audit_events`: 学期を跨ぐので最低 1 年 ＋ 成績異議申立ての期間。削除ジョブは
  作らない（行は小さい）。
- restic の対象は `/srv/aijudge` のまま変えない。監査が DB にあれば足りる。

## 帰結

- 「ログが無い」ではなく「どのログか」を先に決める。新しい記録を足すときは、
  上の表のどの行かを言えなければ置き場所が決まらない。
- 運用ログの書式変更は自由。監査ログの列変更は移行を伴う。この非対称は意図的で、
  片方を軽く保つために分けている。
- ログ基盤を止めても採点は動く。監査を止めると成績の変更ができなくなる。
  **これは不便ではなく、そう設計してある。**
