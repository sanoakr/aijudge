# ADR 0017: 左の帯に何を載せ、どう配るか

- ステータス: 採用
- 日付: 2026-09-11
- 関連: 設計原則 P2, P5 / ADR 0001, ADR 0010 / #165, #184, #185, #189

## 背景

3 ラウンドのモック比較で決めた画面（#185）のうち、**左の常設の帯**だけが未実装で
ある。帯は「どこに用があるか」を開かずに判断させるためのもので、コース内の
行き先とその件数を持つ。

帯は `base.html` にある。つまり**全ページがそのデータを必要とする**。ここが
設計の全部で、残りは配り方の話になる。

着手時点の実測はこうだった。

**教員コンソールの画面（GET）は 34 経路ある。** コースの解決可能性で 3 つに割れる。

| | 件数 | 例 |
|---|---|---|
| `course_id` がパスにある | **17** | `/courses/{course_id}/submissions`, `/manage/courses/{course_id}/kc` |
| 他の id からコースを辿る | **3** | `/review/{submission_id}/reveal` |
| **コースを持たない** | **14** | `/`, `/manage/users`, `/manage/subjects`, `/manage/oidc-settings`, 認証 |

最後の 14 件は取りこぼしではない。**テナント単位の画面には、そもそもコースが
無い**（#165 でパンくずを足したときに確認した事実そのもの）。利用者の一覧に
空のコース帯を出すのは、情報が無いことを情報のように見せることである。

**件数のコストも測った。** コースのメニューが使う `pending_counts` は課題ごとに
引くので、41 問のコースで **42 クエリ**になる。開いたページで 1 回払うなら安い。
全ページに出る帯の裏で払うなら高い。

**ハンドラは 40 を超える。** 帯のデータを引数として渡す形にすると、渡し忘れる
場所が 40 以上できる。忘れると帯が消えるか、数字だけ消える。

## 決定

### 1. 帯は 2 つの形を持つ

コース単位の帯（20 経路）とテナント単位の帯（14 経路）。**同じ帯の「データが
無い状態」ではなく、別の帯である。** テナントの画面に出る行き先は利用者・
科目プロファイル・ログイン方式で、コースの行き先とは階層が違う。

### 2. 配るのは context processor。渡すのはハンドラではない

`Jinja2Templates(context_processors=[...])` に 1 つ足す。解決の順は 2 段。

| 見るもの | 効く経路 | 追加のクエリ |
|---|---|---|
| `request.state.rail_course_id` | 3 | **0** |
| `request.path_params["course_id"]` | 17 | 0 |
| どちらも無ければテナントの帯 | 14 | 0 |

`request.state` を先に見るのは、`/review/{submission_id}/…` の 3 経路のため。
**そこはハンドラが既にコースを読んでおり、テンプレートにも渡している**
（`reveal` の context に `course` がある）。帯のために
`submission → task_version → task → course` を引き直すのは、既に手元にある値を
捨ててもう一度買うことになる。ハンドラ 3 つに 1 行足す。

**40 のハンドラを触らない。** 触る 3 つは「パスから解決できない」という理由が
はっきりしている場所だけで、残りは何もしなくても帯が出る。

#### テンプレートから引かない

`course` は既にテンプレートの context にあるので、Jinja のグローバルに
`attention_counts(course.id)` を置けば、**ハンドラを 1 つも触らずに** 20 経路
すべてが帯を持てる。context processor は Request しか見られないのでこれが
できないが、テンプレートは見られる。

それでも採らない。**テンプレートの描画中に DB を引くことになる。**
このリポジトリは層の向きを機械で守っており（`.importlinter`）、`core` は I/O を
持たず、保存先はどのサブシステムも import しない。描画は I/O を持つ層ではない。
`root_prefix()` をグローバルに置いてあるのは環境変数を読む純関数で、DB は別物
である。

代わりに、**約束をテストにする。** 宣言された GET 経路を数え上げ、コース単位の
経路がコースの帯を出すことを固定する ── `request.state` を書き忘れた新しい
`/review/…` 経路は、数字が静かに消えるのではなくテストで落ちる。

### 3. 件数は 2 文。**落ちても画面を落とさない**

`attention_counts_for_course` が 2 文で答える（#189 の下ごしらえ）。
帯は装飾ではないが、**成績を読む・付ける機能の前提でもない。** 数えられなければ
数字を出さずに行き先だけ出す ── ここで例外を上げると、集計の不調が採点の画面を
巻き込む（P2 の劣化動作）。

### 4. 載せるのは「人が動かないと進まないもの」だけ

再確認の依頼と未確定。**提出の総数・受講者数・知識要素の数は載せない。**
どこに用があるかを教えないので、全ページがクエリを払う理由にならない。
行き先は数字が無くても行き先である。

### 5. 数字は開いた先と一致しなければならない

帯の数字と、開いたページの件数は同じでなければならない。**違うなら、どちらが
本当か確かめに開くことになり、開かずに判断するために置いた帯が用を成さない。**
別の経路（2 文と 42 クエリ）で到達するので、一致はテストで固定する。

### 6. 学習者アプリには帯を置かない

**当初は「同じ仕組みで別のデータ」と書いたが、経路を数えて撤回した**（#185）。

学習者アプリの画面は 4 つ（コース一覧・コース・課題・提出結果）で、一直線の
ドリルダウンである。**13 の行き先を抱える問題が無い** ── パンくずが既に
同じことを言っており、帯を置いても新しく分かることがない。

しかも害がある。学習者の画面は読むことが主で、課題文とコードが本文の
大半を占める。そこから横幅を 248px 取ると、コードの行が折り返し始める
（採点画面で「幅がそのまま可読性」と判断したのと同じ理由が、逆向きに効く）。

**帯が解いたのは「13 の行き先に毎回メニューから下りる」問題であって、
学習者アプリにその問題は無い。** 画面が増えたときに、そのときの経路数を
根拠として立て直すのが筋である。

## やらないこと

- **JSON で後から読む。** 帯の数字だけが JavaScript のある人にしか出ない状態に
  なる。この画面群は JavaScript 無しで成立する（`manage.py` 冒頭）。
- **全ハンドラに渡させる。** 渡し忘れが 40 か所できる。
- **帯のためにコースを引き直す。** 3 経路はハンドラが既に持っている。
- **テナントの画面にコースの帯を出す。** 空の帯は、情報が無いことを情報のように
  見せる。

## 帰結

- コース単位のページは 1 回の描画につき **2 文**増える。テナント単位のページは
  増えない。42 クエリを全ページに広げる案との差がここである。
- ハンドラの変更は **3 か所**（`/review/{submission_id}/…`）。
- 帯が消える経路が 1 つできる ── context processor が例外を上げた場合。
  そこは行き先だけ出して数字を落とす（4 と 3 の帰結）。
- **`request.state` の約束を覚えている必要がある**のは 3 経路だけだが、
  忘れうる。経路表を突き合わせるテストがその代わりに覚える。
