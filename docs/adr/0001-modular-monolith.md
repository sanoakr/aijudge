# ADR 0001: モジュラーモノリスから始め、境界を CI で強制する

- ステータス: 採用
- 日付: 2026-08-27
- 関連: 設計原則 P2, P9

## 背景

aiJudge は AI 採点・AI 作問・スキル/ポートフォリオを「可能な限り独立したサブシステム」
として運用できることを要求されている。加えて複数機関・複数科目の大規模運用を想定する。

この要求を素直に読むとマイクロサービス構成になるが、我々はまだ次を知らない。

- どのサブシステムが実際にスケール上のボトルネックになるか
- サブシステム間の境界が本当に今引いた位置で正しいか
- 開発チームがいくつに分かれるか（当面は少人数）

境界が間違っているマイクロサービスは、モノリスより変更コストが高い。
一方で「あとで分ければいい」と言って境界を曖昧にしたモノリスは、二度と分割できない。

## 決定

**1 リポジトリ・1 デプロイ単位のモジュラーモノリスから始める。**
ただしモジュール境界は規約ではなく機械で強制する。

- `packages/*` を各サブシステムに対応させる（S1〜S11）。
- `packages/core` だけが全モジュールから依存されてよい。逆に core は何にも依存しない。
- `packages/X → packages/Y`（X, Y ≠ core）の直接 import を**禁止**する。
  サブシステム間の連携はイベント（`aijudge_core.events`）と公開 API に限る。
- `evaluators/*` は `packages/core` にのみ依存してよい。
- これらを `.importlinter` の contract として書き、CI で落とす。

負荷とチーム分割の実態が見えた時点で、この境界線でプロセスを切り出す。

## 根拠

- **切り出しコストの低さが独立性の担保になる。** 「独立して運用可能」を証明するのは
  デプロイ単位の数ではなく、依存グラフの形である。依存グラフさえ正しければ、
  切り出しは機械的な作業になる。
- **早期の K8s / メッセージブローカ導入は PoC の速度を落とす。** PoC-0/1 は
  Docker Compose で動かし、K3s 移行は PoC-5 で行う。
- **import-linter は「破った瞬間」に落ちる。** レビューで気づく方式は必ず漏れる。

## 帰結

- 単一プロセスで動くため、サブシステム単体の障害分離は当初は得られない。
  代わりに「S6 / S7 を停止させた状態で E2E が通ること」を CI の定期ジョブで検証し、
  コード上の劣化動作（graceful degradation）だけは最初から保証する。
- `packages/*` を追加したら `.importlinter` にも登録する必要がある。
  登録漏れは `packages/core/tests/test_boundaries.py` が検出する。
- DB は当面ひとつだが、**スキーマはサブシステムごとに分ける**。
  他モジュールのテーブルを直接 SELECT しないこと。これは import-linter では
  検出できないため、レビュー観点として ADR に明記しておく。

## 却下した案

**最初からマイクロサービス。** 境界の正しさを検証する前に分散システムの
運用コスト（トレース、結果整合性、デプロイ調整）を払うことになる。PoC の目的は
アーキテクチャ仮説の検証であり、その速度を落とす選択は本末転倒。

**素朴なモノリス（境界を規約で守る）。** 短期的には最速だが、
「あとで分ける」は実際には起きない。要求が独立運用である以上、選べない。
