# ADR 0008: 自動採点できていなかった課題を、伴走プロセスとルーブリックで採点する

- ステータス: 採用（実装は段階的）
- 日付: 2026-08-28
- 関連: ADR 0002, ADR 0006 / 設計方針 §9.2 Phase 2–3

## 背景

移行元の 2 科目を調べると、既存の Sharif Judge で**自動採点できていなかった
課題**が実在する。

| 種類 | 例 | Sharif Judge で採点できなかった理由 |
|---|---|---|
| サーバ課題 | ネットワーク演習 ex5–ex7（`httpServer2.py`、`httpThreadServer.py`） | 提出物が**受動的**。標準入力を与えて標準出力を比べる形に乗らない。接続して初めて動く |
| クライアント課題 | ネットワーク演習 ex4、test5（`echoClient2.py`） | 外部のサーバ（`133.83.80.110:50007`）に到達できないと動かない |
| 自己採点課題 | プログラミング演習 各 exam の p9 | 判定対象が標準出力ではなく `main()` の返り値、かつ得点が実得点との差で決まる |
| レポート課題 | 両科目 | PDF / DOCX。テストケースという概念が無い |

これらは in/out ディレクトリが空のまま残っており、教員が手で採点していた。

## 決定

### 1. 「自動採点できない課題」と「まだ自動採点できない課題」を区別する

上の 4 種はすべて後者である。**将来は自動採点する。** したがって
「教員レビュー専用」という恒久的な区分を作らない。作ると、そこに入った課題は
仕組みが揃っても移ってこない。

当面の扱いは **AI 観点だけで構成する**。取り込み器はテストケースが 0 件の
課題に対し、決定的評価器ではなく AI 評価器を担当にする。決定的評価器を
担当にすると、その観点は永久に採点されず全提出が `review_required` で
教員に積まれる（設計原則 P5 の「誰も見ていない観点に点を与えない」が、
そのまま「全部を人間が見る」になる）。

テストケースの形が決まった時点で、新しい版を作って決定的評価器に渡す。
過去の採点基準は書き換えない（P8）。

### 2. ネットワーク課題は伴走プロセスで採点する

提出物の外に、採点のために動かすプロセスを置く。

- **クライアント課題**（提出が接続する）→ 伴走**サーバ**を立てる
- **サーバ課題**（提出が待ち受ける）→ 伴走**クライアント**を立てる

#### 伴走プロセスは教材から取り込む。生成しない

**既に存在する。** 移行元の教材を調べたところ、必要なものが揃っていた。

| 用途 | 教材中の実物 |
|---|---|
| ex4 クライアント課題の伴走サーバ | `sample/echoServer.py` |
| ex5–ex6 サーバ課題の伴走クライアント | `sample/httpCheckClient2.py`, `httpTestClient.py` |
| ex5 の採点手順 | `sample/check_ex5.sh`（起動待ち・curl・fixture 生成まで） |

`echoServer.py` は**課題文が名指ししている相手**である（「同一 PC 上で
echoServer.py を実行」）。それに対して採点することが「課題の指示どおりか」の
定義そのものになる。LLM に別実装を書かせると、課題文と採点基準がずれる。

#### LLM を採点の経路に入れない

伴走プロセスは**決定的評価器の参照実装**である。ここに LLM を置くと:

- **設計原則 P3 に反する。** 決定的評価に AI の判断が混ざる。
- **全員が落ちる失敗が作れる。** プロトコルが微妙に違う伴走サーバを生成すると、
  全提出が失敗し、原因は提出物の側にあるように見える。同じ形の欠陥を
  実際に 2 度踏んでいる（作業域が黙って空になる → 全員 0 点、
  タイムアウトの共用 → ワーカー停止。ADR 0006 / ADR 0002）。
- **再現性が壊れる（P8）。** 採点時に生成すると、再採点で別の結果が出る。

#### 実装：同一コンテナ内の 2 プロセス

**サンドボックスの契約を変えない。** 伴走プロセスと提出物を同一コンテナ内の
2 プロセスにし、`--network=none` のまま loopback で通信させる。

実測（2026-08-28）で確認した。`--network=none` のコンテナには loopback
インターフェースだけがあるので:

- 伴走サーバと提出物は `127.0.0.1` で通信できる
- 外部への到達は塞がったまま（`93.184.216.34:80` へ `denied`）

別コンテナにしてユーザー定義ネットワークで繋ぐ案より優れている。

- 隔離を課題の都合で緩めない（`--network` を開けると、開けた状態が既定になる）
- 課題文が「同一 PC 上で echoServer.py を実行」と書いている状況と一致する
- `ExecRequest` / `Workspace` の契約に手を入れずに済む（S4 の変更は **0 行**）

段取り（伴走プロセスを起動 → 待ち受けを待つ → 相手を走らせる → 出力を集める）は
作業域に書き出す**起動スクリプト**が持つ。`Workspace.run` は 1 コマンドを終了まで
走らせる契約なので、2 つを並べるにはサンドボックスの中に段取りを持ち込むしかない。

待ち受けの検出はポートへの接続試行で行う。固定時間 sleep にすると、速い提出でも
毎回その時間を払い、遅い提出は落ちる。

#### 宣言は課題ディレクトリの `companion.yaml`

```yaml
role: client                 # client: 提出が接続する / server: 提出が待ち受ける
companion: echoServer.py     # **教材のファイルを指す**（生成しない）
port: 50007
cases:
  - name: case1
    input: "{host}\n{port}\n"
    expected_contains:
      - "Send b'Hello, world'"
      - "Received b'Hello, world'"
```

`{host}` `{port}` は採点時に伴走プロセスの値へ差し替わる。課題の `in/` には
本番のホスト（`133.83.80.110`）が書かれているので、そのままでは採点機の
設置場所に依存する。

照合は**部分一致**を既定にした。サーバの出力には接続元の一時ポート
（`('127.0.0.1', 53578)`）のように毎回変わる値が混ざるため、完全一致では常に落ちる。

宣言の誤りは取り込み時に落とす。特に**何も照合しないケースを拒否する** ──
それはどんな提出でも通る。宣言があるのに読めない場合も例外にする（空を返すと
「テストケースが 0 件の課題」として取り込まれ、宣言を書いたのに自動採点されない
状態が静かに生まれる）。

#### LLM の出番は「散文の要件 → テストケース」の翻訳

`check_ex5.sh` の冒頭に「ex5-TA（Notion の要件）に基づく自動チェック」と
書かれている。**要件は既に散文で書かれており、教員がそれを bash に手で
翻訳している。** そこが自動化に値する作業で、参照実装を書かせる話ではない。

これは Phase 4（AI 作問）に置く。生成物は**門を 2 つ**通らないと採点に使えない。

```
教員が課題を設定
  → LLM がテストケース（と伴走の起動方法）を下書き
  → 門 1: 参照解答がすべて通る
  → 門 2: 変異させた参照解答が落ちる
  → 教員が承認
  → TaskVersion にバイト列として固定（再採点は同じもので走る）
```

**門 2 が本質である。** 門 1 だけでは、何を送っても OK を返す伴走プロセスが
通ってしまう。参照解答を機械的に壊して（送信メッセージを変える、ポート
読み取りを消す）落ちることを確かめる。Phase 4 の「解の一意性検証で不正な
問題を 95% 以上除去」と同じ考え方。

大学ネットワーク上の実サーバ（`133.83.80.110`）に到達させる案は採らない。
理由が 3 つある。

- **決定性がない。** そのホストが落ちていれば全員が 0 点になり、原因は
  提出物の側にあるように見える。
- **提出コードに外向き通信を許すことになる。** 隔離の前提（`--network=none`）を
  課題の都合で外すと、外した状態が既定になる。
- **採点機の設置場所に依存する。** 学外や別セグメントでは採点できない。

伴走プロセスはコンテナネットワーク内に置き、**提出物はそこにだけ到達できる**
（`--network` を専用ネットワークに繋ぎ、外向きは遮断する）。課題の入出力に
現れるホスト名・ポートは、採点時に伴走プロセスの値へ差し替える。

### 3. レポート課題はルーブリックで採点する

Phase 3（レポート課題の採点）の範囲。構造チェック（必須節・引用形式・字数）は
決定的評価器、論理構成と主張の妥当性は AI 評価器。PDF / DOCX からの
テキスト抽出が前段に要る。

## 帰結

- 取り込み時に「自動テストがまだ無い課題」が可視化される。`aijudge-admin
  task import` はその件数を別に報告する（「取り込めた」と「自動採点できる」を
  混ぜて報告しない）。
- 伴走プロセスは `TestCase.payload` の新しい形として表現する。`payload` の
  解釈は評価器の責務なので（ADR 0002）、コアと採点エンジンは変わらない。
- サーバ課題の採点には**待ち受け開始の検出**が要る（ポートが開くまで待つ、
  開かなければ時間切れ）。これは新しい評価器になる見込みで、
  `code_test_runner` の拡張では収まらない。
- **自己採点課題は保留する。** prog2 の各試験の最終問題（12 件）で、
  Problem 1–8 の自己予測点を `main()` の返り値として返させ、実得点 `x` と
  申告 `y` から `(10-|x-y|)/2` で採点する。扱えない理由が 3 つ重なっている。

  1. 判定対象が標準出力ではなく**終了コード**（現在の実装は `exit_code == 0` を
     合格の前提にしているので、`return 10` は異常終了として扱われる）
  2. `x` が**同じ試験の他問題の採点結果**である。`EvaluationRequest` に
     他の提出の採点結果を見る経路は無い（評価器を単体でテストできるように
     するための意図的な制約）
  3. 得点が連続量で、ルーブリック段階に乗らない（丸めると 1 点差と 3 点差が
     同じ段階に入る）

  2 は「課題間の依存」という新しい概念で、KC 体系（Phase 4）や成績集約
  （Phase 5）と同じ層の話である。ここで急いで `EvaluationRequest` を広げると
  「他の全採点結果を見られる」型になり、評価器の単体テスト可能性
  （ADR 0002 の前提）が崩れる。**当面は AI 観点＋教員確定で運用し、
  成績集約が入る Phase 5 で繋ぐ。**

## 却下した案

**大学ネットワークの実サーバに到達させる。** 上記のとおり決定性・隔離・
設置場所の 3 点で不可。

**サーバ課題を恒久的に教員レビュー専用とする。** 受講 91 名 × 5 課題を
毎年手で採点することになる。それを自動化しないなら、このシステムを作る
理由の半分が無い。

**Sharif Judge と同じ範囲に留める。** 移行の意味が「同じことを別の実装で
やる」になる。既存で採点できていなかったものを採点できるようにするのが、
作り替える理由である。
