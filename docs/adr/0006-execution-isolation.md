# ADR 0006: 提出物の実行はサンドボックス（S4）を必ず通し、隔離できないなら採点を止める

- ステータス: 採用
- 日付: 2026-08-27
- 関連: 設計原則 P3, P8 / 設計方針 §11 検証項目 6 / ADR 0002

## 背景

提出コードの実行は、このシステムで唯一「他人が書いた任意のコードを自分の
機械で動かす」場所である。プログラミング課題だけの話ではない。数学の CAS 実行も、
シミュレータ実行も、同じ性質を持つ（設計方針 §2.2 の S4）。

PoC-1 までの `code_test_runner` は `subprocess` を直接呼んでいた。rlimit は
掛けてあったが、これは事故防止であって防御ではない。ネットワーク送信・
家目録の読み取り・ホストへの書き込みが、いずれも素通りする状態だった。

## 決定

### 1. 実行経路をひとつにする

提出物を動かす経路は `aijudge_sandbox`（S4）だけ。評価器は `subprocess` を
呼ばない。呼べる状態にしておくと、どこか一箇所で隔離が抜け、**抜けたことに
気づく方法も無くなる**。

### 2. 隔離なしに自動で落ちない

使える隔離手段が無ければ `SandboxUnavailable` で採点を失敗させる。
0 点にもしない（隔離できないのは学習者の責任ではない）。隔離なしで点が
付いてしまうより、点が付かない方がましだから。

隔離なしのバックエンドは、独立した許可を 2 つ要求する
（`AIJUDGE_SANDBOX=unsafe` と `AIJUDGE_SANDBOX_I_KNOW_THIS_IS_UNSAFE=yes`）。
環境変数ひとつで外れると、設定ミスが静かに事故になる。

### 3. 使った隔離水準を結果に載せる

`ExecResult.isolation` に `Isolation`（none / os_sandbox / container /
kernel_isolated）を記録する。「サンドボックスで動かした」と後から監査
できなければ、主張として意味がない（P8）。

### 4. バックエンドに「守れないもの」を自己申告させる

`Sandbox.limitations`（`Limitation` の集合）で、そのバックエンドが塞げない穴を
宣言する。`isolation` の強弱だけでは、どの攻撃が通るかが分からない。

| バックエンド | isolation | 申告する limitations |
|---|---|---|
| unsafe | none | 全部 |
| seatbelt (macOS) | os_sandbox | shared_kernel, shared_uid, **process_limit_unenforced** |
| docker | container | shared_kernel |
| docker + runsc (gVisor) | kernel_isolated | （なし） |

## seatbelt 単体では fork bomb を封じ込められない

これは推測ではなく実測である（2026-08-27）。

seatbelt バックエンドに対して fork bomb の脱出試験を実行したところ、
**封じ込めに失敗し、開発機のプロセス表が埋まってシェルが fork できなくなった**
（`fork failed: resource temporarily unavailable`）。復旧に GUI からの
プロセス強制終了を要した。

原因は `RLIMIT_NPROC` の意味にある。これは「このプロセスの子孫」ではなく
**この UID の全プロセス**に対する上限で、seatbelt は UID を分離しない。
上限そのものは掛かる（暴走は頭打ちになる）が、**被害はサンドボックスの外に出る**。
同じ UID で動くほかのプロセス — 採点ワーカー自身を含む — が起動できなくなる。

**穴はプロセス数だけである。** seatbelt が確かに止めるものは確認済みで、
脱出試験として CI に残してある — 作業域外への書き込み、ネットワーク到達、
家目録の読み取り。

### これは「macOS では隔離できない」ではない

区別しておく。封じ込めに足りないのは `sandbox-exec` **単体**であって、
macOS という OS ではない。macOS 上で取れる選択肢は複数ある。

| 方法 | isolation | プロセス数の封じ込め | 備考 |
|---|---|---|---|
| seatbelt 単体 | `os_sandbox` | **不可** | 開発用。提出物には使えない |
| colima / Docker Desktop | `container` | 可 | 軽量 VM 上の Linux。**既存の `DockerSandbox` がそのまま動く** |
| Apple `container`（macOS 26+） | VM ベース | 可 | CLI が docker 非互換。バックエンド追加が必要（未実装） |
| 専用 UID + seatbelt | `os_sandbox` | 可 | UID が分かれれば `RLIMIT_NPROC` が実際の境界になる（未実装） |

したがって正確には:

- **提出物を seatbelt 単体で走らせてはならない。** 自分の書いたコード、または
  信頼できるゴールデンデータを通すためだけに使う。
- **実学生の提出はコンテナで動かす。** `--pids-limit` と `--user=65534` で
  プロセス数と UID をホストから切り離せる。コンテナの中身は Linux だが、
  **その Linux が Mac 上の VM であっても構わない**（開発機での運用として妥当）。
- Apple は `sandbox-exec` を deprecated としている。恒久的な土台にはならない。
  seatbelt 経路を残しているのは、コンテナ実行環境を入れられない機での
  開発を止めないためだけである。

### 破壊的な試験は既定で走らせない

fork bomb 試験は `AIJUDGE_RUN_FORK_BOMB_TEST=yes` の明示的な opt-in を要求し、
さらに `Limitation.PROCESS_LIMIT_UNENFORCED` を申告するバックエンドでは
skip する。**封じ込められないバックエンドで走らせれば、試験そのものが事故になる。**
「上限が効かないこと」を確かめる試験は要らない。効かないことはバックエンド自身が
申告している。

## 帰結

- 実提出を回す前に、コンテナ実行環境の用意が必須になる。開発機（macOS）に
  colima を入れれば同じ水準（`Isolation.CONTAINER`）に揃うので、
  「開発機だけ隔離が弱い」状態を放置しなくてよい。
- 採点結果には `isolation` が残るので、「どの水準で実行された点数か」を
  後から選別できる。os_sandbox で付いた点を実運用の成績に使わない、
  といった運用上の線引きができる。
- 言語・ツールチェインはコンテナイメージで定義する（設計方針 §2.2）。
  イメージの更新は採点の再現性に影響するため、`GradingRun` に記録する対象。

## 却下した案

**rlimit と権限落としだけで済ませる。** 実測で封じ込めに失敗した。
UID を分けない限りプロセス数の上限はホストを守らない。

**専用 UID を切って seatbelt で済ませる。** これは技術的には成立する
（UID が分かれれば `RLIMIT_NPROC` が実際の境界になる）。採らないのは、
sudoers の設定を各開発機で要求する割に、得られるのがコンテナと同じ水準では
ないため（カーネルは共有のまま、ファイルシステムの分離も seatbelt の
プロファイル記述に依存する）。コンテナ実行環境の導入は `brew install colima
docker` で済み、そちらの方が本番構成にも近い。将来 sudoers を前提にできる
運用が出てきたら、バックエンドとして足せる（`Limitation` の申告で
水準の差は表現できる）。

**隔離が無ければ隔離なしで実行し、警告を出す。** 警告は読まれない。
締切直前に「とりあえず動かす」判断が入る余地を残すべきではない。
止まった方が安全である。

**最初から gVisor 必須にする。** 開発機で動かなくなり、評価器の開発が
止まる。自動選択で最も強い隔離を選び、水準を記録する方式にした。
