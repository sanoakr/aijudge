# ADR 0024: 試しの実行は採点ではない ── 別のキュー、別のプロセス、同じ sandbox

- ステータス: 採用（2026-09-24、v1.18.0）。**runner の本数 K は未決** ── 運用機で測ってから決める（手元の値は根拠にしない・設計書 §12）
- 日付: 2026-09-24
- 関連: 設計原則 P2, P3, P7 / ADR 0006, 0011, 0018 /
  `docs/design/online-coding-test.md` §4.2・§8・§10

## 背景

ブラウザ IDE では、学習者が自分で与えた標準入力でコードを**サーバ上で実行**し、
結果を見られるようにする。これは採点と同じ sandbox でコードを動かすが、
性質はまったく違う。

| | 採点 | 試しの実行 |
|---|---|---|
| 誰が待っているか | 誰も（結果は後で読む） | 学習者が画面の前で |
| 古くなったら | 古くならない（その提出の採点） | 数十秒で無意味（とうに書き換えている） |
| 記録 | 残す（P8） | 残さない（行動記録に要約だけ） |
| 量 | 提出の回数 | 試験中に 150 名が数分おき |

採点キューに相乗りすると、ADR 0011 が段階を分けたのと同じ問題が起きる。
**試験中の実行の山が採点を待たせ、採点の山が学習者の画面を固める。**

## 決定

### 1. キューを分ける ── `run_requests`

- 実行要求は `grading_jobs` に入れない。`GradingPhase` も増やさない
- 取り方は採点キューと同じ型（PostgreSQL は `FOR UPDATE SKIP LOCKED`、SQLite では
  runner 1 本のみ）
- **1 人が同時に待てるのは 1 件**。部分一意索引
  `UNIQUE (learner_id) WHERE state IN ('queued','running')` で DB が保証する。
  画面の側で押せなくするだけでは境界にならない（#146 と同じ理由）
- **30 秒以上待った要求は実行せずに期限切れにする。** 混雑時に古いコードを
  走らせても誰の役にも立たず、後ろの要求を待たせるだけである
- 結果は要求の行に書き戻すだけで、`GradingRun` は作らない

### 2. プロセスを分ける ── `aijudge-runner@1..K`

- 新しい合成ルート `apps/runner`。同時実行数 K は systemd のユニット数で決め、
  runner の内部に並列性を持たせない（`aijudge-worker-ai@` と同じ型）
- 運用機（16 スレッド・30 GiB）での初期値は **K = 8、上限の目安は 12**。
  web・PostgreSQL・relay・PAIR に 4〜6 スレッドを残す計算で、詰まるのは CPU の側
- sandbox は runner の起動時に 1 度だけ組み立てる（`DockerSandbox` の初期化は
  書き込み確認でコンテナを立てるので、要求ごとに作らない）

**web プロセスには Docker の権限を与えない。** web は要求を行に書くだけである。
`aijudge_studentweb` は `aijudge_sandbox` を import しない（`web-does-not-run-code`
契約）。`aijudge_ide` も import しない（`ide-does-not-run-code`）── コードを動かせる
のは runner だけ、を構造で固定する。

### 3. sandbox と設定は採点と同じものを使う

**IDE で動いたものが採点で動かない、を起こさない。**

- 提出物を動かす経路は ADR 0006 のとおり `aijudge_sandbox` ひとつ。IDE 専用の
  実行環境は作らない（judge0 を立てない理由でもある）
- 言語・イメージ・1 回の上限は、採点ワーカーと同じ手順
  （`effective_profile(task_version.subject_profile, course.grading_overrides)`）で
  `evaluator_options.code_test_runner` から引く（ADR 0018）。コンパイルのフラグも
  toolchain の表から来る。**IDE 独自の設定値は持たない**
- 隔離は採点と同じく `AIJUDGE_SANDBOX=auto` の選択に従う。運用機では runsc
  （gVisor）で、実測では起動が runc と変わらなかった（157〜168 ms 対 153〜162 ms）
  ので、速さのために隔離を弱める理由が無い

### 4. 実行させる条件は提出と同じ

- 関門（学内限定・受付期間・役割・`may_see`）は提出と**同じ関数**を通す
  （#119・#370 の教訓）。**受付の外では実行もさせない** ── いつでも任意のコードを
  走らせられる窓口にしない
- ソース・stdin は 64 KiB まで。出力は sandbox の上限で切り、画面にはその先頭だけ
- **非公開のテストケースでは実行しない。** 公開サンプル（`hidden=False`）か
  自由入力だけ。試験中のテスト結果は答えの一部である
- 同じ学習者の連続実行は 3 秒空ける

### 5. ブラウザとは HTTP の問い合わせで話す

要求を出すと `run_request_id` が返り、ブラウザは 0.5 秒間隔で結果を問い合わせる。
WebSocket も long-poll も使わない。

- 既存の web ハンドラは同期で、1 リクエストごとに `unit_of_work()` を開く。
  接続を張りっぱなしにする経路はこの前提から外れる
- 大学のプロキシや学習者の PC のセキュリティ製品を確実に通るのは素の HTTP である
- 問い合わせるのは実行を待っている人だけなので、同時に待つのは K と待ち行列の
  数十名程度で、150 名 × 2 回/秒にはならない

## 帰結

- **runner が止まっても採点は進み、採点ワーカーが止まっても実行はできる。**
  両方向をテストで固定する
- runner が落ちているとき、画面は「実行環境が停止しています」と出し、編集・
  自動保存・提出・行動記録は動く（P2）。待っている要求は 30 秒で期限切れになる
- K を上げるのは systemd のユニットを足すだけで、コードは変わらない。上げる根拠は
  段階 3 の負荷試験で測る実行待ちの p95 とする
- 試しの実行の結果は成績の根拠にならない。採点は提出されたコードに対して、
  採点ワーカーがもう一度動かしたものだけである
