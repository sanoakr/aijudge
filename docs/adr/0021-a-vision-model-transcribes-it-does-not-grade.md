# ADR 0021: 画像はモデルに書き起こさせるだけで、採点させない

- ステータス: 採用
- 日付: 2026-09-19
- 関連: 設計原則 P3, P4, P5, P7 / ADR 0002, ADR 0004, ADR 0015, ADR 0018

## 背景

画像で提出する課題が運用に入った。ネットワーク及び演習 2026 の `ex1/paiza1`
── paiza ラーニングの修了認定証を画面キャプチャで出させ、2 つの観点で見る。

| 観点 | 何を見るか |
|---|---|
| `certificate` | 指定した講座の認定証であることが読み取れるか（0–2） |
| `nickname` | 認定証のニックネームに**本人の学籍番号**が入っているか（0–1） |

どちらも観点は `__human__` で宣言してあり、教員と TA が 1 枚ずつ見ていた。
初回の締切前時点で 42 名から 47 件が集まっており、回ごとに同じ量が出る。

**そもそも画像をモデルに渡す経路が無かった。** `ProviderCapabilities.vision`
という宣言だけがあり、`ChatMessage` は本文の文字列しか持っていなかった。

## 決定

### 1. モデルにさせるのは書き起こしだけにする

評価器 `image_text_check` は、画像の**指定された場所に何と書いてあるか**だけを
モデルに答えさせ、段階を決めるのは決定的な照合（正規表現と文字列一致）にする。

    モデル   画像 → 「受講者欄には `Y240040naka` と書いてある」
    こちら   `y240040` in `y240040naka` → 満たす

P3（読めば機械的に分かることを AI に訊かない）の素直な帰結である。文字列が
一致するかは機械に分かる。機械に分からないのは「画像に何と書いてあるか」だけで、
そこだけをモデルに訊く。

### 2. どこを見るかは課題が書く（ADR 0018）

読み取る項目は `TaskVersion.test_cases` が宣言する。評価器は認定証を知らない。

    payload={"criterion": "nickname",
             "where": "認定証の中央、講座名の下にある横線の上に書かれた 1 行。"
                      "左端から右端まで一字も落とさずそのまま写す。"
                      "氏名だけを抜き出してはならない",
             "expect": "learner_reference"}

段階は満たした項目の重みから決める。ただし比例配分だけでは**「0 にすべき提出」を
表せない** ── 別の講座の認定証にも修了文は書いてあるので、項目の一部が満たされて
段階 1 になる。講座名を `required` にすると、そこが外れた時点で最低段階になる。

### 3. 画像を読むモデルは別の経路を持てる

`AIJUDGE_LLM_VISION_BASE_URL` / `AIJUDGE_LLM_VISION_MODEL`。**運用機の主系は
`gemma4:e4b` で vision を持たない。** 画像を読めないプロバイダに画像を渡す
要求は、呼ぶ前に `CapabilityMismatch` で断る（`PolicyViolation` とは分ける
── 片方は経路の誤り、こちらはモデルの誤りで、直し方が違う）。

**この経路はフォールバックを持たない。** 主系と従系の両方に vision モデルが
ある保証は無く、落ちている間の代替が「画像を読めない相手」では、断られるか
（よい方）根拠のない答えが返る（悪い方）。読めないときは採点せず人へ回す。

### 4. 提出者の学籍番号だけは、パイプラインが運ぶ

`EvaluationRequest.learner_reference`。`Submission` は内部 ID しか持たないので、
「提出物に本人の学籍番号が書いてあるか」を見る観点には他に手が無い。解決するのは
合成ルート（ワーカー）で、パイプラインは利用者表を引かない（`aggregation` と
同じ形）。

**ADR 0013 が `due_at` を締め出したのとは扱いが違う。** 遅延は採点の外にある
運用値だが、提出物と提出者の対応は採点そのものである。渡らなければ、それを
要する観点は「満たした」と言わない ── 分からないまま通すと誰の認定証でも通る。

## 測定（2026-09-19・実提出 47 件）

`qwen3-vl:8b`（slab-llm）、自己一貫性 3 本。参照ラベルは 47 枚を目視して
付けたもので、**教員の採点ではない**。

| | 書き起こしのみ + 決定的照合 |
|---|---:|
| 採点できた | 46 / 47（PDF 1 件は SKIP して人へ） |
| `certificate` 一致 | 46 / 46 |
| `nickname` 一致 | 46 / 46 |
| 3 本が割れた件 | 0 |
| 1 件あたり | 中央値 37.4 秒（3 本込み） |

**この数字は「判定できた」証拠ではない。**

- `certificate` は **47 件すべてが正規の認定証**で、判別すべき差が無かった。
  `report_ja` で gemma4 が 19 件全部に 2 点を付けて κ = 0 になったのと同じ形
  である。負の対照として ex2 の規則（別講座）を同じ書き起こしに当てたところ
  141 回すべて不一致だったので、講座名の照合自体は効いている。**別講座の
  認定証を出した学生の実物は 1 件も無く、そこは未検証**である
- **プロンプトはこの 47 件に合わせて 1 回直している**（下記）。別データでの
  検証ではない
- n = 47 で `evals/gates.yaml` の `min_sample_size: 30` は超えるが、参照ラベルが
  教員の `BlindMark` ではないので、ゲートの判定には使えない

### 効いたのはモデルではなくプロンプトだった

最初の版は「受講者名（ニックネーム）」と書いていた。すると `Y230020　岡本秀和`
から**学籍番号を落として氏名だけを返す**（47 件中 5 件）。「横線の上の 1 行を
一字も落とさず写す。氏名だけを抜き出してはならない」に変えたら 0 件になった。
より大きいモデルは試していない ── 直したのは文面である。

### 誤りの向きが一方向だった

5 件の誤りはすべて**要件を満たした学生を 0 点にする**側だった。逆向き ──
書いていない学籍番号を捏造して 0 点を 1 点にする ── は **141 回の書き起こしで
1 度も起きていない**。空欄 5 件と氏名のみ 1 件の計 18 回すべてで、正しく空・
氏名のみと答えた。

**この非対称は、モデルに段階を選ばせていたら保証されない。** 書き起こしを
そのまま根拠として残すからこそ、外したときに何を読み違えたのかが画面に出る。

## 扱わないと決めたこと

**PDF は採点しない。** 描画には PyMuPDF が要り、AGPL なので Apache-2.0 の
この repository には入れられない。SKIP を返して人へ回す（**0 点にしない** ──
読めないのは学習者の落ち度とは限らない・ADR 0015）。実データでは 47 件中 1 件。

**画像を縮小しない。** 縮小すると同じ理由で画像処理の依存が要る。生のバイト列
をそのまま送ると 1 件 20.8 秒 → 37.4 秒（実測）になるが、依存を 1 つ増やす
価値のある差ではない。効いてきたら Pillow（BSD）を検討する。

## 帰結

- 採点エンジン（`packages/core` / `packages/grading`）は画像を知らないまま。
  増えたのは `EvaluationRequest.learner_reference` の 1 項目だけで、これは
  評価器の種類とは無関係の事実である
- 認定証を出す課題は、`course.yaml` の観点から `__human__` を外して
  `image_text_check` を指名すれば自動採点に回る。**engine は 1 行も変わらない**
  （ADR 0002 の標準の受け入れ条件）
- 画像を渡す経路ができたので、レポートのページ画像を見る観点
  （`evals/report_ja` の「結果の提示」── 本文からは判定できないと実測で
  分かっているもの）も同じ経路で測れる
